# Индекс обновлений

Индекс канала описывает, какие версии OpenNCALayer доступны и где лежат их файлы. Его читает и проверяет крейт `oncl-update`.

## Где лежит

- Индекс: `updates/v1/<channel>.json`, где `<channel>` — `stable` или `beta`. Публикуется на GitHub Pages проекта байт в байт, рядом со страницами сайта проекта (`site/`): у сайта нет своего пути `updates`, `pages.yml` копирует каталог `updates/` в артефакт после сборки сайта и сверяет копию с репозиторием.
- Подпись: `updates/v1/<channel>.json.minisig` рядом с индексом.
- Сами файлы (пакеты Velopack, расширение) лежат в неизменяемых GitHub Releases. Индекс ссылается на них по URL и sha256.

Клиент скачивает индекс и подпись только по HTTPS, перенаправления тоже: перенаправление на `http://` отвергается. Индекс больше 1 МиБ отвергается.

## Формат

```json
{
  "schema": 1,
  "channel": "beta",
  "seq": 42,
  "generated": "2026-10-01T00:00:00Z",
  "expires": "2026-10-31T00:00:00Z",
  "core": [
    {
      "version": "0.1.0-alpha.2",
      "flavors": {
        "win-x64": {
          "url": "https://github.com/arynyklas/open-ncalayer/releases/download/v0.1.0-alpha.2/OpenNCALayer-0.1.0-alpha.2-win-x64-full.nupkg",
          "sha256": "<64 hex>",
          "size": 123,
          "contents_sha256": "<64 hex>",
          "delta_from": {
            "0.1.0-alpha.1": {"url": "https://…-delta.nupkg", "sha256": "<64 hex>", "size": 45}
          }
        }
      },
      "rollout": 100,
      "revoked": false,
      "notes_url": "https://github.com/arynyklas/open-ncalayer/releases/tag/v0.1.0-alpha.2"
    }
  ],
  "extension": {
    "version": "0.1.0-alpha.2",
    "chromium_zip": {"url": "https://…", "sha256": "<64 hex>"},
    "firefox_xpi": {"url": "https://…", "sha256": "<64 hex>"}
  },
  "plugins": [
    {
      "id": "kz.example.echo",
      "version": "1.0.0",
      "url": "https://github.com/arynyklas/open-ncalayer/releases/download/plugins-20261029/kz.example.echo-1.0.0.onclp",
      "sha256": "<64 hex>",
      "size": 12345,
      "min_core": "0.2.0",
      "modules": ["kz.example.Echo"],
      "replaces": {"symname": "kz.example.echo", "version": "1.2.1"},
      "name": {"ru": "…", "kk": "…", "en": "…"},
      "rollout": 100,
      "revoked": false
    }
  ]
}
```

| Поле | Смысл |
|---|---|
| `schema` | Версия формата, сейчас `1`. Индекс другой схемы клиент не читает. |
| `channel` | `stable` или `beta`. Должен совпадать с каналом клиента и с доверенным комментарием подписи. |
| `seq` | Номер индекса канала, растёт с каждой публикацией. Должен совпадать с доверенным комментарием подписи. |
| `generated` | Когда индекс собран, RFC 3339. |
| `expires` | После этого момента индекс недействителен, RFC 3339. `cargo xtask index` ставит `generated` + 30 дней. |
| `core` | Версии ядра. Каждая версия встречается один раз. |
| `core[].version` | Версия semver (тег `v<version>`). |
| `core[].flavors` | Пакеты по флейворам: `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `osx`, `linux-x64`. Незнакомые ключи клиент пропускает, так что новые флейворы не ломают старых клиентов. |
| `…flavors.<flavor>.url`, `sha256`, `size` | Полный пакет: URL, sha256 (64 строчные hex-цифры) и размер в байтах. |
| `…flavors.<flavor>.delta_from` | Необязательно. Дельта-пакеты: ключ — версия, от которой применяется дельта. |
| `…flavors.<flavor>.contents_sha256` | Обязательно, если есть `delta_from`. sha256 списка файлов полного пакета: число записей zip, затем записи по имени — длина имени (8 байт, little-endian), имя и sha256 распакованных данных (`oncl_update::contents_sha256`). Пакет, который Velopack собирает из дельты, — другой zip тех же файлов (другой порядок и сжатие), его sha256 с `sha256` не совпадает; клиент сверяет его по этой сумме. |
| `core[].rollout` | Процент установок, которым версия предлагается, от 0 до 100. |
| `core[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия больше не предлагается. Клиент читает только индекс своего канала, поэтому релиз, который есть и в `stable`, и в `beta`, отзывается в обоих. |
| `core[].notes_url` | Необязательно. Ссылка на описание релиза. |
| `extension` | Необязательно. Расширение браузера: версия совпадает с версией ядра, файлы для Chromium (`.zip`) и Firefox (`.xpi`). |
| `plugins` | Необязательно. Версии плагинов (`docs/design/plugins.md`). Каждая пара `id` + `version` встречается один раз, каждое имя модуля и каждый заменяемый бандл (`replaces.symname`) принадлежат одному `id` во всём индексе. |
| `plugins[].id`, `version` | Идентификатор плагина и semver его порта (не версия бандла оригинала). |
| `plugins[].url`, `sha256`, `size` | Пакет `.onclp`: URL, sha256 и размер в байтах. |
| `plugins[].min_core` | Самая старая версия ядра, на которой плагин работает. Более старое ядро эту версию не ставит. |
| `plugins[].modules` | Имена модулей протокола, которые обслуживает плагин: от 1 до 32, без повторов. |
| `plugins[].replaces` | Необязательно. Бандл оригинала, который плагин заменяет: `symname` и его версия в формате оригинала. По нему работает `accessory.installBundle`, а `getBundles` показывает его, пока плагин установлен и включён. |
| `plugins[].name` | Название на русском, казахском и английском, для менеджера плагинов и подсказок. |
| `plugins[].rollout` | Процент установок, которым версия предлагается. Бакет — `sha256(install_id ‖ id ‖ 0x00 ‖ version)[0] * 100 / 256`, свой у каждого плагина и версии. |
| `plugins[].revoked` | Необязательно, по умолчанию `false`. Отозванная версия не предлагается; установки на ней переходят на самую новую неотозванную (раскатка при этом не учитывается, допускается откат на старую версию), а если такой нет — плагин выключается. |

Все URL в индексе должны начинаться с `https://`. Незнакомые поля внутри схемы 1 клиент пропускает: так в формат можно добавлять поля без смены схемы.

## Подпись

Индекс подписывается minisign (Ed25519) в режиме prehashed: подписывается хеш BLAKE2b-512 файла. Подписи старого режима (без хеширования) отвергаются.

Доверенный комментарий подписи — `channel=<channel>;seq=<seq>`, например `channel=beta;seq=42`. Пары могут идти в любом порядке, другие пары `ключ=значение` пропускаются, повтор ключа — ошибка. Доверенный комментарий защищён подписью. Клиент сверяет `channel` и `seq` из него с телом индекса, поэтому подпись одного индекса нельзя приложить к другому.

Секретный ключ хранится только у мейнтейнера. В клиент зашиты два открытых ключа: текущий и следующий, для ротации. Они лежат в `crates/oncl-update/keys/{current,next}.pub` и создаются командой `cargo xtask sign keygen`. Сборка крейта `oncl-update` встраивает те из них, что есть (`build.rs`), и отдаёт их через `oncl_update::embedded_keys()`; без файлов ключей в сборке нет, и обновления в ней выключены.

## Подготовка индекса

Индексы лежат в репозитории в `updates/v1/` и публикуются байт в байт: `.gitattributes` запрещает git менять в них концы строк, иначе подпись не сойдётся. Здесь описаны правила и команды; порядок действий мейнтейнера от первого ключа до выпуска — в [`../dev/release.md`](../dev/release.md).

Все файлы индекса лежат в релизах проекта. URL каждой записи должен быть ровно `https://github.com/arynyklas/open-ncalayer/releases/download/v<версия>/<файл>`, где `<версия>` — версия самой записи, а `<файл>` — имя файла этого вида:

- полный пакет — `OpenNCALayer-<версия>-<флейвор>-full.nupkg`;
- дельта — `OpenNCALayer-<версия>-<флейвор>-delta.nupkg`;
- расширение — `openncalayer-chromium-<версия>.zip` и `openncalayer-firefox-<версия>.xpi`.
- плагин — `<id>-<версия>.onclp` в релизе с тегом `plugins-ГГГГММДД[.N]` (а не `v<версия>`): `https://github.com/arynyklas/open-ncalayer/releases/download/plugins-ГГГГММДД[.N]/<id>-<версия>.onclp`. Предварительная версия плагина в `stable` не допускается.

`notes_url` — `https://github.com/arynyklas/open-ncalayer/releases/tag/v<версия>`. Запросы (`?…`), фрагменты (`#…`) и незнакомые флейворы не допускаются. Это правило проверяют `index add` и `index refresh` (и для индекса, который они читают, и для того, который записывают), `sign` и `index check`. Клиент его не проверяет: подписывается только индекс, который прошёл эту проверку.

- `cargo xtask sign keygen --out <каталог>` создаёт пару ключей мейнтейнера: `oncl-index.key` (зашифрован паролем, пароль вводится без эха) и `oncl-index.pub`.
  - Команда отвергает каталог внутри рабочего дерева git, если он не указан в `.gitignore`. Отвергается и файл, который уже отслеживается git.
  - Перед проверкой существующая часть пути разрешается: символические ссылки, junction и `..`. Рабочее дерево ищется по ближайшему каталогу-предку с `.git`, а не поиском самого git: если git не может открыть репозиторий (например, у связанного рабочего дерева пропал основной), команда отказывается писать ключ, а не считает каталог посторонним.
  - Открытый ключ кладётся в `crates/oncl-update/keys/current.pub` (или в `next.pub` для ротации).
- `cargo xtask index add --channel beta --tag v<версия> --release-assets <каталог>` дописывает версию в индекс по скачанным ассетам релиза:
  - полные пакеты по флейворам;
  - дельты; версия, от которой применяется дельта, — самый новый полный пакет старше новой версии в `releases.<флейвор>.json` Velopack из тех же ассетов;
  - расширение, только оба файла вместе.

  sha256 и размеры берутся из файлов. `seq` растёт на 1, `generated` — текущее время, `expires` — через 30 дней. `--rollout` задаёт процент раскатки, по умолчанию 100. Подпись прежнего индекса удаляется: к новому она не подходит.
- `cargo xtask plugin pack <каталог крейта>` собирает плагин под `wasm32-unknown-unknown` и пишет `target/plugins/<id>-<версия>.onclp`. Версия в `plugin.toml` должна совпадать с версией крейта, модуль проходит ту же проверку ABI, что и в демоне. Пути машины сборки (домашний каталог, тулчейн, рабочее дерево) в модуль не попадают: сборка заменяет их на `/cargo`, `/rustc`, `/workspace` и `/plugin`. Архив детерминирован: те же исходники тем же тулчейном дают те же байты.
- `cargo xtask index add-plugin --channel <channel> --tag plugins-ГГГГММДД[.N] --package <файл.onclp>…` дописывает версии плагинов в индекс. `id`, версия, `min_core`, модули, `replaces` и название берутся из манифеста пакета, sha256 и размер — из файла. Повтор `id` + версии, модуль или бандл оригинала (`replaces.symname`), который уже у другого плагина, и предварительная версия в `stable` отвергаются; индекс с новыми пакетами проходит проверку URL и владельцев до записи, так что при отказе файл не меняется. `seq`, `generated`, `expires` и подпись — как у `index add`; `--rollout` задаёт раскатку.
  - В `stable` попадает только порт, чей `registry.toml` в каталоге портов (`--plugins`, по умолчанию `plugins/`) говорит `conformance = "confirmed"`: совместимость проверена на работающем оригинале. Порт с `computed` или пакет, `id` которого нет ни у одного порта, команда в `stable` не добавит. Для `beta` каталог портов не читается.
- `cargo xtask index refresh --channel <channel>` продлевает индекс, не меняя его содержимое: `seq` растёт на 1, `generated` — текущее время, `expires` — через 30 дней. Индекс нужно продлевать и подписывать заново, пока не прошли 30 дней с `generated`.
- `cargo xtask sign updates/v1/<channel>.json --key <секретный ключ>` пишет `.minisig` с доверенным комментарием `channel=…;seq=…`. Перед записью подпись проверяется открытым ключом той же пары: так ловится испорченный ключ или файл, но не подпись не тем ключом — это ловит `index check`. Неверный или истёкший индекс не подписывается, как и индекс с URL не на релизы проекта.
- `cargo xtask index check updates/v1` проверяет индексы перед публикацией:
  - каждый индекс проходит проверку клиента подписью ключом `crates/oncl-update/keys/current.pub` (не `next.pub`: следующий ключ нужен клиентам, подписывать им рано), а его URL и владельцы модулей и бандлов — правила выше; подписи без индекса нет;
  - тег `v<версия>` каждой версии, новой относительно базы или с заменёнными пакетами (если в базе нет индекса канала — каждой), содержит `crates/oncl-update/keys/current.pub`, и это `current.pub` или `next.pub` проверяемого дерева. Без базы (`--no-base`: ручной запуск Pages) теги не проверяются: версии, опубликованные до ротации ключа, хранят в тегах старый ключ. Если каталога `updates/v1` ещё нет (ключи закоммичены раньше первого индекса), проверка проходит, прочитав только ключи, а Pages ничего не публикует. Сборка без ключа не обновляет себя, и переводить на неё установки нельзя. `index add` проверяет то же до записи, а job `index` для тега без ключа PR не открывает и пишет уведомление;
  - относительно базовой ветки (`--base`, по умолчанию `origin/main`) у изменённого индекса `seq` больше, и ни один индекс не удалён;
  - без `--offline` каждый URL пакета ядра, расширения и плагина отвечает на `HEAD` кодом 200. Гейты ключа в теге, `vm-smoke` и `conformance` относятся только к версиям ядра;
  - с `--vm-smoke` на теге каждой новой версии должен стоять статус коммита `vm-smoke = success` (установщики прошли проверку на чистых системах лаборатории);
  - с `--conformance` на теге каждой новой версии в `stable` должен стоять статус коммита `conformance = success`: сборка тега сверена с оригиналом в лаборатории. В `beta` этот гейт не действует: релиз без суффикса проверяется на `conformance` в индексе `stable`, а предварительной версии хватает `vm-smoke`.

  Оба статуса ставит агент лаборатории на коммит тега: сначала `vm-smoke`, затем для того же тега `conformance`. `index-check.yml` запускает проверку с `--vm-smoke --conformance` и читает статусы через API GitHub своим токеном (право `statuses: read`). Флаги несовместимы с `--offline`. «Новая» значит новая относительно базы; без базы (`--no-base`) новой считается каждая версия индекса.

## Публикация

Тег `v<версия>` запускает `.github/workflows/release.yml`:

1. Для каждого флейвора собираются архив, установщик и пакеты Velopack (`cargo xtask package windows|macos|linux`, внутри `vpk pack --packId OpenNCALayer --channel <флейвор>`). Дельта строится от полного пакета флейвора из релиза с наибольшей версией ниже текущей: для релиза — среди релизов, для пререлиза — среди версий любого вида. Этот пакет скачивается прямо из того релиза (`gh release download`; `vpk download github` видит только 10 последних релизов) и сверяется с его `SHA256SUMS`. Если такого релиза нет, дельты нет; любая другая ошибка останавливает сборку. В релиз попадают `OpenNCALayer-<версия>-<флейвор>-full.nupkg`, `-delta.nupkg` (если есть предыдущий пакет), `releases.<флейвор>.json` (фид Velopack: эта версия и полный пакет, от которого построена дельта) и на Windows `RELEASES-<флейвор>`, а также установщики: `openncalayer-<версия>-<флейвор>-setup.exe` для четырёх флейворов Windows, `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`, `openncalayer-<версия>-linux-x64.AppImage`. Собираются `win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64` и `osx`. Флейворы `win7-*` собирает `cargo xtask win7` (с app-local DLL рядом с exe); исполняемые файлы их пакета, `Squirrel.exe` и заглушка Velopack, а также `Setup.exe` проходят гейт импортов Windows 7. Linux собирается в контейнере с glibc 2.28 (`cargo xtask package linux-build`).
2. Рядом ложатся расширение, SBOM `openncalayer-<версия>.cdx.json` (CycloneDX, `cargo cyclonedx`) и `SHA256SUMS`. На каждый файл релиза выпускается аттестация происхождения сборки (`actions/attest-build-provenance`), её проверяет `gh attestation verify <файл> --repo arynyklas/open-ncalayer`.
3. Подпись кода идёт, только если заданы её секреты, иначе шаг пропускается с уведомлением в журнале. Authenticode через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`; подписываются `openncalayer.exe` и `nmhost.exe` до упаковки и каждый `Setup.exe` после неё (app-local DLL сборок Windows 7 не подписываются). Подпись и нотаризация Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`; `.app` (пакет обновления, `.zip` и содержимое `.pkg`) подписывает и нотаризует `vpk pack`; сам `.pkg` подписывается и нотаризуется, только если задан ещё секрет `APPLE_INSTALL_IDENTITY` («Developer ID Installer»). Архив macOS остаётся неподписанным.
4. После публикации релиза job `index` скачивает его ассеты, выполняет `cargo xtask index add` для каждого канала версии и открывает PR в `main` с неподписанными индексами: пререлиз идёт только в `beta`, релиз без суффикса — в `stable` и в `beta`. У каждого индекса свой следующий `seq`, прежние записи сохраняются, индекс другого канала пререлиз не трогает. Флейвор `osx` в индексы пока не добавляется: универсальная сборка ещё не запускалась на Mac с Intel (лаборатория, P9); его пакеты и установщики в релизе есть.

Мейнтейнер на ветке PR при необходимости меняет `rollout`, подписывает каждый индекс PR (`cargo xtask sign`; для релиза — оба), коммитит индексы с их `.minisig` и пушит. Неподписанный индекс `index check` отвергает. PR, открытый workflow, сам проверки не запускает, поэтому `index-check.yml` (`cargo xtask index check updates/v1 --base origin/main --vm-smoke --conformance`) срабатывает на этот пуш. После слияния `pages.yml` ещё раз проверяет индексы и публикует `updates/` на GitHub Pages под `/updates/`. Весь сайт Pages — один артефакт: другие страницы сайта добавятся в тот же артефакт рядом с `updates/`.

Настройки репозитория меняет только мейнтейнер:

- Pages: Settings → Pages → Source: GitHub Actions;
- PR от workflow: Settings → Actions → General → Allow GitHub Actions to create and approve pull requests.

## Проверка на клиенте

`oncl_update::verify` принимает индекс, только если выполнено всё:

1. Индекс не больше 1 МиБ.
2. Подпись сделана одним из зашитых ключей и сходится с байтами индекса и с доверенным комментарием.
3. Доверенный комментарий разобран, в нём есть `channel` и `seq`.
4. Индекс разобран и соблюдает правила формата: схема 1, URL только `https://`, `rollout` не больше 100, версии не повторяются.
5. `channel` и `seq` индекса совпадают с доверенным комментарием, а канал — с каналом клиента.
6. `seq` не меньше последнего принятого для этого канала. Тот же `seq` — тот же индекс, скачанный повторно: так клиент может повторить обновление, которое не скачалось. Каждый новый индекс канала получает новый `seq`.
7. Сейчас раньше `expires` и прошло меньше 30 дней с `generated`. Индекс, который не подписали заново за 30 дней, отвергается, даже если в `expires` стоит более поздняя дата. Срок у каждого канала свой: предварительные версии меняют только `beta.json`, поэтому `stable.json` продлевается отдельно.

JSON разбирается только после проверки подписи.

## Выбор версии

`oncl_update::choose` выбирает версию ядра для установки. Версия предлагается, если выполнено всё:

- она не отозвана;
- она не помечена локально как плохая, то есть не провалила проверку здоровья на этой установке;
- в ней есть пакет для флейвора установки;
- установка попала в раскатку: бакет `sha256(install_id ‖ version)[0] * 100 / 256` меньше `rollout`.

`install_id` — 16 случайных байт установки, `version` — строка версии. У каждой версии свой бакет, поэтому первыми обновляются не всегда одни и те же установки.

Из предложенных версий берётся самая новая:

- новее текущей — обновление;
- иначе ничего не делается.

Если индекс отзывает текущую версию, важнее уйти с неё, чем соблюсти поэтапную раскатку. Поэтому `rollout` не учитывается: берётся самая новая версия, которая не отозвана, не помечена как плохая и имеет пакет для флейвора. Так установка на отозванной версии получает исправление, даже если оно раскатано не на всех (в том числе при `rollout: 0`). Если эта версия новее текущей, это обновление. Если старше — откат (даунгрейд). Только в этом случае клиент откатывается на старую версию.

Если версия ядра вообще не упомянута в индексе (локальная сборка или версия, убранная из индекса), на старую версию клиент не откатывается.

Скачанный пакет сверяется с `size` и `sha256` из индекса (`Package::check_file`). Пакет, который не сошёлся, не применяется.

## Состояние клиента

Файл `<данные>/update/state.json` записывается атомарно:

```json
{
  "last_seq": {"stable": 7, "beta": 42},
  "install_id": "<32 hex>",
  "bad": ["0.2.0-beta.1"],
  "pending_health": {"from": "0.1.0", "to": "0.2.0", "applied": "2026-10-27T10:00:00Z", "started": "2026-10-27T10:00:20Z"}
}
```

| Поле | Смысл |
|---|---|
| `last_seq` | Последний принятый `seq` по каналам. |
| `install_id` | Случайный идентификатор установки, нужен только для бакета раскатки. Никуда не отправляется. |
| `bad` | Версии, которые на этой установке не прошли проверку здоровья. Они больше не предлагаются. |
| `pending_health` | Обновление применено, но новая версия ещё не подтвердила, что работает. Поле есть только в это время. `started` — начало текущего запуска новой версии; при чистом завершении поле стирается. `crashes` — сколько запусков подряд упали или зависли. `rollback: true` — это откат с версии, не прошедшей проверку. `attempts` — сколько раз откат передавался Velopack. |

Если файл повреждён (не читается как состояние), демон записывает вместо него новый: с новым `install_id` и без `last_seq`. Обновления от этого не останавливаются. Если файл не читается по другой причине (нет прав, его держит другая программа), он не трогается: в этом запуске демон не проверяет здоровье и не откатывает, проверка обновлений повторяется через 30–120 минут, а изменение, которое не удалось сохранить, не применяется. Все записи в файл идут под одной блокировкой: каждая перечитывает файл и меняет только своё поле.

## Обновление в демоне

Сам себя обновляет только экземпляр, установленный через Velopack и собранный с открытыми ключами `crates/oncl-update/keys/current.pub` и `next.pub`. Ключи встраиваются при сборке, если файлы есть. Без них, а также в архиве из Releases или в своей сборке обновления выключены: это пишется в журнал и в окно настроек.

Настройки в `settings.json`: `"updates": {"enabled": true, "channel": "stable"}`, канал `stable` или `beta`. Если канал в настройках не записан, сборка предварительной версии (`-alpha.1`, `-rc.1`) читает `beta`, релиз — `stable`: предварительные версии попадают только в `beta`. Записанный канал не меняется. В окне настроек есть флажок «Обновлять автоматически», выбор канала и кнопка «Проверить сейчас». В меню значка есть пункт «Проверить обновления».

Порядок работы:

1. Первая проверка идёт через 2–10 минут после запуска, следующие — раз в 6–24 часа. Время каждый раз выбирается случайно.
2. Индекс канала скачивается с `https://arynyklas.github.io/open-ncalayer/updates/v1/` через прокси из настроек и проверяется, как описано выше. Затем `choose` выбирает версию.
3. Если индекс не скачался, следующая попытка — через 30–120 минут. Если индекс отвергнут, следующая попытка — в обычный срок. Уведомлений в обоих случаях нет. Ошибку видно в журнале и в окне настроек. Если индекса канала ещё нет (ответ 404: в канал ничего не выпускали), в окне настроек пишется «В канале пока нет выпусков», уведомления нет, а следующая проверка — в обычный срок.
4. О новой версии демон сообщает уведомлением «Доступна версия X», один раз на версию.
5. Velopack получает фид из одной выбранной версии: полный пакет и дельту от текущей версии, если она есть в индексе. Файлы скачиваются только по HTTPS и перед передачей Velopack сверяются с `size` и `sha256` из индекса. Полный пакет, который Velopack собрал из дельты или нашёл на диске, принимается, только если он совпадает с полным пакетом индекса по `sha256` и размеру или содержит те же файлы (`contents_sha256`); проверка идёт до того, как пакет встаёт на место и из него извлекается `Update.exe`. Пакет на диске, не прошедший проверку, удаляется и скачивается заново; собранный из дельты заменяется скачиванием полного пакета. Для этого Velopack собирается из изменённой копии в `vendor/velopack` (см. README).
6. Демон ждёт, пока не останется открытых окон и запросов страниц в работе. После последнего запроса должно пройти 30 секунд. Затем индекс проверяется ещё раз: если версию за это время отозвали или обновления выключили, она не ставится. Новые запросы страниц задерживаются до выхода демона.
7. В состояние записывается `pending_health`. Velopack ставит новую версию после выхода демона и запускает её с теми же аргументами.

Проверка здоровья:

- Новая версия при каждом запуске записывает в `pending_health` время `started`. Проверка идёт в отдельном потоке и не зависит от цикла окон.
- Если её серверы и цикл окон проработали 5 секунд подряд, она удаляет `pending_health` и показывает «Обновлено до X».
- Если этого не случилось за 60 секунд после запуска, версия считается плохой. Она попадает в `bad`, а демон, дождавшись простоя, ставит предыдущую версию из её полного пакета в индексе.
- Чистое завершение до подтверждения не считается сбоем. Чистое завершение — это «Выход» в меню значка, остановка демона для обновления или выход с кодом 2 или 3 (TLS не настроен, порт занят). При нём `started` стирается, а счётчик `crashes` обнуляется.
- Учёт запусков начинается сразу после проверки, что демон запущен один, ещё до проверки TLS и порта. Поэтому запуск, который упал при настройке или вышел с кодом 1, тоже считается сбоем.
- Обработчика завершения сеанса (выход из системы, выключение) нет. Если сеанс закончился, пока новая версия ещё не подтвердила здоровье (обычно первые 5–7 секунд запуска), этот запуск считается сбоем. Два таких запуска подряд без подтверждённого запуска между ними откатят исправную версию и отметят её в `bad` на этой машине; следующие версии предлагаются как обычно.
- Если при запуске `started` ещё стоит, прошлый запуск упал или завис, и `crashes` растёт на 1. После двух таких запусков подряд версия попадает в `bad`, и откат делается сразу, до запуска серверов и окон. Один сбой, после которого версия проработала нормально, к откату не ведёт.
- Предыдущая версия после запуска показывает «Обновление откачено».
- Если Velopack не применил откат и снова запустил плохую версию, откат повторяется, но не больше трёх раз. Если Velopack сразу отказался применять откат, повторов нет. В обоих случаях плохая версия остаётся в `bad` и продолжает работать, демон один раз сообщает «Версия X работает с ошибками», а обычные проверки продолжаются.
- Если индекс не скачался, пакет не загрузился или скачанный пакет пропал до передачи Velopack (его может удалить очистка Velopack при другом запуске программы), откат повторяется через 30–120 минут, тоже не больше трёх раз. Этот счётчик живёт в пределах запуска: пока откат не отменён, следующий запуск плохой версии снова пробует скачать его, прежде чем начать работать, и только потом возвращается к этому расписанию. Если за запуск не удались все три попытки, откат отменяется, как при отказе Velopack: плохая версия остаётся в `bad`, демон один раз сообщает «Версия X работает с ошибками», и следующие запуски откат уже не скачивают. При запуске плохой версии на скачивание индекса и пакета отводится не больше 15 секунд: дальше демон запускается как обычно, а откат повторяется в фоне с обычным временем на загрузку.
- Неудавшийся цикл окон — не чистое завершение, даже когда демон выходит с кодом 2 или 3.
- Если в индексе нет пакета предыдущей версии, плохая версия остаётся в `bad`, а демон один раз сообщает об этом. Обычные проверки продолжаются, и исправленная версия установится, когда выйдет.
- Если предыдущая версия тоже в `bad`, отката нет.
