# Автономная локальная командная строка (`oncl`)

`cargo run -p oncl-cli -- …` запускает независимого потребителя SDK. По умолчанию он чисто локальный: не запускает настольную программу, HTTP-сервер, демон или сеанс браузера. С явным `--endpoint` это, наоборот, потоковый клиент HTTP-контракта `oncl-server` (см. [«Удалённый режим»](#удалённый-режим---endpoint)); обнаружения и неявного перехода между этими режимами нет.

Шифрование и расшифрование потребовали бы внешнего бэкенда G01/G02 SDK: команд `encrypt`/`decrypt` нет, замены «только RSA» тоже. Что не покрыто — в разделе [«Известные ограничения»](#известные-ограничения).

## Архив (без установщика)

`oncl` собирается отдельным архивом `oncl-<version>-<flavor>.zip` (Windows: `win-x64`, `win-x86`, а для Windows 7 SP1 — `win7-x64`/`win7-x86`) или `oncl-<version>-<flavor>.tar.gz` (`linux-x64`, сборка под glibc 2.28; `osx`, универсальный). Он **не входит** в настольный пакет OpenNCALayer: ни установщика, ни канала обновлений, ни автозапуска, ничего не пишется вне указанных вами путей. В архиве лежат программа, `README.md`, `docs/cli.md`, `THIRD-PARTY.txt` (лицензии ровно того стороннего кода, что вошёл в этот флейвор; AWS-LC — только в Linux/macOS), `LICENSE` и `NOTICE`; сертификатов, ключей, токенов и тестовых файлов в нём нет. Обновление — распаковка более нового архива.

**Откуда его взять.** Архивы `oncl` и `oncl-server` workflow выпуска собирает только как артефакты запуска (`platform-*`, хранятся 30 дней): к релизу GitHub они не прикладываются, и в списке файлов `0.1.0-alpha.7` их нет. Берите архив из артефакта workflow или собирайте из исходников ([`docs/dev/development.md`](../dev/development.md)).

```sh
tar -xzf oncl-<version>-linux-x64.tar.gz
./oncl-<version>-linux-x64/oncl --version
printf abc | ./oncl-<version>-linux-x64/oncl hash --algorithm sha256 --input -
```

В Windows распакуйте `.zip` (проводником или `tar -xf oncl-<version>-win-x64.zip`) и запускайте `oncl.exe` из этой папки; распространяемый пакет Visual C++ программе не нужен. Команда мейнтейнера, которая собирает, проверяет и прогоняет (smoke) архивы, — `cargo xtask package platform` (`cargo xtask package platform --help`).

## Команды

| Команда | Что делает |
|---|---|
| `hash --algorithm sha256\|gost2004\|gost2015-512 --input -` | Потоковый дайджест файла или stdin |
| `sign --profile …` | Подпись закрытым ключом, привязанная к источнику (см. ниже) |
| `verify --profile …` | Проверка с доверием хоста; отсоединённая — через `--detached` |
| `extract` | Сырое содержимое CMS; **не проверено** |
| `inspect --profile certificate\|container\|cms\|named-key` | Только открытые метаданные |
| `extend --profile cms\|xml\|pdf --level b\|t\|lt\|lta` | Продление свидетельств без ключа |
| `timestamp acquire\|verify` | Самостоятельный токен RFC 3161 |
| `jws sign\|verify`, `jwt encode\|verify\|decode` | JOSE: RS256 / ECGOST3410-2015-512 |
| `plugin call` | Вызов WASM только в рантайме с правами оператора ([«Плагины»](#плагины-oncl-plugin)) |
| `plugin operations` | Операции, которые объявляет манифест плагина, — чтобы писать права; необязательная проверка модуля |
| `batch run` | Упорядоченный смешанный пакет из JSON-манифеста |

Профили подписи: `cms`, `raw`, `digest-sha256|gost2004|gost2015-512`, `xml`, `wsse`, `pdf`, а также `cades-`/`xades-`/`pades-` с `b`, `t`, `lt`, `lta`. Профили проверки: `cms`, `xml`, `xml-kalkan`, `wsse`, `pdf` и те же семейства уровней. Профиль и алгоритм никогда не выводятся из имён файлов или недоверенных токенов.

Пример (Git Bash):

```sh
printf abc | cargo run -p oncl-cli -- hash --algorithm sha256 --input -
```

печатает `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`. `--input -` занимает stdin ровно для одной роли; две роли с stdin завершаются отказом до любого ввода-вывода.

## Подпись закрытым ключом, секреты и полномочия

```text
oncl sign --profile cms --detached --input document.bin --output signature.der \
  --key signer.p12 --secret-file secrets/signer.secret --authorize \
  --root operator-root.der --pki-endpoint https://pki.example.test
```

* `--authorize` — явное подтверждение именно этого источника, профиля, ключа и места назначения. Пароль — не полномочие. Разблокированного кэша между запусками нет, а строгая проверка сертификатов и отзыва всегда предшествует использованию закрытого ключа (`--offline` влияет только на политику проверки, но не на подпись).
* Источник ключа: `--key` (PKCS#12 или JKS; `--alias`, если записей несколько) **или** `--token-reader NAME --token-kind … --token-alias …` (настоящий PC/SC; проверялось только на программном эмуляторе, физического токена не было; отсутствующие считыватели закрываются отказом без вывода).
* Секреты никогда не передаются аргументами. Используйте `--secret-file` внутри существующего **каталога с доступом только владельца** (SDK проверяет владельца и ACL каталога и файла, число ссылок и точки повторной обработки (reparse points) и ничего не чинит) или `--secret-interactive` (буферы фиксированного размера с затиранием; отказ, если stdin — документ или не терминал). В файле допускается не больше 4097 сырых байт / 4096 байт пароля и один завершающий LF/CRLF; ничего не усекается. Процессные тесты охватывают незащищённый каталог, слишком большой, отсутствующий секрет и секрет-каталог (во всех случаях отказ без использования ключа); случай с символической ссылкой требует привилегии, которой на этой машине нет, и не проверялся.
* Интерактивный ввод: Backspace удаляет один символ (скаляр Unicode), Ctrl-U очищает ввод, Ctrl-W удаляет слово, Ctrl-C отменяет. Режимы терминала восстанавливаются при нормальном завершении, при ошибке и при раскрутке стека (unwind). Отсутствие эха, восстановление и Ctrl-C подтверждены на настоящем Windows ConPTY (см. ниже). Принудительное завершение или заблокированное нативное чтение не гарантируют немедленной отмены или восстановления.
* Считыватель `rpassword 7.5.4`/`rtoolbox 0.0.6` по умолчанию сознательно не использован: он наращивает `String` и стирает только её текущую длину, поэтому выведенные из употребления/усечённые копии не затираются.

## Доверие, сеть и время

Доверие даёт только оператор: `--root`, `--intermediate`, `--pki-endpoint` (точные origin; литеральные IP закрепляют себя сами), `--pki-pin 'http://host:port=IP:port'` для DNS-origin (окружающего DNS нет), `--tsa-url` (+ `--tsa-policy OID`, обязателен для XAdES) для получения свидетельств; CAdES/PAdES/XAdES T/LT/LTA подтверждены, `--as-of <Unix seconds>` — явные часы (по умолчанию — UTC хоста). Сертификаты, пришедшие в документе, якорями доверия не бывают. Вся конфигурация читается под одним бюджетом памяти: не больше 1024 файлов сертификатов, 64 endpoint/pin и `--configuration-bytes` (по умолчанию 16 МиБ) закодированных сертификатов, причём каждый дубликат списывается.

`oncl verify --profile cms --input <signature.p7s> --root <NCA root>` — единственная проверка подписи CMS в проекте: она заменила `openncalayer cms-verify` демона (удалена вместе с путём кэша `crl/` и встроенным набором CA НУЦ по умолчанию). Отличия намеренные: неявного набора доверия по умолчанию нет (корни НУЦ, которым вы доверяете, передайте через `--root`), вход — DER или BER либо, с явным флагом `--pem` (только профиль CMS, не больше 16 МиБ текста, ровно один блок `CMS` или `PKCS7` и ничего вокруг, декодируется до разбора; текстовое поле демо-страницы даёт PEM, её файл `.p7s` — DER), проверка всегда строгая (политика совместимости с NCALayer, `OperationPolicy::ncalayer_compatibility()`, — выбор встраивающего хоста, переключателя в командной строке у неё нет), отчёт строится по проверкам, а недоказанное время подписания или недоступные данные об отзыве дают `Indeterminate` (код выхода 3).

С `--profile cades-*` или `pades-*` подпись, которая проверяется, но нарушает правило baseline, сообщается с причиной `Profile(SigningTimeForbidden|SigningTimeMissing|ContentTypeNotData|SigningCertificateMissing)`: проверка подписи остаётся `Passed`, вердикт — `Invalid` (код выхода 2), а `ades_level` не заявляется. PAdES самого Kalkan несёт атрибут signing-time, который запрещает EN 319 142-1, таблица 1, поэтому под `pades-*` он сообщается так, тогда как `--profile pdf` судит те же байты только по целостности и доверию.

## Отчёты, коды выхода и вывод

| Код выхода | Значение |
|---:|---|
| 0 | Завершено либо проверка `Valid` |
| 2 | Проверка `Invalid` |
| 3 | Проверка `Indeterminate` (например, `--offline`, статус недоступен) |
| 4 | Пакет не завершён (есть элементы с ошибкой или не запущенные) |
| 1 | Сбой выполнения, ввода, ресурсов, прав или использования |
| 130 | Кооперативная отмена (Ctrl-C/Ctrl-Break) |

Дедлайн (`--timeout-seconds`) для любой одиночной команды — код выхода **1** `DeadlineExceeded`, а для пакета — **4** (частичный результат). Поле `code` верхнего уровня отчёта пакета — `Completed`, `Partial`, `Cancelled` или `DeadlineExceeded`; отчёт, который не удалось доставить после остановки, диагностируется в stderr (`report_delivery_failed_after_stop`) и никогда не меняет 130/4.

`--json` пишет отчёт в stdout; `--report <new path>` готовит (staged) отдельный отчёт. Бинарный `--output -` вместе с JSON в stdout отклоняется до любого ввода-вывода. Ошибки использования не раскрывают значения аргументов. Артефакты готовятся (staged) и публикуются без перезаписи (no-clobber); существующее место назначения или источник никогда не заменяются. Квота отчёта, сериализация и синхронизация файла допускаются **до** публикации документа; физический ввод-вывод отчёта после этого всё ещё может завершиться сбоем и сообщается честно (документ и отчёт — не одна атомарная транзакция, а закрытая подпись никогда не откатывается).

## JWS/JWT, WS-Security, плагины, пакеты

* `jws sign|verify --serialization compact|flattened|general [--detached]`; `jwt encode|verify|decode`. `jwt verify` принимает `--issuer`, `--audience`, `--leeway-seconds` и часы хоста; `jwt decode` явно ничего не проверяет. Полезная нагрузка JWS ≤ 256 КиБ, claims ≤ 64 КиБ.
* `sign|verify --profile wsse` с `--soap-version soap11|soap12`, `--wsse-role`, `--wsse-required-header`, `--wsse-timestamp-required`, `--wsse-timestamp-max-lifetime` (проверка), а для подписи — `--wsse-token-reference ncanode-x509-key-identifier|binary-security-token`, `--wsse-token-id`, `--wsse-body-id`, `--wsse-timestamp-id|created|expires`. Неуместные параметры отклоняются до ввода-вывода.
* `plugin call` / `plugin operations`: вызов плагина только в рантайме и перечень операций, объявленных манифестом; установка — не полномочие. Флаги, типизированные параметры, согласие, аудит, отказы и коды выхода — в разделе [«Плагины»](#плагины-oncl-plugin).
* `batch run --manifest batch.json [--key … --secret-file …] --authorize`: элементы `hash`, `sign` (`cms|cms-detached|raw`), `verify` (необязательный `detached`), `extract`, у каждого уникальный `id`. Весь манифест допускается до любого ввода-вывода источников и ключей; места назначения не должны существовать, а выход не может питать другой элемент. Каждый готовый выход публикуется, когда завершается его элемент, поэтому последующий сбой или отмена сохраняют прежние файлы. Плохой источник приводит к сбою только своего элемента. Код 0/2/3 — по худшей проверке, 4 — при любом элементе с ошибкой или не запущенном, 130 — при отмене.

Настоящая доставка Ctrl-Break в принадлежащую группу дочерних процессов (Windows) завершает работу кодом 130; чтения остаются кооперативными.

## Плагины (`oncl plugin`)

```text
oncl plugin operations --manifest plugin.toml [--wasm plugin.wasm] [--json]
oncl plugin call       --manifest plugin.toml --module plugin.wasm --operation OP --caller LABEL
                       --output - [--allow-import NAME …] [request] [key and grants]
```

Установка — не полномочие. Оператор, запускающий команду, сам называет вызывающего (метка `LocalOperator`), операцию, точные импорты, ключ и базы PKI; плагин не может расширить ни одно из них. Здесь нет GUI, нет origin браузера и **нет запроса**: обязательный диалог плагина возвращает типизированный `InteractionRequired`, а согласия никто не спрашивает. Обе команды только локальные; с `--endpoint` они отклоняются с `RemoteUnsupported` до любого ввода-вывода.

### `plugin operations`: что объявлено

Перечисляет `[[operations]]` манифеста (`Manifest::operations()` из `oncl-plugin`, разборщика, которым пользуются `plugin call` и `cargo xtask plugin-ops-check`), чтобы права можно было писать, не читая TOML. Ключей не открывает и ничего не запускает.

| Флаг | Значение |
|---|---|
| `--manifest PATH` | `plugin.toml` плагина (не больше 64 КиБ) |
| `--wasm PATH` | Дополнительно скомпилировать этот модуль (не больше 16 МиБ) относительно манифеста: каждый импорт, который объявляет операция, должен быть импортом модуля, а каждый импорт модуля — объявлен возможностью (capability) (библиотечная проверка `plugin-ops-check`). Код 1, если не подходит |
| `--json`, `--report PATH` | Отчёт в виде JSON (глобальные флаги; `--report` создаёт новый файл и ничего не печатает) |

```text
$ oncl plugin operations --manifest plugins/example/plugin.toml
plugin test.cli 1.0.0: 2 declared operation(s)
operation sign
  label: "a"
  server: yes  manual: no
  cli: yes
  imports: keys_sign_raw
  network: pki
  param file: document (at most 4096 bytes)
  key: raw, content param:file
    signs with your key: a raw signature of the content
operation manual-only
  label: "a"
  server: no  manual: yes
  cli: no (not for the CLI: server = false)
  imports: none
  network: none
  param file: document (at most 4096 bytes)
  key: none
```

`cli:` показывает, может ли `plugin call` выполнить операцию: нужны `server = true` и содержимое, которое хост умеет выполнять. Операция с содержимым `derived` показывается как `cli: no (not runnable: derived content)`: ни один хост пока её не запускает, и `plugin call` отказывает (`subcode=not-declared`). Слова об использовании ключа и о профиле — английские тексты хоста из окна установки (то, что ядро навязывает подписи); `label` и любой `plugin's xpath` — собственный недоверенный текст плагина, он печатается в кавычках и с экранированием. Плагин без `[[operations]]` печатает `declares no operations`.

JSON (`code` — `Completed` либо `InvalidInput`, когда `--wasm` не подходит; `applied` всегда `NotApplied`; необязательные поля при отсутствии опускаются):

| Поле | Значение |
|---|---|
| `code`, `applied` | как выше |
| `plugin` | `{id, version}` |
| `operations[]` | по одному объекту на каждую объявленную операцию, в порядке манифеста |
| `operations[].name`, `.label` | имя операции; английская метка плагина (недоверенная) |
| `.server`, `.manual` | объявленные флаги |
| `.runnable`, `.derived` | `runnable` равен `false` ровно тогда, когда `derived` равен `true` (производное содержимое) |
| `.cli` | `server` и `runnable`: операция, которую принимает `plugin call` |
| `.imports` | объявленные импорты хоста (максимум, который может назвать `--allow-import`) |
| `.network` | `{"kind":"none"}`, `{"kind":"pki"}` или `{"kind":"urls","urls":[…]}` |
| `.params[]` | `{name, kind}`, где `kind` — `document` (`max_bytes`), `text` (`max_chars`), `choice` (`choices`), `flag` или `locale` |
| `.keys[]` | по одному на каждое использование ключа: `kind` (`raw`, `cms`, `cms_ex`, `xml`, `xml_ex`, `xades`), `content` (`param:<name>` или `derived`), `words` и `profile` (навязанные параметры словами, если есть что сказать) |
| `.xpaths` | собственные XPath плагина для профиля (недоверенные), если они есть |
| `module` | с `--wasm`: `{ok}` и, когда `false`, `error` (причина от библиотеки) |

### `plugin call`: флаги

| Флаг | Значение |
|---|---|
| `--manifest`, `--module` | Манифест (≤ 64 КиБ) и модуль (≤ 16 МиБ) единственного плагина, установленного для этого процесса |
| `--operation OP` | Операция: объявленная с `server = true` либо, для плагина без объявлений, метка, которую выдаёт оператор |
| `--caller LABEL` | Метка оператора, записываемая как вызывающий (никогда не origin и никогда не берётся у плагина) |
| `--allow-import NAME` | Точные импорты хоста, которые выдаются (повторяется, только известные имена, не больше 80). Для объявленной операции они должны входить в её объявленные импорты; если не заданы — выдаются все объявленные. Для плагина без объявлений отсутствие флага означает «ни одного» |
| `--output PATH\|-` | Куда пишется ответ (никогда не перезаписывает; `-` — stdout, его нельзя сочетать с `--json` в stdout) |
| `--args-file PATH\|-` | **Свободный** JSON-запрос (≤ 256 КиБ): то, что принимает плагин без объявлений и что объявленная операция всё ещё допускает (оператор доверяет запросу, как раньше) |
| `--param NAME=VALUE` | Типизированный параметр `text`, `choice` или `locale` объявленной операции (повторяется) |
| `--param-file NAME=PATH\|-` | Параметр `document`, читаемый из файла (`-` — stdin; не больше одного источника stdin на команду) |
| `--param-flag NAME` | Параметр `flag`, установленный в true; объявленный флаг, который не назван, равен false |
| `--key PATH [--alias A]` или `--key-name N --key-config FILE` | Ключ, привязанный как handle `--key-handle` (по умолчанию 1); см. [«Именованные источники ключей»](#именованные-источники-ключей) |
| `--secret-file PATH` \| `--secret-interactive` | Пароль ключа, как для `sign` |
| `--authorize` | Обязателен с ключом: подтверждает именно это использование ключа |
| `--plugin-bytes` | Согласие оператора на использование ключа в объявленной операции (ниже); требует ключа |
| `--plugin-pki-endpoint GET=URL` / `POST=URL` | Точные базы PKI, до которых может дотянуться проверка ключа плагина (≤ 16; требует объявленного `network = "pki"`) |
| `--profile` | **Не принимается** (`oncl: ProfileFromManifest`): профиль подписи объявленной операции — из манифеста, его навязывает Core |

Глобальные флаги (`--json`, `--report`, доверие и `--timeout-seconds`) ведут себя как у остальных команд. `--args-file` и любой флаг `--param*` сочетать нельзя (`InvalidCombination`); неверный `NAME=VALUE`, имя, не подходящее под `^[a-z][a-z0-9_]{0,31}$`, больше 16 параметров одного вида, два источника stdin (`StdinConflict`) или источник stdin вместе с `--secret-interactive` — ошибки использования, которые не раскрывают значения и ничего не открывают.

### Типизированные параметры

Для объявленной операции без `--args-file` Core строит запрос из шаблона манифеста точно так же, как ручное окно (`Engine::plugin_server_request`; `module` и `method` берутся только из манифеста, каждый плейсхолдер, занимающий всю строку, заменяется типизированным значением, документ — стандартным base64, ключи отсортированы, запись компактная). Всё проверяется до чтения любого секрета и открытия ключа, а операции без параметров флаги не нужны вовсе:

* каждый объявленный параметр должен быть задан один раз (флаг можно опустить: false); необъявленное имя — `unknown-param`, повторное — `duplicate-param`, отсутствующее — `missing-param`;
* документ берётся только из `--param-file`, а text, choice и locale — только из `--param` (иначе `param-wrong-kind`); choice должен быть одним из объявленных `choices`, locale — `ru`, `kk` или `en`, text — не длиннее `max_chars` символов (корректный абсолютный XPath, если его читает профиль; а если это подписываемое содержимое — без управляющих символов, кроме `\n` и `\t`, и без двунаправленных и невидимых, поэтому `\r` тоже отклоняется) (`param-invalid-value` / `param-too-large`);
* файл документа читается только для объявленного документа и никогда не дальше его объявленного `max_bytes` (и предела запроса 256 КиБ): файл больше — это `InputLimit`, `subcode=param-too-large`, а пустой — `param-invalid-value`;
* весь запрос должен уместиться в 256 КиБ (`request-too-large`).

Текстовый параметр, который читает профиль ключа (`element = "param:xpath"`), служит ещё и тем, с чем сверяется грант `--plugin-bytes`: грант покрывает ровно профиль с этим значением, поэтому плагин, подписывающий другим элементом, получает `options-mismatch`.

Плагин **без** `[[operations]]` не меняется: он принимает только `--args-file`, а `--param*` или отсутствие `--args-file` отклоняются (`PermissionDenied`, `subcode=not-declared`), потому что сверять их не с чем. `--plugin-bytes` на него не действует (предупреждение об этом сообщает).

`plugin call` запускает только операцию с `server = true`. Плагины, поставляемые в `plugins/`, объявляют 30 операций, все с `manual = true` для ручного окна настольной программы ([руководство](manual-plugins.md)) и ни одной с `server = true`, поэтому `oncl plugin call` отказывает каждой из них с `subcode=not-declared`; `plugin operations` их по-прежнему перечисляет.

### Согласие и аудит

CLI никогда не спрашивает. Для объявленной операции Core выдаёт билет на каждое использование ключа и сверяет его с объявлением (одно использование, объявленные вид и параметры), а поскольку CLI не может привязать байты, которые подписывает плагин, к документу, для использования ключа нужен `--plugin-bytes`: **согласие даёт оператор, запускающий команду**, и флаг означает, что он принимает: плагин сам выбирает байты, которые подписывает ключ (при свободном `--args-file` грант привязывает только операцию, вид и параметры, а что подписывать, решает плагин; с типизированными параметрами он привязывает и содержимое: содержимое билета должно равняться точным байтам, переданным для параметра, к которому привязано использование ключа, — текст как UTF-8, документ как байты файла, иначе использование отклоняется до ключа с `subcode=content-mismatch`. Использование в форме дайджеста нельзя вычислить до открытия ключа, оно отклоняется с `subcode=content-binding-unavailable`). Без флага использование отклоняется до применения ключа (`subcode=not-granted`). `--plugin-bytes` покрывает одно использование объявленного вида с точно объявленными параметрами (параметры, которые профиль читает из `--param`, — это эти значения); отклонение — `options-mismatch`, второе использование за один вызов — `key-use-spent`.

CLI не ведёт журнала; запись оператора — это stderr. Перед использованием ключа разрешённое использование ключа объявленной операции пишет одну строку (доверенные факты билета Core; никогда не документ, не значение параметра, не секрет и не nonce), а после неё — обычную строку `private_use`:

```text
oncl: plugin_use operation_id=7 plugin=test.cli version=1.0.0 package=2:<sha256 of manifest+module> operation=sign caller=local-operator declared=true grant=cli-plugin-bytes content_sha256=<sha256 of the bytes signed> content_len=14 prehashed=false options_sha256=<sha256 of the forced options> ticket=<sha256 digest of the ticket>
oncl: private_use operation_id=7 applied=Applied succeeded=true
```

`grant=cli-plugin-bytes` — это согласие (у интерактивного одобрения вместо него стоял бы хеш nonce); `package=2:…` — loose-хеш пакета (вид 2) двух названных вами файлов. Отклонённое использование ключа пишет вместо этого `oncl: plugin_refused operation_id=… subcode=… plugin=… operation=…`, без использования ключа.

### Коды выхода, отказы и строка сбоя

| Код выхода | Значение |
|---:|---|
| 0 | Завершено (`plugin operations`: перечислено, а при заданном `--wasm` модуль подходит) |
| 1 | Любой отказ или сбой, включая каждую ошибку использования и `--wasm`, который не подходит |
| 130 | Отменено (Ctrl-C/Ctrl-Break) |

Сбой печатает в stderr `oncl: <code>; subcode=<id>; applied=<NotApplied|Applied|Unknown>` (`subcode=` — только если у отказа он есть) и ничего в stdout. Отклонённая команда плагина никогда не печатает JSON-отчёт: JSON-поле `subcode` принадлежит элементам `batch run` и HTTP-ошибке `oncl-server`; здесь контракт — строка сбоя, а код выхода и `applied` — как у любой команды. Стабильные подкоды `plugin call`:

| Код | `subcode` | Причина |
|---|---|---|
| `PermissionDenied` | `not-declared` | Операция не объявлена, не `server = true` или производная; импорт сверх объявления; типизированные параметры (или отсутствие `--args-file`) у плагина без объявлений; имя, которое вызывает плагин, не объявлено |
| `PermissionDenied` | `no-key-use` | `--key` для операции, не объявляющей использования ключа |
| `PermissionDenied` | `network-not-declared` | `--plugin-pki-endpoint` без `network = "pki"` |
| `PermissionDenied` | `not-granted` | Использование ключа без `--plugin-bytes` (или не тот плагин или операция) |
| `PermissionDenied` | `key-mismatch` | Использование другого ключа, чем тот, что открыла команда (как на сервере; единственное использование не расходуется) |
| `PermissionDenied` | `content-mismatch`, `content-binding-unavailable` | Типизированные параметры: плагин подписывает не те байты, что переданы, либо привязанное использование — в форме дайджеста |
| `PermissionDenied` | `options-mismatch`, `kind-mismatch`, `key-use-spent`, … | Использование ключа отличается от объявления (весь список — в [дизайне](../design/manual-plugins.md), §4.8); ключ не применялся, кроме `key-use-spent` (первое использование остаётся `Applied`) |
| `InvalidInput` | `unknown-param`, `duplicate-param`, `missing-param`, `param-wrong-kind`, `param-invalid-value`, `invalid-template` | Типизированный параметр неверен (выше) |
| `InputLimit` | `param-too-large`, `request-too-large` | Параметр больше объявленного размера или запрос больше 256 КиБ |

### Примеры

Объявленная операция с параметром-документом и ключом (Git Bash; манифест объявляет `sign` с `server = true`, `param file` — документ, `keys_sign_raw` и `network = "pki"`):

```sh
oncl plugin operations --manifest plugin.toml                    # what may I grant?
oncl plugin call --manifest plugin.toml --module plugin.wasm \
  --operation sign --caller ops-laptop --output signature.b64 \
  --param-file file=statement.pdf \
  --key signer.p12 --secret-file secrets/signer.secret --authorize --plugin-bytes \
  --root nca-root.der --pki-endpoint https://pki.example.test \
  --plugin-pki-endpoint GET=https://pki.example.test/ocsp --plugin-pki-endpoint POST=https://pki.example.test/ocsp
```

Объявленная операция без ключа с типизированными параметрами text, choice и flag:

```sh
oncl plugin call --manifest plugin.toml --module plugin.wasm --operation note \
  --caller ops-laptop --output - \
  --param text='hello' --param pick=two --param lang=kk --param-flag on
```

Плагин без объявлений (без изменений: метку и импорты называет оператор, запрос свободный):

```sh
oncl plugin call --manifest plugin.toml --module plugin.wasm --operation hash \
  --caller ops-laptop --allow-import hash --args-file request.json --output -
```

`plugin call --json` печатает `{operation_id, code: "Completed", applied, response_bytes}` после записи артефакта ответа (сам ответ идёт в `--output`).

## Параметры legacy XML (`XmlSignSpec` / `XadesSpec`)

`sign --profile xml|xades-b|xades-t|xades-lt --legacy` выбирает охраняемый фасад, совместимый с Kalkan/NCALayer (та же строгая проверка до использования закрытого ключа, тот же охранник). Типизированные параметры, каждый сопоставлен одному полю SDK: `--legacy-element`, `--legacy-parent`, `--legacy-namespace PREFIX=URI`, `--legacy-other-prefix-uri`, `--legacy-placement document-element|first-child`, `--legacy-signature-method|--legacy-digest-method rsa-sha256|gost2004|gost2015-512`, `--legacy-signed-info-c14n`, `--legacy-transform enveloped|inclusive|…` (enveloped первым и один раз, не больше одной канонизации), `--signature-id`, `--legacy-signing-time-id|--legacy-signing-time|--legacy-signing-time-reference`, `--legacy-line-breaks`, `--legacy-base64-line-breaks on|off`, `--legacy-output as-is|serialize` с `--legacy-xml-declaration`, `--legacy-standalone-no`, `--legacy-keep-outer-whitespace`, а для XAdES — `--legacy-chain CERT.der` (открытые издатели, ≤16 файлов по ≤16 КиБ). Неподдерживаемые сочетания (legacy CMS/PDF/WSSE/XAdES-LTA, `--add`, `--target-id`, параметры XML для XAdES, уровень, требующий TSA, без `--tsa-url`, неверные привязки пространств имён, управляющие символы) — это `InvalidCombination`/`TsaRequired` до любого ввода-вывода. Ни один параметр не принимает путь к ключу, URI алгоритма или произвольное преобразование. XAdES T/LT/LTA (baseline и legacy) требуют `--tsa-url` **и** `--tsa-policy OID` (иначе `TsaPolicyRequired` до любого ввода-вывода; токен, политика которого отличается от запрошенной, отклоняется после использования ключа и сообщается как `applied=Applied`); baseline XAdES требует ещё и `--signature-id`.

## Именованные источники ключей

`--key-name NAME --key-config keys.json` (sign, jws/jwt, batch, plugin) разрешает NAME через JSON-файл оператора (без секретов, ≤64 КиБ, ≤64 записей, неизвестные поля запрещены, относительные пути разрешаются относительно файла). Файл выбирает, какой контейнер или считыватель открывает выданное имя, поэтому его читают **как файл секрета**: из каталога с доступом только владельца, через проверки владельца/ACL/ссылок SDK, только обычные файлы, его байты списываются с единого общего бюджета конфигурации, чтение идёт контрольными кусками (checkpointed chunks):

```json
{"keys":[{"source":"file","name":"main","path":"signer.p12","alias":null},
         {"source":"token","name":"card","reader":"<PC/SC reader>","kind":"kaztoken","alias":"<key alias>"}]}
```

Имя — это авторизуемый id ключа (`named:NAME`); путь к контейнеру и считыватель никогда не появляются в командной строке, а `--key-name` конфликтует с `--key`/`--token-reader`. `inspect --profile named-key --key-name … --key-config … --secret-file …` читает открытые метаданные именованного источника — файла/JKS/PKCS#12/токена — через провайдер только для чтения (без охранника, без использования закрытого ключа).

## Источники-токены и программный эмулятор

`--token-reader` (настоящий PC/SC) и именованные записи токенов проверяются в тестах на программных токенах репозитория: соберите с `--features token-emulator` и задайте `ONCL_TOKEN_EMULATOR=<oncl-token emulator config.toml>`. Переменная существует только в этой feature (в релизах — никогда); нечитаемый файл — это отказ, а не откат на другой путь (fallback). Физический токен не использовался.

## Отмена, дедлайн и завершающие отчёты

Частичный пакет, остановленный не отменой и не дедлайном, чей отчёт доставить нельзя (закрытый stdout, недоступный для записи `--report`), завершается кодом **1** (сбой выполнения); только остановка отменой или дедлайном сохраняет 130/4 поверх сбоя отчёта.

Пакет, остановленный Ctrl-C/Ctrl-Break или `--timeout-seconds`, всё равно выдаёт завершающий отчёт (по элементам `Completed|Failed|NotRun`, `applied`, `published`, хеш `digest`) из памяти, зарезервированной до первого использования закрытого ключа; код 130 при отмене, **4** при дедлайне. Файл `--report`, записываемый после остановки, создаётся без перезаписи сразу, а не через staging. Прерванный элемент — `Failed` с кодом `Cancelled`/`DeadlineExceeded`. Приоритет кода выхода пакета: 130 > 4 > 2 > 3 > 0. Ctrl-C на интерактивном запросе секрета — `Cancelled` (130).

## Известные ограничения

* **Терминалы:** отсутствие эха, восстановление режима и Ctrl-C подтверждены только на Windows ConPTY; путь Unix `termios` и сигналы Linux/macOS не выполнялись.
* **Заявления об уровне XAdES.** Заявление XAdES-LT/LTA (`ades_level` и профили проверки `xades-lt`/`xades-lta`) требует штампа подписи, значений отзыва И `CertificateValues` со всеми сертификатами пути подписанта выше листа, включая якорь доверия (ETSI EN 319 132-1 §5.4.2); `sign --profile xades-lt` их выпускает. Документ без них заявляется как `T` (`xades-lt` отклоняет его с `InvalidInput`). Это строже, чем у CAdES/PAdES, где заявление LT сегодня требует только штампа плюс статуса отзыва: асимметрия пока намеренная. Проверка охватывает только путь подписанта; путь службы штампов времени и полнота её `TimeStampValidationData` в заявление не входят. `sign --profile xml --add` поверх подписи, чья ссылка покрывает позицию новой подписи (весь документ, объемлющий элемент или член Manifest, если только она не отбрасывает подписи), отклоняется до использования ключа (`InvalidInput; applied=NotApplied`).
* **XAdES с полным CRL удостоверяющего центра.** `verify --profile xades-b|t|lt|lta` допускает встроенный CRL до квоты CLI 32 МиБ на один CRL (48 МиБ всего): XAdES-LT от NCANode/Kalkan около 27 МБ (полный CRL НУЦ в base64) даёт отчёт (подпись `Passed`, цепочка и отзыв оцениваются по `--root`/`--as-of` хоста точно как для XAdES-T) вместо `MetadataLimit`. CRL, выпущенный не издателем подписанта, статуса отзыва не даёт; CRL, перечисляющий подписанта, отзывает его. Подпись или продление XAdES-LT/LTA с CRL больше 256 КиБ не поддерживается (`MetadataLimit`); см. `docs/dev/sdk.md`.
* **Долгосрочный статус (`lt`/`lta`).** Статус отзыва, встроенный в подпись, оценивается на момент, который доказывает штамп подписи, а не по вашим часам: при `--as-of` или часах хоста, сдвинутых позже, документ CAdES/PAdES/XAdES `lt`/`lta` по-прежнему судится по тому, что было свежим в этот доказанный момент, при условии что сертификаты подписанта и цепочки тогда были действительны (для тестовых фикстур NCANode, чьи штампы здесь не проверяются, это не обещано). Статус с `nextUpdate` свеж, пока доказанное время ему предшествует; статус без него (OCSP НУЦ) должен быть выпущен не раньше чем за 300 с до этого момента. Статус, выпущенный после вашего времени проверки (для OCSP — более чем через 300 с), уже просроченный по `nextUpdate` на доказанный момент, недоверенный, отозванный не позже доказанного момента или относящийся к другому сертификату, отклоняется. Подпись без проверенного штампа (`b`) судится по текущему времени, как и статус, который проверяющий получает сам. Правило и ссылки на стандарты: `docs/dev/sdk.md`.
* **Свидетельства:** подпись CAdES-LT/LTA и PAdES-LT/LTA и `extend` без ключа через CLI подтверждены (ниже). Материалы оператора передаются через `--evidence-certificate`, `--evidence-ocsp`, `--evidence-crl` (открытые файлы DER, не больше 64 каждого вида, ≤256 КиБ каждый, ≤8 МиБ всего, списываются с общего резерва конфигурации до любого ввода-вывода документа или ключа; допустимы только с CAdES/PAdES sign и `extend`). Подпись CAdES-LT/LTA и `extend` без ключа B→T→LT→LTA плюс продление LTA подтверждены на замкнутой (loopback) PKI (ответ OCSP без `nextUpdate` должен быть выпущен не раньше чем за 300 с до штампа, иначе он должен нести `nextUpdate` позже штампа, и ни один ответ не может быть выпущен после `--as-of`; обязательны `--tsa-url` + `--tsa-policy`). Подпись LT/LTA без материалов сертификатов+OCSP/CRL — это `EvidenceMaterialRequired` до любого ввода-вывода; материал, который SDK находит недостаточным, обнаруживается только после использования ключа и сообщается как `applied=Applied`. Подпись PAdES-LT/LTA и `extend` PDF без ключа (T→LT→LTA) подтверждены так же и независимо проверены pyHanko (подпись целая/действительная/доверенная по материалам отзыва только из DSS при обязательном отзыве и отключённой загрузке; содержимое DSS и DocTimeStamp; изменённый байт даёт у CLI код выхода 2, а pyHanko отклоняет подпись).
* **JKS:** подпись работает с той же строгой проверкой, что и PKCS#12 (`--alias` выбирает запись); подпись ГОСТ проверяет сам SDK, а не независимый ГОСТ-оракул. Охраняемый фасад legacy XML отклоняет подписанта ГОСТ-2015 (`InvalidInput`, до использования ключа; baseline XML с ГОСТ работает).
* Для публикации нужно место назначения на том же томе с поддержкой жёстких ссылок (FAT/exFAT/SMB дают сбой после использования ключа). Память WASM плагина жёстко ограничена 1 МиБ. `--pki-pin` — это *адресная* привязка DNS, а не секретный PIN.
* `inspect --profile container` требует `--alias`. Шифрования и расшифрования не существует (G01/G02 внешние); команд для него нет.

## Поля отчёта `--json`

`--json` печатает один JSON-объект. Общие ключи: `operation_id` (число), `code` (`Completed` при успехе), `applied` (`NotApplied`, `Applied` или `Unknown`: применялся ли закрытый ключ). Значения с пометкой *текст* — это Rust-представление `Debug` перечисления или структуры SDK: они достаточно стабильны, чтобы их читать, но меняются вместе с перечислением SDK (см. руководство по SDK); завязывайте скрипты на `code`, `applied`, `verdict` и код выхода, а не на эти тексты.

| Команда | Поля |
|---|---|
| `hash` | `operation_id`, `code`, `applied`, `digest` (шестнадцатеричная строка в нижнем регистре), `bytes_in` |
| `sign`, `extend` (записанный выход) | `operation_id`, `code`, `applied` (*текст*), `profile` (*текст*), `provenance` (*текст*), `bytes_in`, `bytes_out`, `signer_count`; `xml` (*текст*) только когда операция выдала отчёт XML |
| `extract` | `operation_id`, `code`, `applied` (`NotApplied`), `bytes_out`, `verified` (всегда `false`) |
| `verify` | `operation_id`, `code`, `applied` (всегда `NotApplied`), `verdict` (`Valid`/`Invalid`/`Indeterminate`), `policy` (*текст*), `checked_at` (секунды Unix), `ades_level` (*текст* или `null`), `signers`; `xml` / `pdf` (*текст*), когда документ — XML / PDF |
| `signers[]` | `signature`, `chain`, `validity`, `revocation`, `timestamp`, `key_usage`, `time_basis` (все *текст*), `claimed_signing_time` (секунды Unix или `null`), `ades_level` (*текст* или `null`), `reasons` (*текст*) |
| `inspect` | `operation_id`, `code`, `applied` (`NotApplied`), `kind` (*текст*), `container_integrity` (*текст* или `null`), `entries`; `cms` (*текст*) для CMS |
| `entries[]` | `alias`, `certificate_sha256`, `subject_cn`, `serial_hex`, `signature_algorithm_oid`, `public_key_algorithm_oid`, `not_before`, `not_after` (секунды Unix); каждое может быть `null` |
| `batch run` | `operation_id`, `code` (`Completed`/`Partial`/`Cancelled`/`DeadlineExceeded`), `attempted`, `completed`, `total`, `stop` (текст или `null`), `items[]` |
| `items[]` | `id`, `status` (`Completed`/`Failed`/`NotRun`), `code`, `subcode` (удалённые элементы с ошибкой, у которых есть точная причина), `applied`, `verdict` (элементы verify), `published` (элементы с выходом), `digest` `{algorithm, hex}` (элементы hash) |

Необязательные поля при отсутствии опускаются, а не равны `null`. `timestamp`, `jws`, `jwt` и `plugin call` печатают собственные, более короткие отчёты (`operation_id`, `code`, `applied` плюс счётчики байт, `profile`, `verdict`, `policy` или `facts` — что уместно); `plugin operations` печатает отчёт, описанный в разделе [«Плагины»](#плагины-oncl-plugin). Таблица выведена из структур отчётов в `crates/oncl-cli/src/reports.rs`, `local.rs`, `public.rs` и `batch.rs`.

## Удалённый режим (`--endpoint`)

`oncl --endpoint https://signing.internal:13579 --token-file client.token --ca-file ca.pem sign --profile cms --key-name corporate-signing --authorize --input doc.bin --output doc.p7s` выполняет операцию на сервере, описанном в [server.md](server.md) / [http-api.md](http-api.md). Клиент — `oncl_api::client::ApiClient` (feature `client` крейта `oncl-api`; только `ureq` + `rustls`, без Tokio/axum/hyper).

* **Пути.** Каждый локальный путь читает и пишет клиент. Документы передаются потоком из файлов/stdin как части запроса (с известным `Content-Length`, когда он есть, и chunked для stdin); результаты готовятся (staged) в приватном каталоге места назначения и публикуются без перезаписи (no-clobber) точно так же, как при локальных запусках. Сервер никогда не открывает путь клиента: в запросе нет поля пути, а путь в любом строковом поле отклоняется (`remote::server_cannot_open_client_path`).
* **Фиксация.** Результат публикуется только после того, как получены **завершающая запись `final`, закрывающий разделитель multipart и конец HTTP-сущности**. Ответ, оборванный где угодно до этого (до/внутри артефакта, до/внутри записи final, «вежливое» завершение без final, отсутствие закрывающего разделителя, отсутствие завершающего чанка), ничего не публикует, не оставляет временных файлов, печатает `oncl: ResponseLost; applied=Unknown` (`NotApplied` для операций без ключа) и завершается кодом 1. **Автоматического повтора, ключа идемпотентности, отката и обещания «ровно один раз» нет**: сервер вполне мог применить ключ (об этом говорит его журнал аудита). Прежние файлы по другим путям (включая прежние выходы пакета) не затрагиваются.
* **`applied`.** Сервер начинает закрытую операцию только после того, как принял всё тело запроса. Сбой, пока тело ещё отправлялось, — `NotApplied`; потерянный ответ после последнего байта тела — `Unknown`, если запрос мог использовать закрытый ключ; типизированный отказ или завершающая запись сообщают собственное значение сервера.
* **Токен.** `--token-file PATH` (каталог с доступом только владельца, те же правила и предел 4096 байт, что у `--secret-file`) или `--token-stdin` (тогда stdin — не документ). Никогда не argv, никогда не переменная окружения; он не попадает ни в одну диагностику, отчёт или ошибку (тесты ищут его в stdout, stderr и каждом файле клиента), а сообщения об ошибках никогда не содержат тела ответа, только стабильный код, статус HTTP и типизированный код сервера.
* **Транспорт.** `https://` использует встроенные корни webpki; `--ca-file` (пакет PEM или DER, повторяется) *заменяет* их для частного сервера (доверяется ровно этому CA или собственному сертификату сервера). Флага для отключения проверки нет. `http://` принимается только для `localhost`/`127.0.0.0/8`/`::1`; любой другой хост с простым http требует `--allow-plain-http` (токен и документы идут без шифрования: защищённая внутренняя сеть за доверенным прокси). Перенаправления никогда не выполняются, а окружающие переменные прокси игнорируются.
* **Ключи.** `--key-name NAME` ссылается на ключ оператора на сервере (секрет с клиента не нужен). Ключевой материал покидает процесс только с `--key PATH --secret-file … --inline-key` (и `inspect --profile container … --inline-key`): контейнер и пароль идут как части `secret`, только в памяти и на стороне клиента тоже, а серверу нужен `inline_pkcs12` глобально и для токена. Считыватели токенов (`--token-reader`) и `--key-config` — локальные устройства/файлы и отклоняются.
* **Полномочия остаются у оператора.** Корни доверия, политика проверки, сеть PKI, часы, TSA, issuer/audience JWT и установка плагинов — конфигурация сервера. `--root`, `--intermediate`, `--pki-endpoint`, `--pki-pin`, `--tsa-url`, `--tsa-policy`, `--offline`, `--as-of`, `--configuration-bytes`, `timestamp acquire --tsa/--algorithm`, `timestamp verify --policy-oid`, `jwt verify --issuer/--audience/--leeway-seconds`, `inspect --alias` и каждая команда `plugin` отклоняются с `RemoteUnsupported` до любого ввода-вывода, а не игнорируются. `sign` по-прежнему требует `--authorize`. Любой параметр, которого нет в wire, отклоняется до любого ввода-вывода с `RemoteUnsupported`: параметры WS-Security сверх `--soap-version`/`--wsse-body-id` (`--wsse-role`, `--wsse-required-header`, `--wsse-timestamp-*`, `--wsse-token-reference`, `--wsse-token-id`) и параметры legacy XML сверх элемента, родителя, методов подписи и дайджеста (пространства имён, размещение, c14n, преобразования, время подписания, переводы строк, объявление, выход и параметры цепочки); так же отклоняются `--token-reader` и `--key-config`.
* **Семейства.** `hash`, `verify`, `extract`, `sign` (cms, cades-*, xml, wsse с `--soap-version`/`--wsse-body-id`, xades-b/t, pdf, pades-* и `--legacy` xml/xades-b/xades-t с методами element/parent/signature/digest), `extend` (cms/pdf t|lt|lta, xml lt|lta), `inspect`, `timestamp`, `jws`, `jwt` и `batch run`. Подпись `raw`/`digest-*` и подпись XAdES LT/LTA — не профили контракта (используйте `xades-t`, затем `extend` без ключа). Свидетельства отправляются из `--evidence-certificate/-ocsp/-crl` как открытые части-документы.
* **Причины отказа.** Типизированный отказ службы, несущий `subcode`, печатается как `oncl: <code>; subcode=<id>; applied=<state>` (клиент сверяет id с опубликованным шаблоном; неверный отбрасывается и никогда не печатается). Команды плагинов удалённо недоступны.
* **Отчёты и коды выхода** — как у локальных (0 завершено/`Valid`, 2 `Invalid`, 3 `Indeterminate`, 4 неполный пакет, 1 сбой, 130 отмена). Вердикт, политика и каждая проверка по подписанту у подписи, проверенной удалённо, совпадают с локальным запуском. Отличия: в wire нет подробностей структуры PDF/XML и нет верхнеуровневого уровня AdES (он опущен, а не выдуман); `time_basis` — вариант (`time_basis_unix` содержит момент); `bytes_in` — байты документа, отправленные этим клиентом, а `bytes_out` — полученный артефакт; факты `timestamp` — объект. `jwt decode` пишет текст полезной нагрузки, декодированный сервером (сервер заменяет недопустимый UTF-8).
* **Пакет.** Манифест читается здесь; источник, который нельзя открыть, приводит к сбою только своего элемента. Выходы готовятся в одном хранилище (общий каталог назначения, иначе `--temporary-directory`/`.`, который должен находиться на томе мест назначения) и ставятся на место жёсткими ссылками после завершающей записи, по одной строке на элемент (`published` на каждый выход). Сервер выполняет закрытый `/v1/batch` (нужно право `batch` у токена).
* **Ограничения этого клиента.** Сервер, который отвечает, пока клиент ещё загружает (например, отказ после метаданных при большом теле), держит соединение открытым и читает и отбрасывает то, что клиент ещё присылает, не дольше одной секунды и около 8 МиБ, поэтому клиент, закончивший в этих пределах, читает типизированный ответ. Клиент, продолжающий отправку дольше, получает сброс соединения, и типизированный ответ может потеряться при сбросе: тогда исход — сбой транспорта с `applied=NotApplied` (тело было неполным). Отмена и дедлайн (`--timeout-seconds`) опрашиваются каждые 50 мс во время ожидания, поэтому Ctrl-C завершает вызов к серверу, который не отвечает вовсе, кодом 130 в течение нескольких секунд (`applied=Unknown`, если ключ мог использоваться и тело было отправлено полностью, иначе `NotApplied`); брошенный обмен заканчивается вместе с процессом, и ничего не повторяется. Документы по 1 ГиБ и RSS, подпись PDF/XML и продление PAdES до LT/LTA через этот клиент проверены HTTP-поверхностью приёмочного прогона `cargo xtask platform-proof`, где клиентом служит `oncl --endpoint` ([`docs/dev/platform-acceptance.md`](../dev/platform-acceptance.md)). Не проверялось: Linux/macOS, Win7, TLS с закреплённым ключом (только файл CA/листа), `jws add`/`cms add`/`wsse` по удалённому пути (поля wire сопоставлены, но удалённого теста CLI нет), прямая удалённая подпись PAdES LT/LTA (покрыта на уровне HTTP тестами `oncl-api`).
* Шифрование/расшифрование: ни команды, ни маршрута wire не существует (G01/G02 внешние); этот клиент их не добавляет.
* **Целостность ответа.** Каждый артефакт, названный завершающей записью, должен быть получен один раз с точной длиной, которую называет запись: извлечение (`bytes_written`) и токены штампов времени (`bytes_out` — длина токена). Правильно оформленная часть неверного размера ничего не публикует (`ProtocolViolation: artifact length differs from the final record`, код выхода 1, `NotApplied` для операций без ключа, `Unknown`, если ключ мог применяться). То же верно для создания JWS/JWT (`bytes_out`, проверяется сервером, когда он завершает запись артефакта с `bytes_out` из отчёта). Подпись и продление CMS/CAdES/XML/PDF не сравниваются: сервер берёт длину артефакта из подготовленного выхода и не навязывает `bytes_out` записи — счётчик SDK (измерено: 8250 для CMS в 1561 байт), поэтому там проверяются только тождество и число, а отчёты используют точную полученную длину.
* **Предупреждение `--allow-plain-http`.** Каждый запуск, использующий его с хостом `http://` не из loopback, печатает в stderr `oncl: warning: --allow-plain-http sends the API token and every document over an unencrypted, unauthenticated connection …` (никогда не токен). Без флага такой endpoint отклоняется до любого соединения (`PlainHttpRefused`).
* **Места назначения пакета.** Когда выходы лежат не в одном каталоге, настоящая жёсткая ссылка создаётся и удаляется в каждом каталоге назначения *до любого запроса* (`DestinationNotLinkable`, `NotApplied`), поэтому ключ никогда не используется для результата, который нельзя поставить на место ссылкой. Проверено на непригодном каталоге и на двух настоящих каталогах; проба проверяет саму возможность, поэтому место назначения на другом томе, не умеющем жёстких ссылок, отклоняется так же.
* **Перенаправления и прокси.** Ответ 3xx никогда не выполняется (токен bearer никогда не пересылается: `UnexpectedStatus (HTTP 307)`), а `HTTP_PROXY`/`ALL_PROXY` игнорируются (тесты фиксируют, что ни цель перенаправления, ни окружающий прокси никогда не получают соединения). Сброс соединения, пока тело ещё отправляется (например, у клиента, который продолжает отправку после одной секунды и около 8 МиБ, которые сервер продолжает читать после раннего ответа), — `NotApplied`: служба принимает всё тело multipart (и повторно проверяет полномочия), прежде чем рабочий поток сможет использовать ключ (`crates/oncl-server/src/service/operations.rs` и `operations/intake.rs`).
