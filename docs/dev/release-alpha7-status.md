# Выпуск 0.1.0-alpha.7: итог и что осталось открытым

Версия `0.1.0-alpha.7` выпущена как pre-release (канал `beta`) 2026-11-13. Документ заменил список блокеров, который велся до выпуска. Он фиксирует, что сделано, чем это подтверждено и что остаётся открытым. Порядок выпуска — [`release-runbook-alpha7.md`](release-runbook-alpha7.md), устройство выпуска — [`release.md`](release.md).

Обозначения «Статус»: **ЗАКРЫТО** — сделано и подтверждено; **ПРИНЯТО** — владелец принял как известное ограничение; **ОТКРЫТО** — не сделано, выпуск состоялся без этого; **ВНЕ alpha.7** — решено не делать в этом выпуске.

## Доказательства

- **1 ГиБ** ([`platform-acceptance.md`](platform-acceptance.md)): полный прогон `platform-proof` — 70/70 на дереве `9a1f0181`; 12 HTTP-кейсов перепрогнаны на `e99a90a2` (12/12). Кейсы SDK (23), CLI (22) и остальные HTTP-кейсы на `e99a90a2` не перепрогонялись.
- **Матрица взаимодействия** ([`platform-interop.md`](platform-interop.md)): 233 строки; на `24be0093` 229 PASS и 4 FAIL (строки `large-*` с размером выше нового контракта 1 ГиБ, затем исправлены); эти четыре строки на `b3b11162` — PASS. Целиком матрица на выпущенном коммите не перезапускалась. Девять строк CMS LT/LTA остаются ограничением оракула NCANode, а не продукта.
- **Оракул ГОСТ** — только локальный (Java-проверяющий с установленным у владельца `kalkancrypt`; JAR не входит в репозиторий и CI): 12 прежних BLOCKED-строк локально PASS; без JAR в CI они BLOCKED.
- **Windows-матрица на установщиках из черновика**: 5 ВМ (Win7 x64/x86, Win10 x64/x86, Win11 x64), установка, запуск, удаление и повторная установка, обычные установщики и `*-winget-setup.exe`. Программа запускалась как `openncalayer.exe run --no-tray --allow-no-wss` (без слушателя `wss`), и в этом режиме у неё не было слушающих TCP-портов и UDP-сокетов (проверялись `netstat` и `Get-NetTCPConnection` по PID программы); режим с `wss` на порту 13579 и TLS-сертификатом не проверялся. По отчёту прогона: 119 PASS, 0 FAIL, 10 NOT RUN (отчёт хранится локально, в репозиторий не входит). Владелец поставил статус `vm-smoke`.

## Не выполнено на ВМ

Из матрицы выпуска остались без прогона, каждый пункт записан как NOT RUN, а не PASS:

- меню значка в трее и «Проверить обновления»;
- принятие запроса UAC на защищённом рабочем столе;
- масштаб 175/200 %;
- режим с `wss` (слушатель `127.0.0.1:13579` и TLS-сертификат): матрица шла в режиме `--allow-no-wss`;
- удержание подписи (выход 4) на выпущенном исполняемом файле (раньше — на тестовом демоне, 24/24 в семи ячейках);
- расширения браузера на Win7;
- `winget install --manifest` (только для stable-релиза);
- отказ обычных установщиков от запуска с полным токеном: **обычные `*-setup.exe` его не отказывают** (установка в профиль администратора, код 0); отказывают только `*-winget-setup.exe` (код 8). Требования к обычным установщикам нет ни в runbook, ни в `winget-installer.md`.

## Известные недочёты

- Три теста `oncl-server` падали нестабильно в CI на ветках PR (`feat/upstream-ports`, `updates/plugins-20261113`, `docs/rework`); на `main` (`99dcdf54`) полный CI зелёный: `cancelled_running_worker_keeps_permit`, `successful_worker_wait_preserves_result_context_without_recording_failure` и `an_aborted_stream_is_logged_with_its_typed_cause`. Нестабильность есть и в выпущенной `0.1.0-alpha.7`. Исправлено в PR #13 (слит 2026-11-14, полный CI зелёный, включая Windows): первые два — продуктовая гонка (вид операции на ресурсах освобождался после слота исполнителя), третий — гонка самого теста (бюджет брался у границы, которая под нагрузкой смещается). Числа даны по двум независимым прогонам исполнителей; сам я их не повторял, и они не совпадают. Linux под нагрузкой: автор правки — 14 из 300 и 5 из 300 до, 0 из 600 после (в сообщении коммита `a5a7182d`); проверяющий — 27 из 600 и 13 из 600 до, 0 из 1000 после. Windows, тест `intake`: автор правки — 30 из 240 до, 0 из 600 после (там же); проверяющий на Windows не воспроизвёл падение вообще (0 из 240 и до, и после, при другой нагрузке), так что Windows-часть эффекта одним независимым прогоном не подтверждена. Стрим-тест: 20 из 150 до, 0 из 300 после (проверяющий, Linux). Не доказано также: юнит-тест правки не фиксирует порядок «до `send`»; редкий обрыв до первого элемента на выбранном бюджете всё ещё может уронить стрим-тест.
- Наблюдатель за оригиналом (`xtask/src/upstream/jar.rs`) берёт первый сертификат блока подписи PKCS#7 (корневой), а не подписанта, поэтому в issues #4 и #6 (закрыты) строка «подпись совпадает с `csernum`/`chash`: нет» ложная; `jarsigner -verify` проходит у обоих JAR. Не исправлено.
- Порты `simourg` и `ezsigner` отмечены `computed`: оригиналы 2.4 и 1.2.2 сверены только по байткоду, лаборатория на них не перепроверялась. Issue #5 (OnaiDocs): порта нет, только анализ.
- Реальная загрузка CRL использует таймаут 5 с при проверке пути, хотя `crl::TIMEOUT` равен 30 с; на реальных крупных CRL НУЦ не исследовалось. XAdES-подпись не поддерживает CRL больше 256 КиБ; лимиты доказательств (2 МиБ у сервера, 1 МиБ у UI) отказывают на CRL размера НУЦ.
