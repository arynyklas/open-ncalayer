# Выпуск версии и подпись индекса обновлений

Инструкция мейнтейнера: от первой пары ключей до опубликованного обновления. Формат индекса, правила проверки и поведение клиента описаны в [`../design/update-index.md`](../design/update-index.md).

Коротко: тег `v<версия>` собирает релиз и открывает PR с неподписанными индексами каналов версии (для релиза — `stable` и `beta`); мейнтейнер подписывает каждый у себя и пушит подписи в этот PR; после слияния индексы уезжают на GitHub Pages, и клиенты видят новую версию. Секретный ключ в CI не попадает никогда.

## 1. Ключи подписи индекса (один раз)

```sh
cargo xtask sign keygen --out <каталог вне репозитория>
```

- Пароль вводится дважды, без эха. Пустой пароль не принимается.
- В каталоге появляются `oncl-index.key` (секретный ключ, зашифрован паролем; в macOS и Linux права `0600`) и `oncl-index.pub`.
- Каталог внутри рабочего дерева git команда отвергает, если он не указан в `.gitignore`; отвергается и файл, который git уже отслеживает. Поэтому `--out crates/oncl-update/keys` не сработает: это каталог открытых ключей, он коммитится.
- Существующая часть пути разрешается заранее (символические ссылки, junction, `..`), а рабочее дерево ищется по ближайшему каталогу с `.git`. Если git не может открыть репозиторий, команда отказывается писать ключ.
- Секретный ключ хранится офлайн у мейнтейнера (зашифрованный носитель), не коммитится и не кладётся в секреты GitHub (D26).

Открытый ключ кладётся в репозиторий и коммитится:

```sh
cp <каталог>/oncl-index.pub crates/oncl-update/keys/current.pub
```

Сборка встраивает `crates/oncl-update/keys/current.pub` и `crates/oncl-update/keys/next.pub`, если файлы есть (`crates/oncl-update/build.rs`). Сборка без них ключей не имеет: обновления выключены, в журнале и в окне настроек — «Ключи подписи обновлений не встроены в эту сборку». Значит, обновлять себя сможет только версия, собранная уже с ключом; копии, установленные из сборок без ключей, придётся переустановить.

## 2. Настройки репозитория (один раз)

Их меняет только мейнтейнер, workflow сделать этого не может:

- Settings → Pages → Source: **GitHub Actions** (иначе `pages.yml` не опубликует индекс);
- Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests** (иначе job `index` не откроет PR с индексом).
- Settings → Rules (или Branches) → правило для `main`: обязательная проверка **Index check / check** (`index-check.yml`). Она запускается на каждый PR и пуш в `main` и всегда отчитывается: если не менялись ни `updates/`, ни `crates/oncl-update/keys/`, шаг cargo пропускается, а проверка проходит, так что обычные PR она не держит. Обязательная проверка должна стоять на коммите до того, как `main` сдвинется, а запуск на пуш в `main` отчитывается уже после пуша: с этим правилом изменения попадают в `main` только через PR, а прямой пуш проходит, лишь если мейнтейнер в списке обхода (bypass list) правила; у классической защиты ветки администраторы по умолчанию освобождены. Workflow не может включить её сам; без неё неподписанный PR индекса можно слить. Pages такой индекс не опубликует, но и все следующие публикации встанут, пока его не подпишут.

Необязательно — секреты подписи кода. Без них шаги подписи пропускаются с уведомлением в журнале сборки, релиз выходит неподписанным:

- Authenticode через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`;
- Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD` подписывают и нотаризуют `.app` (пакет обновления, `.zip`, содержимое `.pkg`); сам `.pkg` подписывается и нотаризуется, только если есть ещё `APPLE_INSTALL_IDENTITY` — идентичность «Developer ID Installer» из того же `APPLE_CERTIFICATE_P12`.

Необязательно — публикация пакета AUR `openncalayer-bin` (`.github/workflows/aur.yml`): переменная `AUR_PUBLISH` = `true` и секрет `AUR_SSH_PRIVATE_KEY` — SSH-ключ аккаунта AUR, который сопровождает пакет. Без `AUR_PUBLISH` workflow только собирает и проверяет `PKGBUILD` и `.SRCINFO` (артефакт `aur-v<версия>`); с `AUR_PUBLISH` и без ключа он падает.

## 3. Выпуск версии

1. Поднять версию в `[workspace.package]` файла `Cargo.toml`, обновить `Cargo.lock` (`cargo check --workspace`), прогнать проверки из раздела «Перед отправкой изменений» README и закоммитить.
2. Поставить тег и запушить его:

   ```sh
   git tag v<версия>
   git push origin v<версия>
   ```

   Первым делом job `version` сверяет тег с версией в `Cargo.toml` и останавливает сборку при расхождении. Версия с суффиксом (`0.1.0-alpha.1`) выходит как pre-release и идёт только в канал `beta`, версия без суффикса — как обычный релиз и в оба канала, `stable` и `beta`.
3. `release.yml` собирает по флейворам (`win-x64`, `win-x86`, `win7-x64`, `win7-x86`, `linux-x64`, `osx`) архивы, установщики и пакеты Velopack с дельтами (`cargo xtask package windows|macos|linux`, Linux — в контейнере с glibc 2.28 через `cargo xtask package linux-build`), расширение, SBOM и `SHA256SUMS`, выпускает аттестацию происхождения на каждый файл и создаёт релиз. Установщики: `openncalayer-<версия>-<флейвор>-setup.exe` (четыре флейвора Windows), `openncalayer-<версия>-osx.pkg` и `openncalayer-<версия>-osx.zip`, `openncalayer-<версия>-linux-x64.AppImage`. Флейворы `win7-*` собираются `cargo xtask win7`, а содержимое их пакетов, вместе с `Squirrel.exe` и заглушкой Velopack, и их `Setup.exe` проходят гейт импортов Windows 7. После успешного релиза без суффикса `aur.yml` готовит пакет AUR.
4. Job `index` скачивает ассеты релиза, выполняет `cargo xtask index add --channel <канал> --tag v<версия>` для каждого канала версии (для pre-release — `beta`, для релиза — `stable` и `beta`; у каждого индекса свой следующий `seq`, прежние записи сохраняются) и открывает PR «chore(updates): add …» с веткой `updates/v<версия>`. Флейвор `osx` в индексы пока не попадает: универсальная сборка ещё не запускалась на Mac с Intel (лаборатория, P9). Индексы в PR **не подписаны**, и `index check` не пропустит PR, пока не подписан каждый из них.

## 4. Подпись индекса в PR

На ветке PR, у себя на машине:

```sh
git fetch origin
git switch updates/v<версия>
```

1. При необходимости уменьшить `rollout` новой версии в индексах PR, `updates/v1/<канал>.json` (0–100). Руками в индексе меняются только значения полей; переформатировать файл нельзя — он публикуется байт в байт, и `.gitattributes` запрещает git менять в нём концы строк.
2. Подписать каждый индекс PR — для релиза оба:

   ```sh
   cargo xtask sign updates/v1/stable.json --key <каталог>/oncl-index.key
   cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
   ```

   Пароль вводится без эха. Перед записью `.minisig` команда проверяет формат и срок индекса, правило URL и саму подпись — открытым ключом той же пары, а не ключами из `crates/oncl-update/keys/`: подпись не тем ключом ловит только `index check` (шаг 3). Неверный, истёкший или ссылающийся не на релизы проекта индекс не подписывается.
3. Проверить так же, как это сделает CI (нужен свежий `origin/main`; без сети — с `--offline`):

   ```sh
   cargo xtask index check updates/v1 --base origin/main
   ```

   Проверяются подпись ключом `crates/oncl-update/keys/current.pub` (только им, не `next.pub`), срок, правило URL, рост `seq` относительно базовой ветки, ключ обновлений в теге каждой версии, новой относительно базы или с заменёнными пакетами (`crates/oncl-update/keys/current.pub` тега должен быть `current.pub` или `next.pub` дерева), и ответ `HEAD` 200 на каждый URL пакета и расширения.
4. Закоммитить индексы вместе с их `.minisig` и запушить. PR, открытый workflow, сам проверок не запускает, поэтому `index-check.yml` срабатывает именно на этот пуш.
5. Слить PR. После слияния `pages.yml` ещё раз проверяет индексы против коммита до пуша (`--base <github.event.before>`; на первом пуше и при ручном запуске — `--no-base`: подписи, срок и URL проверяются, а ключ в тегах — нет, его проверили при добавлении версий) и публикует каталог `updates/` на GitHub Pages: клиенты читают `https://arynyklas.github.io/open-ncalayer/updates/v1/<канал>.json`.

Если до слияния этого PR вышла ещё одна версия, у второго PR тот же следующий `seq` на тех же файлах, и после слияния первого он конфликтует. Не разрешать конфликт вручную и не брать файлы своей ветки: `index check` сравнивает `seq` и пропавшие файлы, а не пропавшие версии, и такая правка молча потеряет версию первого PR. Нужно перезапустить job `index` релиза второй версии (Actions → Release → Re-run job `index`), когда первый PR уже в `main`: он соберёт индексы заново от свежего `main`, с обеими версиями и следующим `seq`. Затем подписать, как выше.

Клиенты увидят новую версию при очередной проверке: первая — через 2–10 минут после запуска, дальше раз в 6–24 часа.

Расширить раскатку позже (вплоть до 100): поднять `rollout` версии в `updates/v1/<канал>.json`, затем `cargo xtask index refresh --channel <канал>` (изменённому индексу нужен новый `seq`, иначе проверка откажет), подписать, открыть PR в `main` и слить — как в разделах 5 и 6. Для релиза — в обоих каналах.

## 5. Продление индекса

Клиент отвергает индекс, которому больше 30 дней с `generated`, даже если в `expires` стоит более поздняя дата. Срок у каждого канала свой: каждый индекс, который не менялся 30 дней, надо продлить и подписать заново. Предварительные версии меняют только `beta.json`, поэтому опубликованный `stable.json` нужно продлевать и тогда, когда выходят одни пререлизы:

```sh
cargo xtask index refresh --channel <канал>
cargo xtask sign updates/v1/<канал>.json --key <каталог>/oncl-index.key
```

`refresh` меняет только `seq` (+1), `generated` и `expires` и удаляет устаревшую подпись; список версий остаётся прежним. Дальше — PR в `main`, проверка и слияние, как в разделе 4.

## 6. Отзыв версии

Сломанную версию отзывают правкой индекса: в её записи `"revoked": true`. Клиент читает только индекс своего канала, а релиз без суффикса записан и в `stable.json`, и в `beta.json`, поэтому отзывать его нужно **в каждом индексе, где он есть, одним PR**. Если отозвать только в одном, установки другого канала останутся на этой версии и будут её получать. Отозванная во всех своих индексах версия больше не предлагается, а установки, которые уже на ней, получают самую новую неотозванную версию своего канала, даже если она старше.

Порядок для релиза (для пререлиза — только `beta`):

```sh
# в updates/v1/stable.json и updates/v1/beta.json: "revoked": true у версии
cargo xtask index refresh --channel stable
cargo xtask sign updates/v1/stable.json --key <каталог>/oncl-index.key
cargo xtask index refresh --channel beta
cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
cargo xtask index check updates/v1 --base origin/main
```

`refresh` нужен ради нового `seq`, иначе проверка откажет. Затем открыть PR и слить. Если исправленная версия уже выпущена, достаточно отозвать сломанную: клиенты перейдут на исправленную как на обновление.

## 7. Ротация ключа

Клиент доверяет только ключам, зашитым в его сборку: `current.pub` и, если есть, `next.pub`. `index check` (в PR и перед публикацией на Pages) проверяет подпись каждого индекса в `updates/v1/` ключом `current.pub` того же коммита, а тег каждой новой относительно базы версии — на ключ `current.pub` или `next.pub` этого коммита. Версии, уже опубликованные до ротации, при этом не перепроверяются: их теги хранят старый ключ. Поэтому ключ меняется в три шага, и между ними есть период, когда сборки доверяют обоим ключам:

| Шаг | `current.pub` | `next.pub` | Чем подписаны индексы | Какие установки принимают индексы |
|---|---|---|---|---|
| до ротации | старый | — | старым ключом | все |
| 1–2, переход | старый | новый | старым ключом | все; версии с двумя ключами примут и новый |
| 3, после переключения | новый | — | новым ключом | только версии с двумя ключами и более новые |

1. **Подготовка.** `cargo xtask sign keygen --out <новый каталог>`; новый открытый ключ — в `crates/oncl-update/keys/next.pub`, коммит и выпуск версии **без суффикса** (релиз, не пререлиз): пререлиз идёт только в `beta.json`, и установки на `stable` не получили бы сборку с двумя ключами. Её лучше раскатать на 100 %: установка, которая её не получит, после шага 3 обновляться перестанет. Все индексы по-прежнему подписываются **старым** ключом: его знают и прежние сборки, и новая. `index check` принимает только подпись ключом `current.pub`, так что подпись новым ключом на этом шаге не пройдёт. После переключения отзыв версии может откатить установку на сборку старше этой, а такая сборка новых индексов уже не примет.
2. **Ожидание.** Дождаться, пока установки обновятся на версию с двумя ключами. Индексы всё это время подписываются старым ключом, их продления (раздел 5) тоже. Телеметрии у проекта нет, поэтому срок выбирает мейнтейнер: клиенты проверяют индекс раз в 6–24 часа, но выключенные компьютеры и установки с выключенным автообновлением отстают.
3. **Переключение** — одним PR в `main`: замена ключей и переподпись **каждого** индекса. После замены `current.pub` `index check` отвергает индекс со старой подписью, поэтому ни этот PR, ни публикация на Pages не пройдут, пока со старой подписью остаётся хоть один канал. Для каждого файла `updates/v1/<канал>.json`, который есть (сейчас `stable` и `beta`):

   ```sh
   cp <новый каталог>/oncl-index.pub crates/oncl-update/keys/current.pub
   git rm crates/oncl-update/keys/next.pub
   cargo xtask index refresh --channel stable
   cargo xtask sign updates/v1/stable.json --key <новый каталог>/oncl-index.key
   cargo xtask index refresh --channel beta
   cargo xtask sign updates/v1/beta.json --key <новый каталог>/oncl-index.key
   cargo xtask index check updates/v1 --base origin/main
   ```

   `refresh` даёт каждому индексу следующий `seq`: без него изменённый индекс проверка не пропустит. Последняя команда проверяет все каналы разом — подпись новым ключом из `current.pub`, срок, правило URL, рост `seq` и `HEAD` 200 по каждому URL — и должна пройти до слияния: после слияния `pages.yml` проверяет те же индексы теми же ключами и только потом публикует. Закоммитить ключи, индексы и их `.minisig` одним коммитом, открыть PR и после зелёного `index-check.yml` слить. Открытые в это время PR с индексами (например, `updates/v<версия>` нового релиза) после этого надо обновить от `main` и подписать новым ключом.

Старый ключ в `next.pub` не остаётся: версии, собранные после переключения, ему не доверяют, и утёкший старый ключ для них бесполезен. Установкам, которые знают только старый ключ, это не помогает: если старый секретный ключ скомпрометирован, их защищает только переустановка.

Порядок важен: индекс, подписанный ключом, которого у клиента нет, отвергается как подделка, и обновления встают до переустановки.

## 7а. Выпуск плагинов

Плагины выходят отдельно от ядра, пачками: релиз с тегом `plugins-ГГГГММДД` (второй за день — `plugins-ГГГГММДД.1` и так далее), pre-release без флага Latest, чтобы «последним релизом» оставалось ядро. Выпускает их workflow `.github/workflows/plugins.yml`.

1. Поднять версию порта в его `Cargo.toml` и `plugin.toml` (они должны совпадать), слить в `main`. Какие порты выйдут, видно заранее:

   ```sh
   cargo xtask plugin pending --channel beta
   ```

   Команда печатает каталоги `plugins/<порт>`, чьей пары `(id, version)` ещё нет в индексе `beta`; пустой вывод — выпускать нечего.
2. Поставить тег на `main` и отправить его: `git tag plugins-ГГГГММДД && git push origin plugins-ГГГГММДД`. Workflow проверяет имя тега, собирает каждый порт из `pending` дважды (`cargo xtask plugin pack`) и сравнивает пакеты байт в байт — пакеты детерминированы, пути машины сборки в модуль не попадают; проверяет, что `plugins/THIRD-PARTY.txt` свежий (`cargo xtask licenses --plugins --check`), и кладёт его рядом с пакетами: в нём лицензии крейтов портов и шрифтов, которые порты встраивают в модуль (`plugins/<порт>/fonts/`: файл шрифта, источник из `fonts/README.md` и текст `OFL.txt`); затем `SHA256SUMS`, аттестация происхождения всех файлов и релиз. Если выпускать нечего, workflow заканчивается с notice и без релиза. Новый шрифт в порте кладётся с `OFL.txt` и `README.md` со строкой `Источник: <URL>`, иначе `cargo xtask licenses --plugins` откажется.
3. Затем workflow открывает PR `updates/<тег>` с пакетами в индексе `beta` (`cargo xtask index add-plugin --channel beta`), неподписанным. На ветке PR:

   ```sh
   cargo xtask sign updates/v1/beta.json --key <каталог>/oncl-index.key
   cargo xtask index check updates/v1 --base origin/main
   ```

   закоммитить индекс с `.minisig`, отправить, дождаться зелёного `index-check.yml` и слить. Клиенты подхватят плагин при следующей проверке индекса и перезагрузят его без перезапуска ядра. Ключ подписи в CI не попадает.
4. В `stable` workflow не пишет. Готовую версию плагина (без суффикса), проверенную в `beta`, мейнтейнер добавляет вручную тем же порядком: `cargo xtask index add-plugin --channel stable --tag <тег релиза> --package <пакет из релиза>`, подпись `stable.json`, проверка, PR. Предварительную версию (`1.0.0-beta.1`) команда в `stable` не добавит.

Собрать пакет локально: `cargo xtask plugin pack <каталог крейта плагина>` — пакет `target/plugins/<id>-<версия>.onclp`.

Отзыв версии плагина — как у ядра (раздел 6): `"revoked": true` у записи в каждом индексе, где она есть, затем `refresh`, подпись, проверка и PR. Установки на отозванной версии переходят на самую новую неотозванную, а если её нет — плагин выключается.

## 8. После выпуска

- Проверить происхождение файлов релиза: `gh attestation verify <файл> --repo arynyklas/open-ncalayer`.
- Убедиться, что индекс опубликован: `curl -fsS https://arynyklas.github.io/open-ncalayer/updates/v1/<канал>.json.minisig`.
- Сам себя обновляет только экземпляр, установленный установщиком (`Setup.exe`, `.pkg`, `.zip`, AppImage): из архива программа работает, но обновления у неё выключены; копию из AUR обновляет pacman.
- Пакет AUR вручную (например, исправление самого пакета): Actions → AUR → Run workflow с тегом и `pkgrel` 2, 3…
