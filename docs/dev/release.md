# Выпуск версии и подпись индекса обновлений

Инструкция мейнтейнера: от первой пары ключей до опубликованного обновления. Формат индекса, правила проверки и поведение клиента описаны в [`../design/update-index.md`](../design/update-index.md).

Коротко: тег `v<версия>` собирает релиз и открывает PR с неподписанным индексом; мейнтейнер подписывает индекс у себя и пушит подпись в этот PR; после слияния индекс уезжает на GitHub Pages, и клиенты видят новую версию. Секретный ключ в CI не попадает никогда.

## 1. Ключи подписи индекса (один раз)

```sh
cargo xtask sign keygen --out <каталог вне репозитория>
```

- Пароль вводится дважды, без эха. Пустой пароль не принимается.
- В каталоге появляются `oncl-index.key` (секретный ключ, зашифрован паролем; в macOS и Linux права `0600`) и `oncl-index.pub`.
- Каталог внутри рабочего дерева git команда отвергает, если он не указан в `.gitignore`; отвергается и файл, который git уже отслеживает. Поэтому `--out crates/oncl-update/keys` не сработает: это каталог открытых ключей, он коммитится.
- Существующая часть пути разрешается заранее (символические ссылки, junction, `..`), а рабочее дерево ищется по ближайшему каталогу с `.git`. Если git не может открыть репозиторий, команда отказывается писать ключ.
- Секретный ключ хранится офлайн у мейнтейнера (зашифрованный носитель), не коммитится и не кладётся в секреты GitHub (D26).

Открытый ключ кладётся в репозиторий и коммитится:

```sh
cp <каталог>/oncl-index.pub crates/oncl-update/keys/current.pub
```

Сборка встраивает `crates/oncl-update/keys/current.pub` и `crates/oncl-update/keys/next.pub`, если файлы есть (`crates/oncl-update/build.rs`). Сборка без них ключей не имеет: обновления выключены, в журнале и в окне настроек — «Ключи подписи обновлений не встроены в эту сборку». Значит, обновлять себя сможет только версия, собранная уже с ключом; копии, установленные из сборок без ключей, придётся переустановить.

## 2. Настройки репозитория (один раз)

Их меняет только мейнтейнер, workflow сделать этого не может:

- Settings → Pages → Source: **GitHub Actions** (иначе `pages.yml` не опубликует индекс);
- Settings → Actions → General → **Allow GitHub Actions to create and approve pull requests** (иначе job `index` не откроет PR с индексом).

Необязательно — секреты подписи кода. Без них шаги подписи пропускаются с уведомлением в журнале сборки, релиз выходит неподписанным:

- Authenticode через SignPath: секрет `SIGNPATH_API_TOKEN`, переменные `SIGNPATH_ORGANIZATION_ID`, `SIGNPATH_PROJECT_SLUG`, `SIGNPATH_SIGNING_POLICY_SLUG`;
- Apple: секреты `APPLE_CERTIFICATE_P12` (base64), `APPLE_CERTIFICATE_PASSWORD`, `APPLE_SIGN_IDENTITY`, `APPLE_ID`, `APPLE_TEAM_ID`, `APPLE_APP_PASSWORD`.

## 3. Выпуск версии

1. Поднять версию в `[workspace.package]` файла `Cargo.toml`, обновить `Cargo.lock` (`cargo check --workspace`), прогнать проверки из раздела «Перед отправкой изменений» README и закоммитить.
2. Поставить тег и запушить его:

   ```sh
   git tag v<версия>
   git push origin v<версия>
   ```

   Первым делом job `version` сверяет тег с версией в `Cargo.toml` и останавливает сборку при расхождении. Версия с суффиксом (`0.1.0-alpha.1`) выходит как pre-release и идёт в канал `beta`, версия без суффикса — как обычный релиз и в канал `stable`.
3. `release.yml` собирает по флейворам (`win-x64`, `win-x86`, `linux-x64`, `osx`) архивы и пакеты Velopack с дельтами, расширение, SBOM и `SHA256SUMS`, выпускает аттестацию происхождения на каждый файл и создаёт релиз. Флейворы `win7-x64` и `win7-x86` появятся вместе со сборками Windows 7: строки матрицы для них закомментированы в `release.yml`.
4. Job `index` скачивает ассеты релиза, выполняет `cargo xtask index add --channel <канал> --tag v<версия>` и открывает PR «chore(updates): add … index» с веткой `updates/v<версия>`. Индекс в нём **не подписан**.

## 4. Подпись индекса в PR

На ветке PR, у себя на машине:

```sh
git fetch origin
git switch updates/v<версия>
```

1. При необходимости уменьшить `rollout` новой версии в `updates/v1/<канал>.json` (0–100). Руками в индексе меняются только значения полей; переформатировать файл нельзя — он публикуется байт в байт, и `.gitattributes` запрещает git менять в нём концы строк.
2. Подписать:

   ```sh
   cargo xtask sign updates/v1/<канал>.json --key <каталог>/oncl-index.key
   ```

   Пароль вводится без эха. Перед записью `.minisig` команда проверяет индекс так же, как клиент: неверный, истёкший или ссылающийся не на релизы проекта индекс не подписывается.
3. Проверить так же, как это сделает CI (нужен свежий `origin/main`; без сети — с `--offline`):

   ```sh
   cargo xtask index check updates/v1 --base origin/main
   ```

   Проверяются подпись ключами из `crates/oncl-update/keys/`, срок, правило URL, рост `seq` относительно базовой ветки и ответ `HEAD` 200 на каждый URL пакета и расширения.
4. Закоммитить индекс вместе с `.minisig` и запушить. PR, открытый workflow, сам проверок не запускает, поэтому `index-check.yml` срабатывает именно на этот пуш.
5. Слить PR. После слияния `pages.yml` ещё раз проверяет индексы (`--base HEAD`) и публикует каталог `updates/` на GitHub Pages: клиенты читают `https://arynyklas.github.io/open-ncalayer/updates/v1/<канал>.json`.

Клиенты увидят новую версию при очередной проверке: первая — через 2–10 минут после запуска, дальше раз в 6–24 часа.

## 5. Продление индекса

Клиент отвергает индекс, которому больше 30 дней с `generated`, даже если в `expires` стоит более поздняя дата. Если за 30 дней не было релиза, индекс надо продлить и подписать заново:

```sh
cargo xtask index refresh --channel <канал>
cargo xtask sign updates/v1/<канал>.json --key <каталог>/oncl-index.key
```

`refresh` меняет только `seq` (+1), `generated` и `expires` и удаляет устаревшую подпись; список версий остаётся прежним. Дальше — PR в `main`, проверка и слияние, как в разделе 4.

## 6. Отзыв версии

Сломанную версию отзывают правкой индекса: в её записи `"revoked": true`. Такая версия больше никому не предлагается, а установки, которые уже на ней, получают самую новую неотозванную версию — даже если это откат назад (D24). Раскатка для них не учитывается: исправление доходит и при `rollout: 0`.

Порядок: править `revoked` в `updates/v1/<канал>.json`, затем `cargo xtask index refresh --channel <канал>` (нужен новый `seq`, иначе проверка откажет), подписать, открыть PR и слить. Если исправленная версия уже выпущена, достаточно отозвать сломанную: клиенты перейдут на исправленную как на обновление.

## 7. Ротация ключа

Клиент доверяет двум зашитым ключам, `current.pub` и `next.pub`, поэтому ключ меняется в два релиза:

1. `cargo xtask sign keygen --out <новый каталог>`; новый открытый ключ — в `crates/oncl-update/keys/next.pub`, коммит, выпуск версии. Индекс всё ещё подписывается **старым** ключом.
2. Дождаться, пока установки обновятся на версию с двумя ключами (индекс для этого продолжает выходить со старой подписью).
3. Записать новый открытый ключ в `current.pub`, а `next.pub` удалить до следующей ротации, выпустить версию и дальше подписывать индекс новым секретным ключом.

Порядок важен: индекс, подписанный ключом, которого у клиента нет, отвергается как подделка, и обновления встают до переустановки.

## 8. После выпуска

- Проверить происхождение файлов релиза: `gh attestation verify <файл> --repo arynyklas/open-ncalayer`.
- Убедиться, что индекс опубликован: `curl -fsS https://arynyklas.github.io/open-ncalayer/updates/v1/<канал>.json.minisig`.
- Установщики (`Setup.exe`, `.pkg`, AppImage) в этой фазе не собираются; релиз содержит архивы и пакеты Velopack. Сам себя обновляет только экземпляр, установленный через Velopack: из архива программа работает, но обновления у неё выключены.
