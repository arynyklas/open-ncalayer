# Наблюдатель за оригиналом

Наблюдатель следит за оригинальным NCALayer: версия и поля манифеста `ncalayer.der`, его подписант, дистрибутивы, состав и содержимое бандлов ядра и плагинов, сертификаты в keystore, API-поверхность байткода. Любое изменение не позже чем через 6 часов становится коммитом фактов в ветке `upstream` этого репозитория и issue с меткой `upstream`, `upstream-plugin` или `upstream-alert`. Решение — D28 в [`roadmap.md`](../design/roadmap.md).

## 1. Что публикуется и что нет

Публикуются только **факты**:

- поля манифеста НУЦ (`version`, `info`, `updurl`, `syspkgs`, `disturls`, бандлы со всеми полями, включая неизвестные новые) и его sha256, размер, время подписи, подписант (sha256, серийный номер, субъект, издатель, срок);
- для каждого дистрибутива и бандла: URL (без одноразового ключа страницы загрузок), имя файла, размер, sha256, опубликованный на странице SHA-1, формат, состав файлов (путь, размер, sha256, вид), сведения о JRE (версия, поставщик, архитектура, число файлов, хеш дерева), метаданные установщиков (ключи `[Setup]` из разрешённого списка, значения реестра, файлы `[Run]`, `Info.plist`, смещение payload в `.sh`, версия Go и хеш вложенной программы лёгкого установщика, версии `tzdb.dat`);
- для каждого JAR: заголовки `MANIFEST.MF` из разрешённого списка, подписанты блоков подписи, хеш содержимого без файлов подписи, публичные и защищённые классы, методы и поля с дескрипторами, методы с аннотацией `NCALayerMethod`, имена модулей, строковые константы — коды ошибок и URL, номера портов, счётчики классов сторонних библиотек, нативные файлы, алиасы и сертификаты keystore, сведения о вложенных манифестах.

Никогда не публикуются: файлы оригинала и их части (бинарники, извлечённые файлы, декомпилированный код, дословные фрагменты кода, тексты скриптов установщиков, тексты страниц сайтов НУЦ), закрытые ключи и зашифрованные блоки ключей keystore, пароли.

## 2. Как устроено

Код — `cargo xtask upstream` (`xtask/src/upstream/`). Запуск — workflow [`upstream.yml`](../../.github/workflows/upstream.yml): по расписанию каждые 6 часов и вручную, `concurrency: upstream` (запуски не пересекаются). Используется только `GITHUB_TOKEN`, секретов нет.

- **`collect`** (windows-2025, только `contents: read`): `cargo xtask upstream tools` закрепляет внешние распаковщики, `cargo xtask upstream run --dry-run` опрашивает источники, скачивает изменившееся в `$RUNNER_TEMP`, распаковывает, собирает факты и пишет каталог emit — только `*.json` (это проверяет и сам `run`, и отдельный шаг). Каталог уходит artifact'ом `upstream-facts` на 3 дня; оригиналы удаляются вместе с временным каталогом.
- **`publish`** (ubuntu-24.04, `contents: write`, `issues: write`, без кэшей): `cargo xtask upstream publish --from out` заново и строго проверяет artifact (только ожидаемые пути, только JSON до 64 MiB, схемы с отказом на неизвестные поля, история совпадает с `latest/facts.json`, `key8` сходится), рендерит issues сам из `diff.json`, коммитит в ветку `upstream`, пушит без force и шлёт `repository_dispatch` `upstream`. Если `collect` упал — issue `upstream-alert` `collect_failed`.

Опрос: манифест скачивается и проверяется всегда — CMS-подпись, ровно один подписант `CN=NCALayer`, сертификат подписанта подписан корнем НУЦ (`oncl_pki::roots::nca_production`). Дистрибутивы и фиксированные файлы — HEAD (размер, `ETag`, `Last-Modified`) и `hash` манифеста; ссылки страницы загрузок — по опубликованному рядом SHA-1, одноразовый ключ `download.php?key=` в идентичность источника не входит; бандлы — по `hash` манифеста, без запросов. Источник считается исчезнувшим только после 3 неудачных опросов подряд, успех сбрасывает счётчик. HTML-страница вместо файла или манифеста (ошибка или капча со статусом 200) — сбой опроса, а не новая версия и не `bad_signature`. Если не загрузилась сама страница загрузок, её ссылки остаются в фактах и тоже считают неудачи. Ключ `download.php?key=` обслуживает ровно один запрос (HEAD тоже; дальше — 302 на HTML-страницу `404.php`) и только с cookie сессии страницы и `Referer`, поэтому опрос ссылки страницы не запрашивает: `run` перед каждой её загрузкой заново читает страницу в новой сессии и берёт ссылку с тем же slug со свежим ключом. Статус и счётчик неудач ссылки меняют только эти загрузки (и отсутствие страницы или ссылки на ней); новая или вернувшаяся ссылка начинает со статуса `ok`, а неудачная (`failing`) или отвергнутая (`refused`) скачивается снова каждым запуском, пока загрузка не удастся. Неудачные загрузки ссылки, которая есть на странице, останавливают счётчик на 2 (`failing`): убирает ссылку только её отсутствие на странице или неудача загрузки самой страницы (после двух неудачных загрузок — уже первое такое событие). Если изменение замечено, а скачать файл не удалось (в том числе адрес отвергнут — `refused`), опрос его «не запоминает»: следующий запуск увидит изменение снова и повторит загрузку. Файл, оставленный как «содержимое не изменилось», тоже сверяется с `hash` манифеста и опубликованным SHA-1.

Оригиналы **не запускаются никогда**: ZIP, JAR, `.sh` (заголовок и ZIP-payload) и лёгкий установщик Windows (программа на Go с gzip-потоком настоящего установщика) разбирает наш код, записи ZIP читаются в памяти и на диск не пишутся; Inno Setup распаковывает innounp 2.71.2 (скачивается с закреплённого коммита репозитория InnoUnpacker, сверяется sha256 архива и программы), MSI с кабинетами и DMG — 7-Zip из образа runner'а, только версии 25.01 и новее: они по умолчанию отказываются создавать символические ссылки за пределы каталога распаковки (более старые не используются, такие дистрибутивы получают `skipped`). Вывод инструментов пишется в файл в рабочем каталоге, в журнал — только код выхода. Обход каталога после инструмента пропускает символические ссылки и reparse point.

Лимиты: манифест 1 MiB, страница 2 MiB, бандл 256 MiB, дистрибутив 1 GiB; распаковка — 4 GiB всего, 200 000 файлов, 512 MiB на файл, вложенность архивов 4. Больше лимита — ошибка, а не обрезка. Перенаправления — вручную, не больше 5, каждый адрес проверяется.

Адреса назначения — только публичные: loopback, частные сети, link-local, CGNAT 100.64/10, ULA, multicast, unspecified, адреса документации и IPv4-mapped такие же отвергаются до соединения (у бандлов НУЦ есть URL на частные адреса — они получают статус `refused`). Имя разрешается один раз на запрос, проверяются все его адреса, и соединение идёт только на них — без повторного разрешения и без прокси из окружения, поэтому смена DNS-ответа (DNS rebinding) соединение никуда не уведёт. Запрос без сессии может пойти на любой проверенный адрес (если один не отвечает — на следующий). Сессия — одна загрузка ссылки страницы: чтение страницы и запрос ссылки идут на адрес, на который сессия попала первым (пока адрес не закреплён, следующий пробуется, только если к предыдущему не удалось подключиться): у `ncl.pki.gov.kz` несколько адресов A, а PHP-сессия живёт на одном бэкенде, и ссылка, запрошенная у другого, отвечает `404.php`. Каждая ссылка получает свою сессию, поэтому замолчавший бэкенд стоит неудачи одной ссылки, а не всех. TLS сайтов `*.pki.gov.kz` выпущен публичным WebPKI-центром, поэтому для всех хостов используются корни WebPKI (таблица `TLS_ROOTS` в `xtask/src/upstream/http.rs` позволяет назначить хосту корни НУЦ).

## 3. Ветка `upstream`

Orphan-ветка, только JSON (проверяется перед каждым коммитом):

```
state.json                         состояние опроса (внутреннее)
latest/facts.json                  последние факты
index.json                         история
history/<id>/facts.json            факты записи
history/<id>/diff.json             разница с предыдущей записью
history/<id>/changes.json          изменения источников по опросу
```

- `id` = `<YYYY-MM-DD>-<version>-<key8>`: в `version` всё вне `[A-Za-z0-9._-]` заменено на `_`, `key8` — первые 8 hex sha256 байтов `facts.json`. `id` соответствует `^[0-9]{4}-[0-9]{2}-[0-9]{2}-[A-Za-z0-9._-]+$`.
- Все файлы — `serde_json` с отступами и переводом строки в конце, коллекции отсортированы, в фактах нет времени запуска, `ETag` и `Last-Modified`: одинаковый мир даёт одинаковые байты и одинаковый `key8`.
- `latest/facts.json`: `{schema: 1, manifest, bundles{symname: {name, version, required, …, fetch, jar, signer_matches}}, distributions{source id: {url, page, label, filename, size, sha256, published_sha1, format, status, unpack, files, jre, jars, embedded_manifests, meta}}, jars{sha256: {…, content_sha256, manifest_mf, signers, api, libraries, natives, keystores, embedded_manifests}}}`. `fetch`/`status`: `ok`, `pending`, `unreachable`, `refused`, `hash_mismatch`.
- `index.json`: `{schema: 1, entries: [{id, date, observed, version, key8, path, kind, summary{core[], plugins[{symname, from, to, change}], distributions[], notes[]}, issues[{key, number, label}]}]}`, по возрастанию `observed`. Строки `summary` — простой текст.
- `kind`: `baseline` — первые факты; `change` — изменение; `repack` — изменились только байты (перепакованный или переподписанный JAR с теми же содержимым, API и заголовками, переподписанный манифест с тем же JSON).
- Идентификаторы источников: `manifest`, `dist:<type>` (`disturls` с непустым URL), `page:<slug подписи ссылки>`, `fixed:ncalayer.zip`, `fixed:tzdb.dat`, `bundle:<symname>`.

## 4. Issues

- `upstream` — ядро: изменились поля манифеста (кроме переподписи), бандл ядра (`required`, кроме перепаковки) или содержимое дистрибутива. Смена подписанта манифеста — предупреждение в issue, не сбой.
- `upstream-plugin` — по одному на изменившийся плагин (кроме перепаковки), со строкой о порте из `plugins/<short>/registry.toml`.
- `upstream-alert` — сбой: `bad_signature`, `manifest_unreachable`, `collect_failed`; одно issue на вид в день: оно создаётся первым запуском дня, следующие его не меняют.

Последняя строка тела — `<!-- upstream-key: <key> -->`: `core:<version>:<key8>`, `plugin:<symname>:<version>` (`plugin:<symname>:removed:<key8>`), `alert:<kind>:<date>`. По ключу повторный запуск находит issue: тело то же — ничего; другое и issue открыто — тело заменяется и добавляется комментарий; закрыто — только комментарий, не переоткрывается. Номера issues записываются в `index.json` в том же коммите. Первый запуск даёт запись `baseline` без issues; перепаковка и смена доступности источника — только строка в `summary.notes`.

## 5. Ручной запуск

```sh
gh workflow run upstream.yml -f mode=run           # сбор и публикация
gh workflow run upstream.yml -f mode=issues-only   # issues последней записи ветки
```

Локально, без публикации:

```sh
cargo xtask upstream run --dry-run --emit target/upstream/emit
```

Без `--dry-run` `run` сначала открывает ветку `upstream` (её worktree и есть состояние, `--state` тогда запрещён), затем публикует каталог emit тем же кодом, что и `upstream publish` (нужны `GITHUB_TOKEN` и `GITHUB_REPOSITORY`). `publish` отказывается от каталога emit, в `index.json` которого нет какой-либо записи ветки: такой каталог собран не из её состояния и стёр бы историю. MSI и DMG распаковывает 7-Zip 25.01 или новее (путь — `ONCL_7Z`; пакет `7zip` Ubuntu 24.04 старее, с ним MSI и DMG получают `skipped`); без innounp установщики Inno Setup получают статус `skipped`. `cargo xtask upstream poll` печатает только изменения источников.

## 6. Разбор `upstream-alert`

- `bad_signature` — манифест не проверился: другая подпись, неизвестный издатель, CN не `NCALayer`. Факты не обновлены. Скачать `ncalayer.der` вручную и сверить подписанта с опубликованными сертификатами НУЦ; если НУЦ сменил корень — обновить `oncl_pki::roots`.
- `manifest_unreachable` — манифест недоступен (сетевая ошибка, статус не 2xx, HTML или другой файл вместо DER) 3 опроса подряд или с первого запуска. Проверить доступность сайтов НУЦ с runner'ов (журнал `collect`); при блокировке — резервный путь ниже.
- `collect_failed` — job `collect` упал: журнал прогона по ссылке в issue.

## 7. Резервный путь при недоступности сайтов НУЦ с runner'ов GitHub

1. Переменная репозитория `UPSTREAM_SOURCE=lab` — плановые запуски `collect` выключаются.
2. На хосте с прямым доступом к сайтам (приватная лаборатория), в checkout `main`. Наблюдатель соединяется только напрямую: переменные прокси (`HTTPS_PROXY`, `ALL_PROXY` и др.) он не использует — через прокси соединение ушло бы мимо проверенных адресов; если они заданы, `run`, `poll` и `tools` пишут об этом строку.

   ```sh
   git fetch origin upstream
   git worktree add --detach ../upstream-state origin/upstream
   cargo xtask upstream run --dry-run --state ../upstream-state --emit <dir>
   cargo xtask upstream publish --from <dir> --branch-dir ../upstream-lab --no-push --no-issues
   git -C ../upstream-lab push origin HEAD:refs/heads/upstream-lab-<дата>
   ```

   `publish` с `--no-push --no-issues` не требует токена: он проверяет каталог emit, создаёт worktree ветки `upstream` в `../upstream-lab` и коммитит факты. Затем — PR из `upstream-lab-<дата>` в `upstream`.
3. После слияния — `gh workflow run upstream.yml -f mode=issues-only`.
4. Когда доступ вернётся — удалить переменную `UPSTREAM_SOURCE`.

## 8. Потребители

- Реестр плагинов (P12): `index.json` и `latest/facts.json` (`manifest.version`, `bundles{symname: {version, required}}`), пересборка Pages по `repository_dispatch: upstream`.
- Приватная лаборатория: читает ветку без токена (по sha коммита), скачивает изменившиеся оригиналы со сверкой sha256 из `latest/facts.json`, декомпилирует изменившиеся JAR в песочнице без сети и учётных данных и хранит всё у себя.

## 9. Известные ограничения

- Имена файлов MSI в фактах — ключи таблицы File, как их выдаёт 7-Zip, а не имена при установке.
- Порты, вставленные в байткод инструкцией `sipush`, в пул констант не попадают и в `ports` не видны.
- Ссылки страницы загрузок без опубликованного SHA-1 скачиваются целиком на каждом опросе (сейчас SHA-1 публикуется для всех ссылок); ссылка в статусе `failing` или `refused` — на каждом запуске, пока загрузка не удастся.
- Первый бандл, JAR которого не скачался, получает API-diff только при следующем изменении: появление JAR после сбоя — только строка в `notes`.
