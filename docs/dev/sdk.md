# Rust SDK: встраивание, возможности, стабильность, готовность к публикации

`oncl-core` — встраиваемый SDK OpenNCALayer: типизированное потоковое подписание, проверка,
валидация, инспекция и штампы времени над файлами и потоками байт; доверие, ключи, часы, сеть,
аудит и лимиты ресурсов принадлежат приложению-хосту. В нём нет UI, демона, слушателя,
коллектора, установщика и самообновления, display-сессия не нужна. Автономный CLI `oncl` и
HTTP-сервис `oncl-server` — потребители того же движка, а не части замыкания SDK.

Страница — контракт SDK в том виде, как он поставляется. Дизайн — в
[`../design/platform.md`](../design/platform.md); README крейта —
[`../../crates/oncl-core/README.md`](../../crates/oncl-core/README.md).

## 1. Использование сегодня (релиза в реестре нет)

В crates.io ничего не опубликовано, и документация нигде не предлагает `cargo add` версии из
реестра. Свободны ли имена крейтов `oncl-*` на crates.io или заняты, **не проверено**.
Зависеть нужно от проверенного тега или коммита по path или git. SDK собирается с двумя
локально изменёнными крейтами RustCrypto (`vendor/streebog`, `vendor/hmac`: дополнительные
варианты для секретного ввода), поэтому у потребителя должен быть тот же `[patch.crates-io]`:

```toml
[dependencies]
oncl-core = { path = "OpenNCALayer/crates/oncl-core", features = ["full"] }

[patch.crates-io]
streebog = { path = "OpenNCALayer/vendor/streebog" }
hmac = { path = "OpenNCALayer/vendor/hmac" }
```

Для git у каждой записи должны быть одинаковые `git` URL и `rev`. `cargo xtask sdk smoke`
(раздел 7) собирает потребителя ровно так, но из распакованных пакетов исходников, а не из
workspace.

## 2. Features и замыкание зависимостей

У `oncl-core` нет default-features (`--no-default-features` — минимальный SDK). Замыкание — это
обычный граф зависимостей без proc-macro, который печатает `cargo xtask sdk closure`
(`cargo tree -p oncl-core --no-default-features [--features F] -e normal`, хост Windows):

| набор features | крейтов | крейты `oncl-*` в нём |
|---|---|---|
| minimal | 92 | oncl-core, oncl-gost, oncl-pki, oncl-registry |
| `tokens` | 99 | + oncl-token |
| `xml` | 95 | + oncl-xml |
| `pdf` | 95 | + oncl-pdf |
| `jose` | 97 | (новых `oncl-*` нет; добавляет base64, serde, serde_json) |
| `plugins` (включает `xml`) | 149 | + oncl-flows, oncl-pdk, oncl-plugin, oncl-protocol, oncl-token, oncl-xml |
| `full` | 150 | всё перечисленное, + oncl-pdf |

Ни один набор не содержит Slint, winit, tokio, axum, hyper, velopack, tray-icon, rfd, webbrowser
и никаких `oncl-ui`, `oncl-desktop`, `oncl-api`, `oncl-server`, `oncl-cli`, `openncalayer`,
`oncl-nmhost`; `cargo xtask sdk closure` падает, если один из них появился. `oncl-update` не
входит в `full`: он попадает только через собственную feature `distribution` крейта
`oncl-plugin` (хранилище пакетов плагинов); это отдельное добровольное включение этого крейта,
оно проверяется отдельно (его тесты и его место в цепочке публикации ниже).

| feature | что добавляет |
|---|---|
| (minimal) | хеширование, CMS/CAdES B/T/LT/LTA, PKI-валидация, ключи из файлов / встроенных PKCS#12 / JKS / слотов, названных хостом, пакеты (batch), инспекция, отдельные штампы времени |
| `tokens` | аппаратные токены и ID-карты как источники ключей |
| `xml` | XMLDSig, XAdES, WS-Security: подпись / добавление / проверка |
| `pdf` | PAdES: подпись / проверка |
| `jose` | JWS и JWT: создание / добавление / проверка |
| `plugins` | безголовый хост WebAssembly-плагинов (только рантайм, права выдаёт оператор) |
| `full` | всё перечисленное |

Шифрование и расшифрование в SDK пока не входят: они ждут казахстанский ГОСТ-бэкенд шифрования
и не заменяются путём «только RSA».

## 3. API встраивания на одной странице

Приложение строит один `Engine` и допускает один контекст на операцию:

```text
EngineServices::hash_only(limits)            // host services, nothing global
    .with_keys(provider, guard)              // key sources + the audit guard
    .with_validation(ValidationServices)     // trust anchors, status transport, clock
    .with_temporary_store(store)             // only for operations that must stage bytes
    .with_cades(...) / .with_plugins(...)    // optional
Engine::new(services)?
engine.begin(ExecutionGrant, OperationPolicy, Arc<dyn OperationControl>)? -> OperationContext
engine.sign / verify / hash / inspect / extend / stamp / ... (request, Source, output, &mut ctx)
```

Швы, которыми владеет хост (ничего не читается из сети, UI или настроек десктопа):

| шов | тип | примечания |
|---|---|---|
| разрешение | `ExecutionGrant` | действия и id ключей, только из доверенного кода хоста |
| ключи | `KeyProvider` (`keys::KeySources` для файлов/inline/named/токенов) | секреты берутся в заём, затираются (zeroize), не попадают в spool |
| аудит | `KeyUseGuard` | `before_use` обязан записать надёжно **до** применения закрытого ключа; отказ запрещает использование; `finish` записывает исход |
| доверие, статус | `ValidationServices` (якоря, промежуточные, `HttpTransport`, `NetworkPolicy`, часы) | строгие политики без статуса закрываются отказом |
| транспорт | `oncl_pki::http::HttpTransport` | CRL / OCSP / RFC 3161; `UreqTransport` — лишь значение по умолчанию; см. пример `custom_transport` |
| часы | `Arc<dyn Fn() -> OffsetDateTime>` | внедряются, чтобы вердикты воспроизводились |
| отмена, прогресс | `OperationControl` | контрольные точки; блокирующий ввод-вывод должен прерываться хостом |
| временное хранилище | `TemporaryStore` | ограниченное, приватное; никогда не хранит ключи и пароли |

Запускаемые примеры (`cargo run -p oncl-core --example <name>`; они выпускают одноразовую RSA
PKI во время запуска, не используют сеть и не коммитят ключей):

- `sign_file [WORKDIR [FILE]]` и `verify_file WORKDIR FILE`: отсоединённая CMS-подпись при
  строгой валидации; `verify_file` завершается с кодом 1 для изменённого документа.
- `custom_transport`: `HttpTransport` хоста, подключённый к валидации; при недоступной сети
  строгая подпись отклоняется с `NotApplied`.

`tests/examples.rs` запускает их как настоящие процессы, поэтому они не устареют.

## 4. Контракты результата и ошибок

**Вердикт.** `Verdict::{Valid, Invalid, Indeterminate}` — ответ о подписи, а не ошибка
выполнения. Отчёт разделяет целостность подписи, цепочку до якоря, срок действия, отзыв,
доказательство штампа времени и заявленное время подписания (`CheckStatus::{Passed, Failed,
Unavailable, NotApplicable}`); отсутствующие свидетельства — это `Unavailable`/`Indeterminate`,
но не `Valid`. Отмена, дедлайн и ошибки ресурсов — ошибки, а не вердикты.

**Замечания профиля.** Запрос профиля CAdES/PAdES (`cades-b`, `pades-t`, ...) требует больше,
чем целостность. Если сама подпись верна, но в CMS нет требования baseline, подписант сохраняет
`signature = Passed` и несёт `ValidationReason::Profile(ProfileViolation)`: нет signing-time в
подписи CAdES, есть signing-time в подписи PAdES (EN 319 142-1, таблица 1; Kalkan его пишет),
тип содержимого не id-data или нет атрибута signing-certificate. Такой подписант на этом
профиле `Invalid` и не заявляет `ades_level`. Проблемы digest, ESS и значения подписи остаются
отказами `Signature(..)` и сообщаются рядом, а не заменяются. Общие профили `pdf`/`cms` baseline
не требуют и судят те же байты только по целостности и доверию.

**AppliedState.** Каждый отказ после того, как операция с закрытым ключом могла начаться,
несёт `NotApplied`, `Applied` или `Unknown` (`OperationError::applied_state`). SDK не обещает
откат, повтор или «ровно один раз»: уже выданный удалённо штамп времени или подпись, вычисленная
до отказа приёмника вывода, остаются как случились. Охранник, отказавший в `finish` после
применения ключа, сообщает `Applied`.

**Ошибки.** `OperationError` (типизированная ошибка) и `ErrorCode` (`OperationError::code`,
стабильные машиночитаемые категории, никогда не выводятся из сообщений) публичны. Позиция по
стабильности на пре-1.0 альфах: хосты должны сопоставлять `ErrorCode` с wildcard-веткой.
Сегодня ни это перечисление, ни `ValidationReason`, ни `ProfileViolation` не помечены
`#[non_exhaustive]`; добавление варианта (как `ValidationReason::Profile`) ломает исходники и
указывается в заметках о миграции выпуска, который его вносит. Пометка этих перечислений
`#[non_exhaustive]` — запланированное изменение для первого выпуска, которому понадобится новый
код; в эту поставку оно намеренно не входит, так как меняет и сопоставления всех потребителей
внутри workspace. Текст `Display` вариантов — для логов, а не для управления потоком.

**Отчёты владеют своими резервами.** Результаты, удерживаемые хостом (`ScopedSigners`,
промежуточный вывод, результаты пакетов), сохраняют резервы памяти/метаданных и исходную область
операции; освобождайте их до следующего допуска при бюджете одной операции по умолчанию (так
делают примеры).

## 5. Лимиты

`ResourceLimits::default()` (профиль движка по умолчанию; хост может его менять):

| лимит | по умолчанию |
|---|---|
| операций одновременно | 1 |
| входной документ | 1_073_741_824 байт (1 ГиБ) |
| контейнер (структура CMS/XML/PDF) | 1_073_741_824 |
| обрамление (framing) | 67_108_864 |
| вывод | 2_214_592_512 (input + container + framing) |
| учитываемая живая память | 1_073_741_824 (1 ГиБ) |
| scratch (временное хранилище) | 8_589_934_592 |
| метаданные | 67_108_864 |
| дедлайн операции | 300 с от допуска, не перезапускается |

Документ больше 1 ГиБ отклоняется типизированной ошибкой `InputLimit`; хосты могут поднять
`input_bytes`, но гарантирован только 1 ГиБ. Это лимиты учёта, а не измерения RSS процесса.
Приёмочный прогон «1 ГиБ / 1 ГиБ» (`cargo xtask platform-proof`) выполнен: 70/70 на `9a1f0181`,
см. [`platform-acceptance.md`](platform-acceptance.md). Лимиты отдельных форматов (пакет — 1024
элемента, 8 подписей на JOSE-токен, итерации KDF при инспекции 10_000, ...) описаны в
соответствующих модулях. Унаследованные интерфейсы плагинов NCALayer сохраняют свои контрактные
лимиты строк/Base64; лимиты SDK на них неявно не распространяются.

**Подписанные результаты и `container_bytes`.** `input_bytes` ограничивает документ, а не
подпись: подписанный результат документа ровно размера `input_bytes` может превысить его только
на классифицированные байты контейнера, но не выше `container_bytes` или собственного предела
формата, и SDK читает такой результат повторно из любого `Source` (файл, сокет, HTTP-загрузка).
Хост, который обязан принять всю загрузку до начала работы (`oncl-server`), складывает этот ввод
в spool через `FrozenInput::capture_wire`, который не списывает ни один из двух лимитов (держит
не больше оставшегося лимита документа плюс оставшегося `container_bytes`, сужаемого
необязательным максимумом), и отдаёт движку `FrozenInput::wire_reader` — внешний seekable-источник
известной длины: движок списывает и классифицирует wire ровно как для файла, так что учёт тот же,
что у SDK и CLI. Движку никогда не отдаётся допущенный снимок таких байт (`FrozenInput::reader`
их отклоняет; `wire_inspection_reader` — повтор в той же операции для собственных проверок
хоста). Роль, которая вообще не документ, например свидетельства валидации со своими границами,
можно складывать так же с максимумом. Ключ сервера `container_bytes` (по умолчанию 1 ГиБ) — это
`ResourceLimits::container_bytes` движка; потолок wire для запроса с подписанным `input` равен
`input_bytes + container_bytes + framing_bytes + 64 КиБ` (см. `docs/user/http-api.md`).

**Приём ввода без слота.** Хост, которому отдают байты запроса, пока он ждёт медленного клиента,
не должен занимать на это ожидание один из слотов `max_in_flight` движка (или поток).
`Engine::admit_intake` — это `Engine::admit` без слота: память, временный диск, метаданные,
лимиты документа, контейнера и обрамления, дедлайн и управление списываются ровно как при
допуске, а `OperationAdmission::occupy_slot` (или, не позднее, `Engine::begin_admitted`) занимает
слот, когда ввод получен, и при занятости всех слотов отказывает тем же `CapacityExceeded`
(ничего не меняется, вызов можно повторить). Число таких операций хост ограничивает сам. Две
инкрементальные формы API «одним вызовом» принимают байты частями: `oncl_pki::io::InputSpool`
(`document` для `FrozenInput::capture`, `wire` для `FrozenInput::capture_wire`; `push` на каждую
часть, `finish` отдаёт `FrozenInput`) и `oncl_pki::digest::HashStream` (`hash_source`); каждая
часть учитывается, ограничивается (проба N+1 на пределе, `InputLimit`) и сверяется с управлением
и дедлайном операции, как в форме «одним вызовом», с одним отличием по памяти: эта форма
списывает с операции свой буфер чанка 256 КиБ, а `InputSpool` буфера не держит и памяти на него
не списывает (часть пишется напрямую, не больше `IO_CHUNK_BYTES` за запись). Хост, который
накапливает части перед `push`, владеет этим буфером и списывает его сам: `oncl-server` один раз
на запрос резервирует `IO_CHUNK_BYTES` через `ResourceScope::reserve_memory` и пушит по 256 КиБ
(он также сбрасывает накопленное перед ожиданием клиента, чтобы правила темпа не относили время
диска на счёт клиента). `oncl-server` использует все три для фазы загрузки (см.
`docs/user/server.md`).

**Учёт CAdES.** Проверка, расширение и сопровождение подписью (co-sign) в `cms::ades` (и простой
CMS co-sign) читают wire подписи один раз классифицирующим CMS-парсером, пока складывают его в
spool: структура SignedData (заголовки, сертификаты, значения отзыва, signer infos и их токены
штампов времени) — контейнер и ограничена `container_bytes`; документом считается только
содержимое. Отсоединённое содержимое читается отдельно и списывается с `input_bytes`.
Отсоединённый документ, уже допущенный хостом (читатель `FrozenInput`, как у spool в
`oncl-server`), воспроизводится и повторно не списывается — одинаково при verify, extend и
co-sign. Присоединённый результат CAdES — это документ + подпись: документ ровно размера
`input_bytes` снова проверяется, расширяется и сопровождается подписью, на один байт больше —
`InputLimit`, а структура подписи, не помещающаяся в лимит контейнера, — `ContainerLimit` (или
`InputLimit`, если весь присоединённый wire уже при приёме больше `input_bytes +
container_bytes`), до любого использования ключа. Свидетельства, которые движок копирует из wire
(сертификаты, статус, токены штампов), снова списываются с `container_bytes`, а extend и co-sign
списывают и записываемую структуру (замер: verify 7081, extend до LT 17429 байт контейнера), так
что лимит контейнера должен вмещать структуру плюс эти свидетельства и выходную структуру;
свидетельства дополнительно ограничены `EvidenceLimits`. Spool — временное хранилище
(`TempLimit`) до `input_bytes + container_bytes` плюс один чанк. Простой профиль `cms`
(`cms::stream::verify`/`extract`) всегда читал wire так; до этого правила путь CAdES списывал весь
wire с `input_bytes`, что отклоняло документ на пределе.

**Надбавка контейнера для подписанных PDF.** Лимит документа — не вся граница обратного чтения
подписанного PDF: чтение PDF, который уже несёт подписи, может превысить лимит документа на
ограниченную надбавку. Предел:
`min(container_bytes, (max_revisions - 1) * 4 * max_object_bytes + PdfLimits::max_evidence_bytes)`
(`crates/oncl-pdf/src/verify.rs`, `lib.rs`): около 188 МиБ по умолчанию
(`max_revisions` = 16, `max_object_bytes` = 1 МиБ), `PdfLimits::max_evidence_bytes` по умолчанию
128 МиБ. `max_evidence_bytes` — поле слоя PDF; ни один поставляемый хост (CLI, сервер, десктоп)
пока не выводит его из `EvidenceLimits.max_total_bytes`, поэтому у всех поставляемых хостов
остаётся значение по умолчанию 128 МиБ.

### Реестр плагинов и объявленные операции (`plugins`)

`PluginRegistry::install(manifest, package, wasm, limits, policy)` записывает вместе с плагином
`PackageHash`. `PackageHash::File` — SHA-256 всего файла пакета, прочитанного
`oncl_plugin::Package::read`; `PackageHash::Loose` (`plugins::loose_package_hash(manifest_toml,
wasm)`, его используют CLI и сервер, загружающие манифест и модуль раздельно) — хеш этих двух
входов с доменным разделением. Виды никогда не равны и кодируются разными тегами
(`PackageHash::canonical`); loose-хеш — не хеш файла пакета, и ничто не сверяет ни тот, ни
другой с модулем: реестр принимает значение как есть. Хост, который грузит через
`oncl_plugin::Store` (feature `distribution`, этим крейтом не включается), обязан брать манифест,
модуль и `File(package.sha256)` из одного значения `Package`. `BuiltinInfo::sha256` (только
модуль) не относится ни к одному виду. Идентичность зарегистрированного плагина для аудита —
`PluginIdentity { id, package, version }`, а не имя из манифеста (`Engine::plugin_identity`).

Плагин без `[[operations]]` не меняется: его права и `PluginPermission::with_keys` жёстко
фиксируют ключ. Для плагина, объявляющего операции, `PluginRegistry::allow_declared` (и
`allow_declared_with_pki`) добавляет политику реестра, построенную только из манифеста:
объявленные импорты для одной тройки `(plugin, operation, caller)` и **любой** ключ. Выбранный
ключ проверяется на стороне разрешения конкретного вызова (`PluginPermission::with_keys` там), а
она никогда не принимает объявленную политику за ключ. Объявленная `network` соблюдается: `none`
не принимает ни одного адреса, `pki` принимает только адреса на PKI-хостах, которые передаёт хост
(обычно `oncl_plugin::NCA_PKI_HOSTS`, поддомены включены), а операции с `network = [urls]` в этом
выпуске не запускаются в ручном окне (`PluginRequestError::NetworkUnsupported`, в списке не
показываются). Вправе ли вызывающий данного вида использовать вариант операции `manual` или
`server` — проверка хоста, который всё связывает.

`Engine::plugin_operations` перечисляет `Manifest::manual_operations` (без URL-сетей).
`Engine::plugin_request` строит точный текст запроса, который получает модуль, из разобранного
JSON-шаблона (любой JSON-объект; каждое строковое значение-плейсхолдер целиком на любой глубине
заменяется, никогда не ключ и не часть строки) и типизированных значений `PluginParam`, а не
вставкой текста: итоговая длина считается заранее и отклоняется выше `max_transfer` плагина
(`ErrorCode::InputLimit`) до любой подстановки, затем пишется один раз в буфер этого размера.
Документы — стандартный base64 и не пустые; текст считается в символах, как его объявленный
лимит, и, если профиль ключа читает его как XPath, проверяется `Source::check_value`. Текст,
являющийся подписываемым содержимым, не может содержать управляющих символов кроме `\n` и `\t`,
двунаправленных и невидимых (`InvalidValue`; окно передаёт тот же `&str`, что отображает).
Операция с ключом обязана объявлять `network = "pki"`, а текстовый параметр может быть
содержимым ключа любого вида (его байты UTF-8). Текст не нормализуется. Вывод — компактный JSON
с отсортированными ключами объектов (порядок ключей шаблона не сохраняется), целые как записаны;
число шаблона, не являющееся `i64`/`u64`, отклоняется (`InvalidTemplate`), а не печатается заново.
Необъявленные, не-manual, `derived` и URL-сетевые операции и неверные параметры отклоняются
`PluginRequestError`, всегда `NotApplied`, до использования любого ключа. Согласие в этот API не
входит; билет использования ключа, его охранник и одобренный ручной вызов (ниже) идут следом.

#### Билет использования ключа и `PluginConsentGuard` (`plugins`)

Плагин, чей манифест объявляет любые `[[operations]]`, вызывается через `plugin_call` только под
объявленным именем операции, кто бы ни выбрал метку (ручное окно, grant сервера, флаг CLI):
любая другая метка отклоняется до запуска модуля (`PermissionDenied`, `NotApplied`,
`OperationContext::plugin_refusal() == Some(TicketRefusal::UndeclaredOperation)`). Сервер
пропускает (и логирует как ошибку) grant с необъявленной операцией такого плагина, а CLI
отклоняет вызов. Плагин без объявлений не меняется. Вызов под объявленным именем получает билет.
Для каждого из `keys_sign_raw/cms/cms_ex/xml/xml_ex/xades` Core один раз декодирует аргументы,
строит из этого же декодированного значения `plugins::PluginUse` и кладёт его в контекст
операции; `AuthorizedSigner::sign_digest` переносит его в `KeyUseEvent` (`KeyUseEvent::plugin()`,
`None` для любого использования документом и для операций плагина без объявлений). Билет
называет идентичность плагина (`id`, `PackageHash`, версия), объявленную операцию, вызывающего,
вид подписи, handle и `KeyId` единственного привязанного ключа, `ContentBinding` (SHA-256 и длина
подписываемых байт; `prehashed` для входа CMS `Digest`) и `options_sha256`. Хеш опций — SHA-256
от `oncl_plugin::operations::Profile::encode` по профилю, построенному из фактических
аргументов, тем самым кодировщиком, который `KeyUse::options_sha256` использует для объявленного
профиля. Аргументы, которые никакой профиль выразить не может (CMS с co-sign, `attrs.extra`,
`econtent_type`, выбор `digest`, сертификаты `Extra`, собственный TSA, signingTime не по
умолчанию, XML `signature_id`/объект signing-time, XML `transforms` не в виде проверяемого
списка, цепочка XAdES), отклоняются до открытия ключа. XML `transforms` принимаются только как
проверяемый список: сначала `enveloped`, затем не больше одной канонизации (пустой список и
любой другой порядок отклоняются); список входит в хеш опций. `cosign = Auto` принудительно
становится `Never`, поэтому содержимое билета — действующее содержимое. Импорт, вид которого
операция не объявляет, или чьё объявленное содержимое — `derived`, отклоняется. Объявленная
операция привязывает не больше одного ключа; каждый импорт, принимающий ключ (`keys_describe`,
`keys_chain`, `keys_release`, импорты подписи), на любой другой handle отвечает единственным
`PermissionDenied`, а `keys_release` привязанного handle идемпотентен. Билет допускает ровно
одно использование (`max_uses = 1`).

`KeyUseEvent::plugin()` существует только с feature `plugins` крейта `oncl-core`; доступный без
feature `KeyUseEvent::is_plugin()` говорит, несёт ли событие билет (без feature всегда `false`).
`KeyUseGuard` хоста, регистрирующего плагины с объявленными операциями, ОБЯЗАН отклонять любое
событие, для которого `is_plugin()` истинно, если это не охранник плагина (охранник документов,
игнорирующий его, авторизовал бы использование по билету как использование документом);
`oncl-server`, `oncl-cli` и `ConsentGuard` из `oncl-ui` так и делают.

`PluginConsentGuard` (`KeyUseGuard`) — охранник движка плагинов. `before_use` отклоняет
(`PermissionDenied`, ключ не применён; причина записывается по `OperationId` в ограниченный лог
на `REFUSAL_LOG` (64) записей: `refusals(id)`, `take_refusals(id)`, `refusal_log()`), если только
событие не несёт билет и охранник не держит непросроченный `PluginApproval` для того же вызова,
идентичности плагина, операции, вызывающего, ключа и handle, с одним неистраченным
`ApprovedUse`, чьи вид, содержимое и хеш опций равны билету; использование тогда тратится. Без
одобрения он отклоняет всё, в том числе использование ключа документом (без билета): документам
нужен свой движок. `PluginApproval` (не `Clone`, не `Deserialize`, публичного конструктора нет)
выдаёт Core (ниже); его nonce принимается один раз. Охранники сервера (`DurableAuditGuard`) и CLI
(`Authority`) отклоняют каждое использование по билету, пока не появятся их собственные grants
(`plugin_bytes` в MP8/MP9); плагины без объявлений не меняются.

#### Manual window (ручное окно): сводка согласия, одобрение, одобренный вызов (`plugins`)

Три шага Core, в таком порядке (`docs/design/manual-plugins.md` 4.2, 4.3, 4.8). И
`plugin_prepare`, и `plugin_call_approved` принимают один и тот же `ManualCall { plugin_id,
operation, params, key: &PluginKeyBinding, caller: &CallerContext }`:

1. `Engine::plugin_prepare(&ManualCall, &mut OperationContext)` возвращает `PluginPrepared` или
   `PluginPrepareError` (всегда `NotApplied`). Он один раз открывает ключ (вход в токен или
   расшифровка хранилища ключей происходят здесь и ещё раз при вызове), поэтому хост собирает
   секрет ДО показа согласия и кладёт его в запрос ключа в привязке; неудачное открытие — это
   `KeyUnavailable` без причины.
   Он проверяет параметры как `plugin_request`, замораживает то, что подписывается (байты
   привязанного параметра, SHA-256 и длину; для профиля `cms_ex` с `content_form` = `digest` —
   дайджест, который сам Core считает хеш-алгоритмом алгоритма подписи привязанного ключа той же
   функцией, которой позже пользуется подписант: ГОСТ 34.311, Стрибог или SHA-2 по сертификату и
   политике контекста, но никогда не дайджест, названный плагином), и опции
   (`KeyUse::options_sha256`, где источники `param:` профиля заполнены из типизированных текстовых
   параметров: тот же кодировщик, что на стороне билета). `caller` обязан быть
   `CallerContext::LocalOperator` (у ручного окна нет origin), а привязка ключа — нести публичные
   метаданные (`with_public_metadata`: alias и сертификат). Метаданные — заявление хоста о ключе,
   которым подписывают: Core показывает их и отдаёт плагину (`BoundKey`, `keys_describe`), а
   `plugin_prepare` сверяет их сертификат с тем, что хранилище держит для ключа
   (`CertificateMismatch`).
   `PluginPrepared::summary()` — это `ConsentSummary`: **доверенное** описание для отображения
   (идентичность `{id, PackageHash, version}`, имя операции, вид, число использований,
   объявленный профиль с подставленным текстом пользователя, хеш опций, имя параметра
   содержимого, длина, SHA-256 и prehashed-дайджест, alias ключа, серийный номер, subject CN,
   отпечаток SHA-256 и `not_after`, а также PKI-адреса, зарегистрированные хостом). Текста
   плагина в нём нет (`name`, `description`, `label` остаются в собственном кадре плагина);
   `key.alias` и `key.subject_cn` — строки хоста и сертификата, и отрисовщик обязан их
   экранировать.
2. `UserConfirmation::after_user_confirmed(&ConsentSummary)` — единственный способ получить токен,
   который принимает `PluginPrepared::approve(confirmation, ttl)`. **Обязанность хоста:**
   вызывать его только из обработчика собственного действия пользователя на элементе
   подтверждения, после отрисовки именно этой сводки; никогда не подтверждать автоматически,
   заранее или по сохранённому ответу (ничего не сохраняется). Он называет SHA-256 показанной
   сводки, так что подтверждение одной сводки не одобряет никакую другую. Токен не `Clone` и не
   `Copy`. `approve` возвращает `PluginApproval`: вид, привязка содержимого и хеш опций из шага
   prepare, одно использование (`max_uses = 1`), вызов контекста, с которым он подготовлен,
   дедлайн `ttl` по монотонным часам от текущего момента (`None` — это `APPROVAL_TTL` = 120 с;
   больший запрос обрезается до него, ноль отклоняется) и nonce из 16 байт CSPRNG операционной
   системы (при сбое ГСЧ ничего не выдаётся).
3. `Engine::plugin_call_approved(&ManualCall, PluginApproval, &ManualHost, &mut OperationContext)
   -> ApprovedCall` запускает модуль в ручном окне. Он заново выводит использование из
   параметров, переданных **сейчас**, и до запуска модуля отклоняет одобрение, выданное не ровно
   для них (другой документ, текст, ключ или handle, вызывающий, операция, вызов; просрочено):
   модуль никогда не видит документ, которого пользователь не одобрил. Затем строит запрос
   (`plugin_request`), передаёт одобрение `PluginConsentGuard` движка и запускает
   `oncl_plugin::Compiled::call_manual` со свежим `BoundInteraction` (`BoundKey` строится из того
   самого `PluginKeyBinding`, которым подписывает бэкенд; часы — часы валидации, считанные при
   вызове; транспорт и `OcspCache` — хоста, из `ManualHost`; origin нет). Охранник остаётся
   авторитетной проверкой при использовании ключа. Одобрение отзывается по окончании вызова
   (`Drop`, то есть и при trap, ошибке и панике). Движок должен быть построен через
   `EngineServices::with_plugin_keys(provider, Arc<PluginConsentGuard>)`: это его единственный
   охранник ключей (`with_keys` его сбрасывает, и одобренный вызов тогда отклоняется с
   `TicketRefusal::NoGuard`); одновременно идёт один одобренный вызов (`Busy`). Документы держите
   на другом движке: `ConsentGuard` десктопа отклоняет событие с билетом, а охранник плагина —
   событие без билета.

Одобрение привязывает SHA-256 сертификата подписанта: его несут `ApprovedUse` и `PluginUse`, его
показывает `ConsentSummary.key.fingerprint_sha256`, `plugin_prepare` один раз открывает ключ и
отклоняет (`CertificateMismatch`), если сертификат хранилища не совпадает с метаданными
привязки, а в точке подписи `AuthorizedSigner` ставит на билет отпечаток сертификата, который
держит аренда ключа; охранник (и быстрая проверка `plugin_call_approved`) отклоняют другой с
`TicketRefusal::CertificateChanged`, ключ не применён. Alias — только для отображения и не
сверяется. Алгоритм prehash выбирается тем же строгим правилом, что у подписанта. Операционные
замечания: давайте каждому движку свой `PluginConsentGuard` (один слот одобрения); вызов,
отклонённый как `Busy`, расходует своё одобрение (пользователь подтверждает снова); хосты ОБЯЗАНЫ
задавать дедлайн в контексте, передаваемом в `plugin_call_approved` (плагин держит слот
операции, пока не истечёт дедлайн или топливо); дедлайн одобрения — монотонный `Instant`, который
может не идти, пока система приостановлена.

`ApprovedCall` — честный исход: `result()`/`response()` (строка ответа модуля), `applied()`
(`Applied` и когда модуль упал после использования ключа, `Unknown`, когда само приложение не
сообщило, `NotApplied` для каждого отказа) и `refusals()` (типизированные `TicketRefusal` этого
вызова: от охранника или от проверок до запуска модуля, плюс `NoGuard`, `Busy`, `Replayed`,
`UndeclaredOperation`, `Caller`).

#### Подкоды отказов и факты аудита (`plugins`)

`ErrorCode` не меняется. Рядом с ним у каждого отказа плагина есть `PluginRefusalCode` (стабильный,
`#[non_exhaustive]`): `id()` — строка в kebab-case (`content-mismatch`, `package-changed`,
`approval-expired`, `not-declared`, `not-granted`, ...), которая **никогда не переиспользуется и
не перенумеровывается**; `ALL` перечисляет все подкоды в порядке только-добавления, а тест
фиксирует полный список id, так что изменение всегда намеренное. `error_code()` — `ErrorCode`, с
которым сообщается отказ (всегда тот, что даёт `OperationError::code`: `PermissionDenied` для
отказов по билету, вызывающему и объявлению, `InputLimit`/`InvalidInput` для параметров,
`UnsupportedAlgorithm`, `MissingKeyProvider`, `Io`). Он есть у каждой причины: `From<TicketRefusal>`,
`From<&PluginRequestError>`, `From<&PluginPrepareError>`, `From<ApprovalIssueError>`,
`From<ApprovalRejected>` и метод `subcode()` каждой. `TicketRefusal::NotGranted` — для
использования ключа сервером или CLI, которое не покрыто ни одним grant оператора;
`TicketRefusal::AuditFactTooLong` — для использования, чьи версию или id grant нельзя записать в
аудит (больше 255 байт), отклоняется до обращения к журналу.
`DurableAuditGuard::with_plugin_policy` возвращает `io::Result<Self>` (ошибка, если охранник уже
разделён).

Где хост это читает: `ApprovedCall::subcode()` (первый отказ охранника, иначе причина, по которой
вызов нельзя было подготовить; `None`, когда ничего не отклонено, в том числе после ошибки,
наступившей после применения ключа), `OperationContext::plugin_refusal_code()` (необъявленная
метка, отклонённая в `plugin_call`), а для сервера с охранником `DurableAuditGuard` —
`take_plugin_refusals(operation_id)`, отображаемый через `PluginRefusalCode::from`. **Плагин
подкода никогда не видит**: его собственная ошибка — голый `PermissionDenied` без текста с
причиной.

`PluginAuditRecord::from_ticket(&PluginUse, nonce, grant_id)` — то, что называет аудит
использования: плагин `{id, вид пакета + sha256, version}`, операция, `PluginUse::digest()`
(дайджест билета), SHA-256 nonce одобрения (с доменным разделением; никогда не сам nonce),
SHA-256 и длина содержимого, является ли содержимое prehashed-дайджестом, SHA-256 опций, вид
вызывающего (не его имя), `declared` и `grant_id` оператора. Ни байт документа, ни параметров,
ни секретов. `PluginConsentGuard` выдаёт его событием `tracing` (`target =
"oncl::plugin_audit"`), когда использование авторизовано, а отказ с его `subcode` и дайджестом
билета — событием `warn`; отказы, не доходящие до охранника (ошибка запроса или prepare,
одобрение, отклонённое вызовом), — события `warn` того же target с `subcode`. Долговременная
форма — в `docs/user/server.md` (аудит).

`PluginApproval::new`, `ApprovedUse::new` и остальные конструкторы не публичны. С feature
`testing` крейта `oncl-core` (никогда не входит в выпуск) `PluginApproval::for_tests`,
`ApprovedUse::for_tests`, `PluginUse::for_tests` и `KeyUseEvent::with_plugin_ticket_for_tests`
подделывают то, чего Core никогда бы не сделал, — для тестов охранников. Сборка выпуска
`testing` никогда не включает: программы выпуска собираются с `-p`, но `cargo build --workspace
--all-targets` и `cargo test` объединяют `testing` из dev-зависимостей в те же бинарники, поэтому
CI запускает `cargo xtask check-release-features`. Он читает `cargo tree -p
<openncalayer|oncl-cli|oncl-server|oncl-ui> -e normal -f "{p} [{f}]"` (features, разрешённые для
обычного дерева, без dev-зависимостей) и падает, если у какого-либо крейта виден `testing`.

## 6. Semver, версии и миграция

- Версия общая для всех крейтов SDK и приложений (`[workspace.package]`). У плагинов свои версии.
- До 1.0 (`0.1.0-alpha.N`) любая альфа может ломать публичный API любого крейта SDK. Каждая
  поломка требует повышения версии и заметки о миграции ниже; внутренние модули не становятся
  стабильными контрактами только потому, что они `pub` для workspace.
- Версия SDK — **следующая невыпущенная** на момент изменения, читается из тегов и манифестов, а
  не угадывается. Новейший тег — `v0.1.0-alpha.7` (выпущен 2026-11-13, пре-релиз), и это же
  версия `[workspace.package]` в этом дереве; следующее повышение — до `0.1.0-alpha.8`.
  Повышение меняет вместе: `[workspace.package] version`, пины `=0.1.0-alpha.N` цепочки SDK в
  `[workspace.dependencies]` (нужны для `cargo package`), четыре встроенных `plugin.toml`
  (`version`, `min_core`), lock-файлы (`Cargo.lock`, `plugins/Cargo.lock`,
  `crates/oncl-pdk/example/Cargo.lock`) и строку статуса в README, если она называет выпуск.
  Пин, расходящийся с версией workspace, делает весь workspace неразрешимым (`failed to select
  a version for the requirement oncl-gost = "=0.1.0-alpha.8"`), так что забытый пин не уедет в
  выпуск.

Заметки о миграции:

| от → к | изменение |
|---|---|
| 0.1.0-alpha.6 → 0.1.0-alpha.7 | `oncl-core`, `oncl-xml` и `oncl-pdf` впервые появляются как крейты SDK (в alpha.6 их не было): прежней публичной поверхности, с которой нужна миграция, нет. `oncl-pki` встраивает корни НУЦ из собственного каталога `roots/` (те же байты, что `fixtures/nca/prod`, проверяется тестом) и `testing-data/` вместо чтения `fixtures/` вне крейта; API не меняется. У `oncl-core` появляется feature `full`. |

## 7. Готовность к публикации (и что не заявляется)

Цепочка SDK в порядке публикации (каждый крейт после тех, от которых зависит):

`oncl-gost` → `oncl-registry` → `oncl-pki` → `oncl-pdf` → `oncl-protocol` → `oncl-pdk` →
`oncl-xml` → `oncl-token` → `oncl-flows` → `oncl-update` → `oncl-plugin` → `oncl-core`

Это множество, достижимое из `oncl-core` со всеми features плюс `distribution` крейта
`oncl-plugin` (`oncl-update`). Эти крейты несут `description`, `license` (Apache-2.0),
`repository`, `rust-version`, `keywords`, `categories`, список `include` (исходники, данные,
которые встраивает сборка, `LICENSE`, `NOTICE`; без тестов, fixtures, корпусов, скриптов и
оракулов; `oncl-core` дополнительно поставляет `README.md`, три примера и `THIRD-PARTY.txt`) и
`publish = true`. Всё остальное (`oncl-ui`, `oncl-desktop`, `oncl-api`, `oncl-server`,
`oncl-cli`, `openncalayer`, `oncl-nmhost`, `oncl-tls`, `oncl-trust`, `oncl-ipc`, встроенные
модули, их сборочные и тестовые крейты, shim'ы для Windows 7, `oncl-testkit`, `oncl-port-tests`,
плагины) остаётся `publish = false` по умолчанию workspace.

Проверка, не требующая ни реестра, ни загрузки (`cargo xtask sdk smoke`):

1. `cargo package --offline` всей цепочки **с** верификацией: каждый крейт собирается из
   собственного упакованного tarball, а соседи разрешаются из локального оверлея tarball'ов
   cargo. Нужны `--config patch.crates-io.hmac.path=…` и `…streebog.path=…` (ниже).
2. Файлы `.crate` распаковываются; smoke проверяет, что внутри нет `tests/`, `fixtures/` и
   `target/`, а `LICENSE`/`NOTICE` есть.
3. Отдельный крейт (свой `[workspace]`, свой lock-файл) зависит от `oncl-core` (`full`) и
   `oncl-pki` по path в распакованные исходники, с `[patch.crates-io]` на остальные распакованные
   крейты и на изменённые `hmac`/`streebog`. Его `cargo metadata` не должен содержать ни одного
   локального пакета вне распакованных исходников; его `cargo tree` не должен содержать ни одного
   из запрещённых крейтов UI/десктопа/обновления/сервера/рантайма; затем он собирается и
   запускается: настоящие подпись и проверка CMS, изменённый документ отклонён, а офлайн-подпись
   отклонена с `NotApplied`. В этом процессе нет ни дисплея, ни демона, ни коллектора, ни
   слушателя.

Что **не** проверено и не заявляется:

- **Загрузка заблокирована.** `oncl-gost`/`oncl-pki` нуждаются в дополнительной feature
  `secret-input` изменённых `streebog` и `hmac`; в версиях с crates.io её нет, поэтому
  `cargo package` крейта `oncl-gost` без конфига patch падает («`hmac` does not have that
  feature»); `cargo publish` сначала пакует, поэтому ожидается, что он остановится именно там
  (не запускалось: здесь ничего не публикуется). До любого выпуска их нужно опубликовать под
  именами, которыми мы владеем, или предложить upstream, а манифесты соответственно изменить.
  Это решение, а не часть этой поставки.
- Доступность и принадлежность имён крейтов в реестре не проверены.
- `cargo publish --dry-run` против настоящего реестра, загрузка и проверки после неё остаются за
  отдельно санкционированной публикацией.
- Consumer smoke работает только на платформе хоста; матрица Linux/macOS/Win7 — отдельные гейты
  (приёмочный прогон «1 ГиБ / 1 ГиБ» выполнен, см. раздел 5).

Команды: `cargo xtask sdk closure`, `cargo xtask sdk smoke [--keep]`,

## Лимиты свидетельств и большие встроенные CRL (D1)

`oncl_pki::evidence::EvidenceLimits` получил три публичных поля (поломка исходников для литералов
структуры; все литералы в дереве мигрированы):

| Поле | Смысл |
|---|---|
| `max_crl_bytes` | суммарный допуск CRL-свидетельств в spool |
| `max_crl_item_bytes` | на один CRL, никогда выше `crl::MAX_CRL_LEN` (64 МиБ) |
| `max_total_bytes` | сумма по всем категориям свидетельств, включая CRL |

`EvidenceLimits::validate` отклоняет нулевые `max_crl_bytes`, `max_crl_item_bytes` или
`max_total_bytes` с `EvidenceError::InvalidLimits` (как отклоняет и нулевой `max_bytes`). Порядок
трёх он не навязывает: приём берёт минимум из предела элемента, суммы по CRL и общего и
ограничивает предел элемента значением `MAX_CRL_LEN`, так что предел выше другого просто не
является определяющим. `EvidenceLimits::intersect` — единственный поэлементный минимум двух
наборов, им пользуются `oncl-core` и `oncl-xml`.

`max_bytes`/`max_item_bytes` теперь относятся только к свидетельствам, не являющимся CRL. Чтобы
сохранить прежний допуск литерала, задайте `max_crl_bytes = max_total_bytes = max_bytes` и
`max_crl_item_bytes = max_item_bytes`. Декодированные сертификаты, ответы OCSP и токены сохраняют
усиленное списание RAM/метаданных; CRL больше `crl::MAX_BER_CRL_LEN` (1 МиБ) обязан быть DER,
сканируется на месте через `crl::serial_status` и списывается один раз; меньший может быть BER,
нормализуется в дерево и сохраняет усиленное списание. `EvidenceStore::collect_base64` допускает
элемент свидетельства из текста base64 с квотами на декодированный размер, для XML-носителей.

Хосты: CLI допускает CRL до 32 МиБ (16/1 МиБ для прочих свидетельств, 48 МиБ всего) и потолок
покрытия размером с документ (потолок вывода); у `oncl-server` тот же потолок покрытия (его
`max_coverage_bytes` — потолок вывода операции, а не `input_bytes`: штамп PAdES LT -> LTA
покрывает весь подписанный документ, который при полном допуске уже превышает `input_bytes`).
`oncl-server` (2 МиБ на CRL) и `oncl-ui` (1 МиБ) сохраняют прежние границы и поэтому отклоняют
sign/extend с полным CRL НУЦ (около 20 МБ); хост, которому это нужно, задаёт поля `max_crl_*`.
Хост, который отдельно ограничивает PDF-свидетельства, должен выводить эту границу из
`EvidenceLimits.max_total_bytes` (ни один поставляемый хост пока так не делает; см. надбавку
контейнера в разделе 5). Потоки свидетельств DSS в PDF читаются областями: они больше не
ограничены `PdfLimits::max_object_bytes`, только учётом контейнера и памяти в области действия и
квотами свидетельств.

Область D1: офлайн-проверка CMS/CAdES и, со слайсом XML ниже, XAdES со встроенным полным CRL. Не
покрыто: онлайн-загрузка CRL (`crl::fetch_for`, по-прежнему декодируется целиком с усилением
128x), файлы CRL оператора (`--evidence-crl` ограничен 256 КиБ на файл),
онлайн-загрузка для PAdES-LT и сторона ПОДПИСИ XAdES (ниже). Структурные защиты PAdES (`/ID`
trailer, свободная голова объекта 0) исправлены; проверка PAdES-LT настоящих файлов NCANode
ограничена чтением областей DSS и пределом надбавки контейнера (раздел 5, «Лимиты»).

### XAdES с полным CRL (сторона проверки)

XAdES-LT NCANode/Kalkan пишет полный CRL НУЦ (около 20 МБ, 27 МБ base64 с `&#13;` в концах
строк) в `xades:EncapsulatedCRLValue`. `XmlVerifyProfile::max_metadata_bytes` теперь ограничивает
только структурную разметку: текст листьев `EncapsulatedX509Certificate/OCSPValue/CRLValue`
записывается сканером как исходные экстенты, вычитается из свойства, в котором находится, и
потоком пропускается через `EvidenceStore::collect_base64` (ссылки на сущности и CDATA
декодируются на лету, буферы по 16 КиБ), так что декодированные байты списываются с
`max_crl_item_bytes`/`max_crl_bytes`/`max_total_bytes` до сохранения. Ни `String`, ни DOM, ни
`Vec` base64 для листа не существует. `validate_unsigned_layout` решает по структуре, записанной
сканером, а представление архивного штампа времени берёт канонические текстовые отрезки каждого
листа у канонического рендерера (`canonical_stream::stage_with_leaves`), а не разбором
отрендеренных байт. Текст корректного листа ограничен только квотами свидетельств на его
декодированные байты: лист из пробелов декодируется в ничто и ограничен лишь размером входа (он
идёт потоком и никогда не удерживается). XAdES во встроенном WSSE сохраняет прежнюю границу
экстента (`70 x max_metadata_bytes` на `Signature`), так что CRL больше примерно 17 МБ внутри
SOAP-конверта по-прежнему отклоняется.

Видимые хосту изменения: заданные хостом `EvidenceLimits` больше не обрезаются лимитом метаданных
(`effective_limits`: лимит лишь масштабирует значения по умолчанию у хоста, который ничего не
настраивал, и то же верно на путях sign и extend (`effective_limits` общая); ненастроенный
SDK-хост по-прежнему отклоняет CRL больше 256 КиБ с `EvidenceError::Limit`);
`VerifyRequest::xades_with_limits` — аналог `cades`/`pades` для XAdES, и CLI использует его со
своей квотой CRL 32 МиБ; обратное чтение отсканированного (DER, больше 1 МиБ) CRL списывается
только как память, но не ещё и как метаданные (допуск XML-индекса — 56 МиБ из 64 МиБ бюджета
метаданных по умолчанию). `oncl-server` и `oncl-ui` лимитов XAdES не передают и продолжают
отклонять.

Не покрыто (сторона ПОДПИСИ): `xades::source::material_xml`/`complete_signature`, `sign.rs`,
`xades.rs` и `references/extension.rs` по-прежнему строят неподписанные свойства как `String`,
ограниченные `max_metadata_bytes`, поэтому подпись или расширение XAdES-LT/LTA с CRL больше
256 КиБ отклоняются с `MetadataLimit`. Оставшийся дизайн: писать сгенерированные свойства в
промежуточный артефакт (их каноническая форма при exclusive C14N равна тексту, которым они
генерируются, так что покрытие архива и отрезки листьев не требуют разбора; доказать
дифференциальным тестом против `canonical_stream`) и собирать голову + промежуточные неподписанные
+ хвост.

## Встроенный статус LT/LTA оценивается на момент доказательства

Статус отзыва, который несёт подпись (ответы OCSP, CRL у CAdES/PAdES/XAdES `LT` и `LTA`), —
свидетельство для проверки спустя долгое время после выпуска. Раньше он оценивался по часам
проверяющего (`nextUpdate`, `ALLOWED_PERIOD`, срок действия сертификата ответчика на `now`),
поэтому документ, который при подписании давал `Valid`, через несколько минут становился
`Indeterminate`, при любом размере. Теперь правило живёт в одном месте, в `oncl-pki`
(`ocsp::check_embedded_at_proof`, `crl::serial_status_at_proof`, выбираются через
`validation::offline_revocation`; переключатель — `pkix::Currency`), и им пользуются CAdES,
XAdES и PAdES.

**Правило.** Когда проверяется время доказательства `P`, встроенный ответ OCSP или CRL о
сертификате пути принимается, если всё, что проверялось раньше, по-прежнему проходит (CertID,
привязка эмитента, подпись, цепочка ответчика и OCSPSigning/no-check, `unknown` отклоняется, CRL
— полный CRL эмитента) и при этом:

* свеж на `P` (EN 319 102-1 5.2.5.4: максимальная свежесть `nextUpdate - thisUpdate`, если
  ограничение не говорит иное): при наличии `nextUpdate` (у каждого CRL и у ответа OCSP, который
  его имеет) ответ свеж тогда и только тогда, когда `P < nextUpdate`, так что 35-дневный CRL УЦ,
  выпущенный за часы до доказательства, годится; без него (OCSP НУЦ) — тогда и только тогда,
  когда `P - CLOCK_SKEW < thisUpdate` (300 с, строго);
* `thisUpdate <= now + CLOCK_SKEW` (для CRL: `thisUpdate <= now`): никогда не из будущего
  проверяющего;
* сертификат ответчика строит цепочку **на момент `thisUpdate`** (а не `now`);
* `nextUpdate` и `ALLOWED_PERIOD` с `now` не сравниваются.

`P` — genTime штампа времени подписи (`T`, `LT`) — для документного штампа времени PAdES это
первое доказательство — и для `LTA` тот же штамп времени подписи: архивные штампы времени защищают
свидетельства, но `P` не двигают (статус, встроенный после штампа времени подписи и до архивного
штампа, должен оставаться приемлемым). Встроенный статус собственного сертификата службы штампов
времени оценивается так же, с genTime того токена в роли его `P`. Без времени доказательства
(уровень `B`, отсутствующий или недействительный штамп) `at` равен `now`, и прежнее правило
сохраняется; статус, полученный онлайн, всегда оценивается как актуальный на `now`.

Без изменений: сертификаты подписанта и цепочки оцениваются как действительные **на `P`** (так
было и раньше: `certificate_facts` и путь до якоря используют `P`); отозван в `P` или раньше —
`Invalid`; отозван после `P` — подпись остаётся действительной и сообщается
`RevokedAfterProvenTime`.

**Считаются все приемлемые статусы (выбор).** Для одного сертификата оценивается каждый
встроенный ответ OCSP и CRL, прошедший проверки выше, в произвольном порядке (их число ограничено
лимитами хранилища свидетельств). Любой приемлемый `revoked` отзывает: сообщается самое раннее
время отзыва среди них (в `P` или раньше: `Invalid`/`Revoked`; после `P`:
`RevokedAfterProvenTime`). `Good` требует хотя бы одного приемлемого `good` и ни одного
`revoked`; иначе статус остаётся `Unavailable`. Неприемлемый статус (устарел, не тот эмитент или
ответчик, другой сертификат, `unknown`) по-прежнему игнорируется и никогда не превращает
`Unavailable` в `Good`. Ответ `good`, стоящий первым, больше не скрывает последующий `revoked`.
Статус, полученный онлайн (`check_path_revocation`), использует ОДИН источник на сертификат (CRL
загружается, только если OCSP не дал ни `good`, ни `revoked`). Это остаточная слабость, а не
исправление: `good` OCSP от ответчика принимается без обращения к CRL, который мог бы сказать
`revoked`. EN 319 102-1 требует приемлемой информации о статусе, а не всех доступных источников,
так что это выбор политики, зафиксированный как открытый. Кроме того, у `offline_revocation` нет
контрольной точки работы/дедлайна внутри цикла по статусам (граница — только лимиты хранилища
свидетельств; худший случай равен прежнему случаю без приемлемого статуса).

**Стандартная основа (ETSI EN 319 102-1 V1.3.1, прочитано по опубликованному тексту).** 5.2.5.4
(проверка свежести отзыва): статус свеж, когда `issuance time > validation time - maximum accepted
freshness`; 5.5.4 шаг 6 повторяет проверку со *временем лучшей подписи*, когда статус не был
свеж относительно текущего времени; 5.5.4 шаг 4a: время отзыва после времени лучшей подписи
подпись не делает недействительной, в этот момент или раньше — `INDETERMINATE/REVOKED_NO_POE`;
5.2.6.4 (валидация сертификата X.509) запускает проверку со временем валидации и не сверяет с ним
сертификат подписи CRL эмитента. Умолчание `nextUpdate - thisUpdate` из шага 1 5.2.5.4 применяется
к ответам, несущим `nextUpdate`; для ответов OCSP НУЦ, которые его не несут, свежесть — это
ограничение `CLOCK_SKEW` (стандарт говорит FAILED без nextUpdate, пока ограничение не задано).

**Окно повтора.** Окно, в котором атакующий, владеющий ответом «good» до отзыва, может его
использовать, — собственная действительность ответа, `nextUpdate - thisUpdate`: до 35 дней для
CRL НУЦ (300 с для ответа без `nextUpdate`). Архивный штамп времени / доказательство
существования `LTA` его не сужает: `P` — genTime штампа времени подписи, а архивные штампы лишь
защищают встроенное. Это умолчание стандарта и окно прежнего правила на момент подписания.

**Не проверено / намеренные отличия.** (0) Доказательства на настоящей PKI нет: закреплённые
fixtures NCANode LT здесь никогда не достигают времени доказательства, так что каденция НУЦ
(35-дневный CRL корня, выпущенный за часы до штампа времени) проверена записанным
производственным CRL (`tests/crl.rs`) и синтетическим 35-дневным CRL, а не Valid-документом
настоящей PKI; путь простого CMS офлайн покрыт тестом `oncl-core`
`offline_cms_status_is_judged_at_the_proof_time_not_the_host_clock`; `P` — ПОСЛЕДНИЙ прошедший
штамп времени подписи, тогда как стандарт (5.5.4 шаг 3b) берёт самый ранний (консервативно, было
и раньше). (1) 5.6.2.2.4 шаг 2a также просит доказательство существования информации об отзыве
не позже контрольного времени; для `LTA` это архивный штамп времени, связывающий свидетельства,
который проверяется графом свидетельств, для `LT` оно не запрашивается (кроме штампа времени
подписи ничего нет), как и в 5.5.4. (2) Строгое `>` и свежесть 300 с — выбор в пределах
ограничения, которое стандарт оставляет политике валидации, а не предписанные им значения. (3)
Отозван в `P` или раньше — здесь `Invalid`; стандарт говорит `INDETERMINATE/REVOKED_NO_POE`
(строже, без изменений). (4) Правило модели цепочки стандарта о компрометации ключа при отзыве
УЦ после `P` не моделируется.

## Плотные PDF: бюджет перекрёстных ссылок (D4, D6)

`PdfLimits::max_objects` (по умолчанию 4096) ограничивает только обходы ГРАФА объектов: число
полей AcroForm, элементы свидетельств DSS, члены одного потока объектов, обход представления
подписи. Он больше не потолок размера документа. Размер документа в объектах ограничен
`PdfLimits::max_xref_entries` (по умолчанию 4 Mi записей по ВСЕМ ревизиям), и за каждую запись
платится:

| Что | Стоимость |
|---|---|
| строка перекрёстных ссылок (любой ревизии) | 16 байт памяти операции, резервируется по мере чтения строки (шагами не более 65 536 строк), а не заранее |
| серия последовательных номеров объектов | 32 байта (в худшем случае по одной на запись) |
| классическая таблица xref / поток xref | читается чанками по 64 КиБ / инкрементально разжимается (включая предиктор PNG) прямо в строки; декодированная таблица не удерживается, `max_object_bytes` и `max_decoded_bytes` на неё больше не действуют, размер после разжатия ограничен объявленными строками и `max_decode_work` |

Отклоняется до выделения любой строки: объявленное число сверх оставшегося бюджета и число,
которое остаток файла вместить не может (классика). Лишние или недостающие данные потока xref
обнаруживаются только после того, как присутствующие строки прочитаны и списаны (это
некорректный документ, всё равно отклоняется до использования ключа). Сверх бюджета отказ —
`PdfError::Limit("xref entries")` (limit+1 точно, по всем ревизиям); квота памяти, не
вмещающая строки, — `MemoryLimit`; оба происходят при чтении, до любого использования закрытого
ключа (`NotApplied`). Классическая таблица принимается независимо от того, куда падают границы
чанков по 64 КиБ: заголовок подраздела или запись, разрезанные концом чанка, перечитываются из
свежего чанка (в том числе когда её последний токен упирается в конец чанка, где число может быть
разрезано), так что приём обычных записей от выравнивания не зависит; единица, начинающаяся с
начала чанка, принимается, если заканчивается раньше этого чанка по 64 КиБ, и отклоняется
иначе. Заголовок подраздела, окружённый более чем чанком пробелов, всё ещё может быть отклонён в
зависимости от выравнивания (отказ закрытием; в реальных документах так не бывает).

Не списывается (ограниченные временные): чанк чтения 64 КиБ, буферы строк разжатия/предиктора
(`RowReader`, одна строка предиктора не больше `max_object_bytes`) и копия при росте вектора строк
(не больше одного шага, 1 МиБ, сверх списанной ёмкости).

Хосты, делающие предварительную проверку обновления PAdES, добавляют строки через
`budget::PriorSignatures::xref_entries` → `budget::PlanInputs::xref_entries`
(`budget::xref_memory` — верхняя оценка, используемая `plan_memory`); сервер так и делает.
`budget::reader` больше не масштабируется с `max_revisions`.

Замеры (отладочная сборка, настоящий процесс `oncl`, `scripts/pdf-dense/gen_dense_pdf.py`, три
ревизии, перепроверено pyHanko; подпись выходного файла цела на всём файле): 1 M объектов,
классический xref (123 МБ) подписывается за 3,2 с при пике рабочего набора 43 МБ; 1 M объектов
как потоки объектов + потоки xref Flate/PNG (58 МБ) — 1,9 с при 44 МБ; 4 M объектов (потолок по
умолчанию) — 13,5 с при 135 МБ.
