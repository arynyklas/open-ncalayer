# OpenNCALayer Platform Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Реализовать утверждённую Rust-платформу OpenNCALayer: SDK, независимые desktop/CLI/HTTP, полный функциональный охват pinned NCANode и обработку содержательных XML/PDF до 10 ГиБ в контрольном RAM-бюджете 1 ГиБ.

**Architecture:** Общий `oncl-core` исполняет типизированные операции и политики, используя PKI и отдельные XML/PDF-модули. Потоковое I/O и ресурсные механизмы лежат ниже форматов, чтобы не образовать цикл Core → format → Core. Приложения предоставляют авторизацию, взаимодействие, секреты, аудит и транспорт; GUI/installer/self-update не становятся обязательной частью SDK.

**Tech Stack:** Rust и существующий Cargo workspace; существующие PKI/ГОСТ/PCSC/wasmi; Slint software renderer; Tokio, rustls, ureq; новый HTTP adapter на axum/hyper; RSA private operations через CNG на Windows и AWS-LC на Unix; OpenTelemetry/OTLP только в выбранной серверной конфигурации.

**Spec:** [Утверждённый дизайн](../../design/platform.md). Исполнитель читает оба документа. План не разрешает самостоятельно сокращать дизайн.

**Статус:** утверждён пользователем 2026-11-02, включая WinGet. Исполнение — **subagent-driven**, не Native. F01–F04, C01/C02 и X01 реализованы и приняты после RED/GREEN, smoke и независимого review; остальные задачи остаются открыты. 2026-11-03 пользователь отдельно разрешил локальные коммиты, изолированные worktree C03/XML/PDF и локальную интеграцию. Push и публикации не разрешены.

## Global Constraints

- До 10 ГиБ исходного документа: `10_737_418_240` байт; XML и PDF обязательны, а не только транспорт больших байтов.
- До 1 ГиБ RAM: `1_073_741_824` байта фактической памяти контрольного 64-битного процесса с одной активной операцией; отдельно учитывать контейнер/framing и выходные накладные байты.
- Содержательные случаи больше 2/4 ГиБ; никаких доказательств готовности одним padding/sparse-файлом.
- Ограниченное временное хранение документов разрешено; ключи/пароли из запросов не выгружаются в spool; постоянной очереди и архива документов нет.
- Собственный HTTP API полностью выключен по умолчанию; после включения — loopback, индивидуальные токены и права. LAN/TLS или доверенный reverse proxy включаются явно.
- Desktop подтверждает конкретное действие; headless имеет заранее выданные полномочия, не автоответы на диалоги. Межоперационного кеша desktop-разблокировки нет.
- Перед применением закрытого ключа сервис обязан успешно записать локальный аудит. Сбой после применения не выдаётся за «ключ не использован».
- OTLP: только опциональные метрики/spans, off по умолчанию, ограниченные буферы; collector не блокирует операции и не заменяет аудит.
- ГОСТ-2004, ГОСТ-2015/512, RSA; НУЦ РК и явно настроенные CA. Применимые ГОСТ-профили шифрования обязательны, не заменяются одной RSA-веткой.
- Файловые PKCS#12/JKS и наши токены; не добавлять экспорт закрытых ключей, запись JKS/токенов, PKCS#11/HSM или произвольный UI плагинов.
- Старые контракты NCALayer, пакеты/ABI и документированные отличия сохраняются; новые большие лимиты и HTTP-auth не переносятся на WSS неявно.
- Сохранять desktop-матрицу, включая Win7 x86/x64, закреплённые toolchains, статический CRT и существующие платформенные гейты. Не отключать target ради нового dependency.
- Общий номер workspace для SDK/приложений; версии плагинов не объединять. Реальные crates.io/browser-store публикации отложены.
- WinGet desktop: только stable, Windows 10 1809+ x64/x86, per-user; штатный updater сохраняется. Генерация/локальная приёмка обязательны, первая подача в microsoft/winget-pkgs и внешняя публикация — отдельное разрешение; до приёма не заявлять каталогную доступность.
- Работать в изолированных worktree, не перезаписывать чужие изменения. Отдельное разрешение пользователя 2026-11-03 допускает локальные коммиты проверенных блоков и локальную интеграцию веток. Push, внешние PR/MR и публикации по-прежнему требуют отдельного разрешения.
- Не создавать реализационные stubs/auto-yes/fake fallback. Промежуточная задача может добавить законченный частный механизм, но полный продукт не считается готовым до финальных гейтов.
- Переносить все реальные потребители изменённого экспорта, удалять устаревшие пути без re-export/shim. Перед переносом использовать LSP references/rename при работающем сервере.
- Permanent tests проверяют поведение, границы, ошибки и безопасность. Не создавать source-text/import/wiring/mock-echo тесты; существующие тесты случайных UI-формулировок удалять, не перепривязывать к новой копии.
- У каждого изменения: RED до реализации, GREEN после интеграции и реальный smoke. При параллельной работе проверки выполняет владелец интеграции вне работающих агентов; форматирование/полный lint/build — один раз после согласованного набора изменений.

## Review Focus

1. Подтверждённый источник меняется после выбора, Enter из пароля или double-click сертификата попадает в подтверждение: новые байты/случайный ввод не должны применять ключ. Тесты B01/U02.
2. `Content-Length` отсутствует/лжёт, multipart boundary разбит между чанками, секретный part похож на файл: соблюдать квоты без полного буфера и не писать секреты в spool. Тесты F01/S03.
3. Ключ уже применён, затем отказывает аудит/запись/соединение: не обещать rollback/exactly-once, не фиксировать частичный результат как успех. Тесты S01/B01/T02.
4. Большие XML-ссылки/namespace-границы и PDF offsets/object streams/revisions пересекают 4 ГиБ: проверять фактически подписанные байты, не усекать offsets и не принимать wrapping/перекрывающиеся ByteRange. Тесты X02/X03/X05/P01/V01.
5. Разрешённый plugin/route пытается подменить вложенный method, ключ или Origin; сертификат навязывает внутренний AIA/CA URL; JWT задаёт `alg=none`: полномочия/доверие не расширяются по данным запроса. Тесты F03/J01/L01/S02.

## 2. Общие интерфейсы между задачами

Имена ниже фиксируются планом; тела реализаций здесь не пишутся. Конкретные profile-поля берутся из перенесённых существующих spec-типов и pinned-матрицы, не из произвольного JSON.

### 2.1 I/O и ресурсы: F01

В `oncl_pki::io`: `ReadSeek: Read + Seek`, `Source<'a>` (последовательный либо seekable reader с `Option<u64>` известной длины), `Region { offset: u64, len: u64 }`, `TemporaryStore`, `StagedArtifact`. Последний не публикует файл при Drop: публикация — отдельный успешный `commit`/`copy_to`.

В `oncl_pki::resource`: `ResourceLimits`, `ResourceScope`, `ProcessingError`, `Progress`, `Deadline`, `SharedBudget`, `ResourceReservation`, `OperationLease` и `OperationControl: Send + Sync` с `checkpoint(&self, progress: Progress) -> Result<(), ProcessingError>`. Scope ограничивает одну операцию; один SharedBudget ограничивает совокупные in-flight operations, live memory и временный диск всех её scopes. Резервирование/освобождение checked и RAII, до выделения/записи; отдельный SharedBudget на каждый HTTP-запрос запрещён. Базовый I/O chunk — 256 КиБ, metadata имеет отдельную квоту.

`ResourceLimits.operation_timeout` задаёт конечный ненулевой timeout; Deadline на монотонных часах охватывает intake, ожидание executor/token, crypto/PKI и выдачу результата. Cancel/deadline различаются от Invalid signature. Root OperationLease разделяет время жизни worker и response/output artifact: drop соединения не освобождает занятые worker/reservation раньше фактического конца, а медленный output не делает удерживаемый temp «бесплатным».

В S02 `oncl_server::executor::BoundedExecutor` имеет отдельные workers/queue_capacity/admission_wait limits. `submit(ctx: OperationContext, work)` принимает owned context и Send work, возвращает ограниченно ожидаемый WorkHandle; closure получает тот же context/Scope, не новую квоту. Workers используют spawn_blocking только после получения permit; неограниченная очередь Tokio blocking pool не служит admission control. Runtime/Tokio не входят в низкоуровневый SharedBudget.

В `oncl_pki::digest`: `DigestValue` с алгоритмом и фиксированным буфером не более 64 байт; `HashState::new(HashAlg)`, `update(&mut self, &[u8])`, `finish(self) -> DigestValue`; `hash_source(Source<'_>, HashAlg, &mut ResourceScope) -> Result<DigestValue, ProcessingError>`.

Контрольный профиль для resource-harness: document `10_737_418_240`, RAM `1_073_741_824`, scratch `68_719_476_736` байта; metadata `67_108_864` байта. Это входные значения контрольного стенда, не обещание, что любая комбинация batch/metadata поместится в тот же диск. Container/output/framing имеют отдельные проверяемые квоты; корректная надбавка к целевому документу принимается обратно verifier/decryptor.

### 2.2 Контекст, ключи и отчёты: F01–F03

F01 определяет Core `Engine`, `EngineServices`, owned `OperationContext`, `OperationId`, `ExecutionGrant`, `Action`, `OperationPolicy`, `OperationError/ErrorCode`, HashReport и декларацию `ValidationPolicy` ниже PKI. `EngineServices::hash_only(ResourceLimits)` создаёт один общий budget на Engine и исполняет hash без настройки ключей/сети/temp; `with_shared_budget(Arc<SharedBudget>)` подключает единый бюджет приложения. Новые зависимости добавляются реализующими их задачами, не пустыми backend.

F02 добавляет `KeyId`, `KeySelector`, `KeyRequest`, `KeyLease`, `KeyProvider`, `AuthorizedSigner`, `KeyUseGuard`, `KeyUseReceipt`, `KeyUseEvent`, `KeyUseOutcome`, `TokenDeviceId`, `TokenGateRegistry`, `AppliedState::{NotApplied, Applied, Unknown}` и `EngineServices::with_keys(provider, guard)`. TokenGateRegistry — bounded admission/device-execution registry по physical device/reader, не второй APDU mutex: сериализацию уже обеспечивает существующая PC/SC transaction и её emulator holder/Condvar. Registry ограничивает ожидающие работы/срок и не допускает неограниченных заблокированных threads; разные devices/software keys не получают общего lock. F03 добавляет ValidationServices/with_validation. Отсутствующая требуемая зависимость даёт MissingKeyProvider/MissingValidationServices, не выдуманную функцию.

`OperationPolicy` содержит `validation: ValidationPolicy`, допустимые алгоритмы подписи и явное `allow_prehashed`; factories strict_online/offline_report/ncalayer_compatibility не принимают привилегию из wire. F01 реально применяет grant/ресурсные ограничения hash, F02 — key/action restrictions, F03 реализует полную validation-семантику. OfflineReport не разрешает ослаблять обязательные проверки перед private operation.

`OperationContext` — owned/Send состояние одного явного вызова/пакета: grant, policy, ResourceScope, время и `Arc<dyn OperationControl>`, с F02 — локальные leases. Он переносится из HTTP intake в bounded worker и не разделяется между несвязанными запросами; shared только Root OperationLease, передаваемый также финальному response/output. `KeyProvider::open(&self, request: &KeyRequest<'_>, ctx: &mut OperationContext) -> Result<KeyLease, OperationError>`. Grant создаёт доверенный хозяин/authorizer, не Deserialize; KeyLease не экспортирует private material.
Worker захватывает собственный `Arc<Engine>` отдельно от owned OperationContext и передаёт context в работу; context не заимствует Engine/control/Slint handle. Это два независимых owned значения, не self-referential move и не обещание `OperationContext<'a>`.

`KeyUseGuard::before_use(&self, event: &KeyUseEvent) -> Result<KeyUseReceipt, OperationError>` и `finish(&self, receipt: KeyUseReceipt, outcome: KeyUseOutcome) -> Result<(), OperationError>`. Local/desktop guard проверяет явное полномочие/consent; durable server guard дополнительно пишет аудит. Это реальные разные политики, не пустая реализация server guard.

В `oncl_pki::key`: `DigestSigner` с `certificate() -> &Certificate`, `algorithm() -> SigAlg`, `sign_digest(&mut self, digest: &DigestValue) -> Result<Vec<u8>, KeyError>`; `PublicKey::verify_digest(SigAlg, &DigestValue, &[u8])`. Core предоставляет `AuthorizedSigner`, который выполняет guard/grant перед реальным применением lease. Форматные модули не зависят от Core.

В `oncl_pki::validation`: `ValidationPolicy::{StrictOnline, OfflineReport, NcalayerCompatibility}`, `ValidationContext`, `CheckStatus`, `SignerValidation`, `ValidationReport`, `Verdict::{Valid, Invalid, Indeterminate}`. Контекст/ожидаемое доверие устанавливает хозяин, не произвольный клиентский payload.

### 2.3 Публичные семейства Engine

Каждый метод добавляется только задачей с рабочей реализацией; не объявлять будущие ветки, возвращающие выдуманный успех/`unimplemented!`.

```text
Engine::new(services: EngineServices) -> Result<Engine, OperationError>;
Engine::begin(&self, grant: ExecutionGrant, policy: OperationPolicy,
              control: Arc<dyn OperationControl>) -> Result<OperationContext, OperationError>;
Engine::hash(&self, algorithm: HashAlg, input: Source<'_>,
             ctx: &mut OperationContext) -> Result<HashReport, OperationError>;
Engine::sign(&self, request: SignRequest<'_>, input: Source<'_>, output: &mut dyn Write,
             ctx: &mut OperationContext) -> Result<OperationReport, OperationError>;
Engine::verify(&self, request: &VerifyRequest, input: Source<'_>, detached: Option<Source<'_>>,
               ctx: &mut OperationContext) -> Result<VerificationReport, OperationError>;
Engine::extend(&self, request: &ExtendRequest, input: Source<'_>, output: &mut dyn Write,
               ctx: &mut OperationContext) -> Result<OperationReport, OperationError>;
Engine::extract(&self, input: Source<'_>, output: &mut dyn Write,
                ctx: &mut OperationContext) -> Result<ExtractionReport, OperationError>;
Engine::encrypt(&self, request: &EncryptRequest, input: Source<'_>, output: &mut dyn Write,
                ctx: &mut OperationContext) -> Result<EnvelopeReport, OperationError>;
Engine::decrypt(&self, request: &DecryptRequest<'_>, input: Source<'_>, output: &mut dyn Write,
                ctx: &mut OperationContext) -> Result<EnvelopeReport, OperationError>;
Engine::inspect(&self, request: &InspectRequest<'_>, input: Option<Source<'_>>,
                ctx: &mut OperationContext) -> Result<InspectionReport, OperationError>;
Engine::stamp(&self, request: &StampRequest, input: Source<'_>, output: &mut dyn Write,
              ctx: &mut OperationContext) -> Result<TimestampReport, OperationError>;
Engine::verify_stamp(&self, request: &StampVerifyRequest, token: Source<'_>, data: Option<Source<'_>>,
                     ctx: &mut OperationContext) -> Result<TimestampReport, OperationError>;
```

`SignRequest` содержит profile, Create/Add mode, ограниченный список signers/KeyRequest и при необходимости detached-источник; профиль определяет семейство, не скрытый filename guess. `ExtendRequest` содержит существующее семейство и целевой AdES level. `EncryptRequest` содержит EnvelopeProfile и сертификаты получателей; `DecryptRequest` — KeyRequest и разрешённые profiles. `InspectRequest` различает Certificate/Container/NamedKey/SignatureMetadata; он не создаёт новые ключи. Requests с секретами не получают Serialize/открытый Debug/необоснованный Clone.

`OperationReport` содержит id, профиль, bytes in/out и результат. `VerificationReport` содержит Verdict, per-signer checks, реальную policy/time basis и причины. `EnvelopeReport` различает authenticated/unauthenticated content и не утверждает авторство отправителя. Fatal execution error отличается от завершённого отчёта с Invalid/Indeterminate.

Features Core `tokens`, `xml`, `pdf`, `jose`, `plugins` добавляются с реализующими их задачами; отсутствующие path dependencies заранее не объявляются. `full` объединяет готовые features в R01. Все продуктовые приложения полной поставки собираются с нужным полным набором; минимальный SDK — отдельно.

### 2.4 Проверки и smoke без дублирования scaffolding

F01 создаёт рабочий `crates/oncl-core/examples/sdk_probe.rs`: сначала только hash. Каждый форматный шаг добавляет в него реальный case с именем своей задачи (`C01`, `X03`, ...), который исполняет настоящую операцию и записывает артефакты/итог в `--out`. Не реализованный case отсутствует/даёт usage error, не fake pass. Probe использует только synthetic fixtures через `oncl-testkit`; чтение whole-file helper допустимо для маленького контейнера ключа, не для большого документа.

Общий smoke форматных задач: `cargo run -p oncl-core --features <готовые-features> --example sdk_probe -- --case <ID> --out target/platform-smoke/<ID>`. Ожидается корректный крипторезультат/контрольный отказ и проверяемые артефакты; не просто «процесс не упал». Полное независимое interop и большие случаи добавляются V01/V02, не заменяются этим smoke.

В каждой задаче RED/GREEN выполняется указанной командой: сначала после добавления поведенческого теста, до исправления (ожидаемый конкретный FAIL; для нового модуля допустима ошибка отсутствующего API), затем после реализации (PASS). Существующий сообщённый пользователем сбой не перезапускается ради подтверждения.

## 5. Самопроверка и исполнение

Перед передачей плана проверяются: покрытие всех разделов spec, зависимости, единые имена общих интерфейсов, отсутствие consumer→Core→format→Core циклов, отсутствие будущих ссылок на несуществующие path dependencies и отличие ожидаемых результатов от выполненных прогонов. Тела криптоалгоритмов/серверов здесь не написаны; интерфейсы и проверяемые решения заданы, выбор внутренних структур внутри этих ограничений остаётся исполнителю.

При исполнении сначала читаются актуальные manifests и изменения пользователя: нынешняя version/toolchain/порядок релизов могут измениться после даты плана. Новые зависимости pin/lock и advisories проверяются на этот момент. Нельзя незаметно перейти к уязвимому private RSA backend или убрать Win7 ради удобства dependency.

Пользователь утвердил план и выбрал task-by-task **subagent-driven** с отдельными агентами/review. Не подменять этот метод на Native без нового решения пользователя. Запуск реализации требует отдельной команды; перед стартом проверить доступность провайдера. На этапе подготовки агентные проверки были недоступны из-за лимита провайдера — это не положительное review. Самопроверка документа выполнена автором; реализация и whole-branch review ещё не выполнены.

### 5.1 Явный override workflow и handoff субагентам

- **Локальные коммиты разрешены отдельно 2026-11-03:** сначала проверенный checkpoint интеграционной ветки, затем коммиты законченных проверенных блоков в отдельных worktree и локальная интеграция. Не коммитить stubs, частичный success или известные незакрытые дефекты. Push/внешние PR/MR/публикации не разрешены; чужие dirty-файлы и приватные ledgers/артефакты не включать.
- Каждый task brief содержит собственный полный Task, Global Constraints, дословные реализуемые/потребляемые интерфейсы §2, конкретные predecessor snapshots/patches и точные RED/GREEN/smoke команды. Относительные сокращения Files раскрываются до workspace paths. Отдельный ownership list задаёт writable subset; общие Cargo/engine/context/policy/validation файлы принадлежат только владельцу интеграции, если не выделено явное эксклюзивное окно.
- Агент не переименовывает shared type, не меняет чужой файл/ожидания теста и не расширяет public interface за пределами ownership. Необходимое изменение передаётся как конкретный interface delta владельцу интеграции до дальнейшей работы. У зависимой задачи вход — принятый актуальный predecessor snapshot/diff, не только исходный текст плана.
- Последовательность обязательна для F01→F02→F03, S01→S02→S03, U01→U02→U03→U04; X01/export cutover имеет эксклюзивное окно consumers; M01 и R02 завершаются до W01, W01 — до W02. Разрешённые параллельные C03/XML/PDF работают в отдельных worktree от проверенного checkpoint; общие Engine/profile/Cargo контракты фиксирует владелец интеграции, который также разрешает конфликты при локальной интеграции.
- **Изолированные проверки:** в каждом отдельном worktree его владелец выполняет собственный RED до реализации, GREEN и actual smoke после правок, используя отдельный CARGO_TARGET_DIR и ограниченный CARGO_BUILD_JOBS. Соседние worktree не читаются и не редактируются. Команды/stdout/stderr/exit code сохраняются в report; независимый reviewer проверяет diff и evidence, а владелец общей интеграции выполняет проверку объединённого результата. Для нескольких writers в одном worktree проверки остаются централизованными и выполняются после их завершения.
- Task/whole-branch reviewer получает brief, report и реальный task-scoped BASE/HEAD diff после локального коммита либо before/after snapshot, включая additions. Пользовательские и предыдущие принятые изменения не приписываются текущей задаче. Ledger complete ссылается на реальные commits/artifacts и фактические проверки; независимый reviewer не подменяется self-review.
